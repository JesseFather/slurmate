# sshd（SSH 中转站）

作业里跑一个**用户态 sshd**。原生 VS Code Remote-SSH、codex 这类**要求一个 ssh
连接**的工具都从这里接进来 —— 而用户不能直接 ssh 到计算节点。

这是一个**独立项目** —— 它是 Slurmate 的一个插件，但 Slurmate 不依赖它。
契约（目录形状、清单的每个键、作业侧钩子）见 [`../README.md`](../README.md)，
这里只讲**这个插件自己**的事。

```
sshd/
  plugin.json            清单
  client/index.js        准备密钥 + 写 ~/.ssh/config
  client/sshconfig.js    让用户自己的 ssh 认出一个恒定别名
  job/start.sh           作业侧的用户态 sshd
```

★ 这里**不写每个文件有几行**（从前写过）—— 行数是行号的另一种写法，改一行代码它
就开始说错话，而没有任何东西会因此变红。理由见
[CONTRIBUTING.md](../../CONTRIBUTING.md) 的〈文档：指路按符号名，不写行号〉。

## 它给的是什么：在 Slurm 分配里的一把 ssh

★ **这一段是理解这个插件的前提，不是免责声明。**

站点通常用 `pam_access` + `/etc/security/access.conf` 限制谁能 ssh 进计算节点。
这个用户态 sshd **读不到那份策略**，而且是**结构性**的：非 root 的 sshd 只能用
`UsePAM no`，PAM 栈整个不跑，`pam_access` 从不执行。

它不是"绕过了白名单"就完了 —— 白名单要保护的那件事是**「用户不在 Slurm 监管下
使用计算节点」**，而这个会话**就在监管之下**，实测可证：

1. 会话的 cgroup 落在 `job_<id>/step_batch` 里（与作业同一个）；
2. 三重 `setsid` 想脱离的进程，作业一结束就被收掉，一秒都活不过去。

**换句话说：它给的是「在 Slurm 分配里的一把 ssh」，不是「一个逃出 Slurm 的 ssh」。**

★ 因此**不要**试图让它去遵守白名单（比如打开 `UsePAM`）。那会让功能对**所有**
普通用户失效 —— 站点那份 `access.conf` 通常只放行 root 与管理员。

### 爆炸半径

注入的是**公钥**（不是秘密），授的是「以你自己身份进入你自己的作业」。

非 root 的 sshd 根本无法切换成别的用户，所以最坏情况是作业属主让别人用**他自己
的**账号 —— 那是他本来就有的权力，不产生任何新访问。

## 站点侧

```ini
[plugin:sshd]
enabled      = yes          # ★ 缺省是 no（清单里 defaultEnabled = false）
default_cpus = 1
default_mem  = 2G
bin          =              # 留空 = /usr/sbin/sshd（清单里的 convention）
```

★ **`defaultEnabled` 是 `false`，这是刻意的。** 那个标记为 `true` 的只有一种插件：
「升级前那个唯一可用的服务」。新插件标 `true` 等于给所有站点在升级时**静默多开
一个能力** —— 而这一条开出来的是一条交互式 ssh 的路。**想开就写 `enabled = yes`。**

★ 这是唯一一个清单里 `bin.discovery` 用 `convention` 的插件：sshd 的路径是
约定（`/usr/sbin/sshd`），而 `which` 的结果只是"登录节点上恰好有这个文件"——
守护进程跑在登录节点上，作业跑在计算节点上，那两件事无关。对 sshd 来说，
`convention` **反而比 `which` 更可信**。

### 提交时必须带一行公钥

清单里的 `contributes.submitPubkey` 是 `true`，所以：

- 客户端提交前会先备好一把密钥（`client/index.js` 的 `prepare`）；
- 守护进程校验它，并下发 `SLURMATE_SSH_PUBKEY`。

**没有它守护进程会拒绝这次提交**（`code 2`）—— 校验在提交时发生，不是等到作业
跑起来。

## 客户端侧

它**没有** `contributes.surface`，所以框架**连一块界面都不会建**。用户要用的东西
跑在他自己的机器上；客户端唯一要做的事，是让 `ssh slurmate` 这个名字能连进来。

### 两把钥匙，别搞混

| 钥匙 | 在哪 | 干什么 |
|---|---|---|
| IDM 私钥 | 用户手工注册到账户 | 登录**登录节点**（与 Slurmate 无关，是集群的事） |
| 中转站密钥 | 插件的**数据目录**里（见下） | 登录**作业里的那个 sshd** |

中转站这把是**一次性**的：只被写进你自己那个作业的 `authorized_keys`，**任何一个
IDM 或集群的登录入口都不认识它**。

★ **所以它可以不加密地躺在磁盘上**，而别处的私钥必须加密存盘。偷到它的人还得先
有你的 IDM 私钥才能连上登录节点、开隧道进去 —— 他得先拿到那把更值钱的钥匙。

### 它的三个文件住在哪儿

| 文件 | 归谁 |
|---|---|
| `config`、`known_hosts`、`id_ed25519` | **插件的** —— 住在框架给的**插件数据目录**里（`ctx.dataDir()`），一个插件一份 |
| `~/.ssh/config` | ★ **用户的** —— 我们只往最上面加两行 `Include`，其余一个字不动 |

★ 那个目录的路径由**插件身份**算出来（`plugin.json` 里声明了
`contributes.data.inherit = "relay"` ⇒ 同一个插件的各个版本共用一份），所以它对每个
用户、每种安装位置都不同 —— **别把它写死**。它的好处是基座知道它在哪儿：面板上的
「本机的插件数据」列得出、也删得掉。

★ **而这一份不会被"回收一个布局组"带走。** 那个动作清的是**属于某个布局组**的数据
（浏览器存储 + `ctx.dataDir()` 那个目录），判据是清单里的 `perInstance`。这个插件
**没有**声明它 —— 它只有一份，不属于任何一个组。
★ 反过来说：一份数据属于某个组、还是不属于任何组，决定的是**用户删掉一条 ssh 条目
时它会不会跟着走**。这里选"不跟着走"是因为 `config` 与 `id_ed25519` 重建要重新注册，
而且它们与服务端那一份是配套的。

★ 写进 `config` 里 `User` 那一行的是**这条会话所属那条连接**里的用户名
（`ctx.connection()`）—— 不是"当前活跃连接"，也不是 `whoami()`（后者是模块级单值，
而切换活跃连接**不会**停掉已经在跑的会话 ⇒ 它可能给出**另一个站点**的用户名）。
拿不到连接时**不写**，只报一句 —— 写错那个字段的症状是"ssh 连上了，但不是你要的那台
机器"，而用户完全看不出为什么。

★ 从前这三个文件住在 `~/.slurmate/ssh/` —— 那是这个插件**自己发明**的位置。搬家的
理由就是这个：插件不该自己决定"我往用户的机器上放什么、放哪儿"。旧位置的残留会在
下一次会话建立时自动清掉（见 `sshconfig.js` 的 `dropLegacyFiles`）。

### 改用户的 `~/.ssh/config`：三条纪律

`ssh slurmate` 这个名字不在 DNS 里，也不可能在 —— 它只能来自 ssh 的配置文件。
客户端没有第二条路。所以 `sshconfig.js` 会动那个文件，而那是整个客户端里**最容易
造成灾难性后果的一次写盘**（那个文件坏了，用户所有的 ssh 都不通）。

1. **绝不重写。** 只往**最上面**加两行（一句注释 + 一行 `Include`），其余内容
   **逐字节原样保留**。
2. **`Include` 必须在最上面。** ssh 对每个参数取「第一个获得的值」，所以用户自己
   那份配置里常见的 `Host *` 块如果排在前面，它的 `Port`/`User` 会**赢过**我们
   这一份，而症状是「配置看着完全正确但连不上」。**实测确认过这一点。**
3. **写的路径一律是绝对路径。** `~` 在 `Include` 里是按 `$HOME` 展开的（实测），
   而 `$HOME` 在极少数场合不等于用户的家目录。家目录真的搬走时那条 `Include` 会
   悬空 —— 实测确认**悬空的 `Include` 不是致命错误**，ssh 会忽略它继续读后面的
   内容，所以用户其余的 ssh 完全不受影响，重开一次会话即可自愈。

`Include` 加不上时**照样**把我们自己那份配置写好（用户可以手工加那一行，也可以
`ssh -F <路径>`），但**必须说出来** —— 不说的话他敲 `ssh slurmate` 只会得到
`Could not resolve hostname`，而根因是我们没能改他的文件。

## 作业侧（`job/start.sh`）

### 三个钩子都用上了

| 钩子 | 干什么 |
|---|---|
| `precheck_sshd` | 查公钥形态 + 查私有临时目录。**非 0 → 宿主写墓碑并以 24 结束，不会开始挑端口** |
| `start_sshd` | 生成/复用主机密钥、写 config 与 authorized_keys、起 sshd、嗅探版本行 |
| `cleanup_sshd` | 把 sshd 自己的日志并进作业日志（在宿主的最后一行之后、NFS 补写之前） |

外加一个 `PLUGIN_SESSION_FIELDS[ssh_host_key]`：主机公钥通过**宿主**写进会话文件。

★ `ssh_host_key` 这个**键名是跨语言契约**：守护进程按 `SESSION_FILE_FIELDS`
白名单读它，客户端的 `sshconfig.js` 把它写进 `known_hosts`。改名字要三处一起改，
而漏掉守护进程那一处的症状是**字段凭空消失、谁都不报错**。
`cluster/test-sessiond-logic.py` 第 20 节钉着这条。

### 主机密钥：`ln` 而不是 `mv`

`$HOME/.slurmate/ssh/host_ed25519` 在**共享家目录**里。★ 注意这个 `$HOME` 是**作业
进程的**（集群账号那个 NFS 家目录），与客户端那一侧的三个文件**不是同一个目录** ——
上面说的搬家搬的是客户端的，而这一份**留在原地**（`ctx.dataDir()` 管不到另一台机器
上的家目录，也不该管；两侧只通过会话文件里的 `ssh_host_key` 交汇）。

客户端把它钉死在固定的 `UserKnownHostsFile` 里。换了主机密钥，ssh 会判定为
**中间人攻击** —— 用户看到的是「昨天还能用，今天连不上」。

两个作业同时首次启动时，它们竞争同一个路径：

- `mv`（rename）的败者是**静默覆盖** —— 已经连上的客户端下次连接就会看到新主机
  密钥，也就是那个中间人告警，而密钥在客户端眼里变来变去；
- `ln` 的败者拿到 `EEXIST`，**先到者胜出**，密钥一旦落定不可变、且内容从诞生那
  一刻起就是完整的。（`>` 配 noclobber 做不到这一点：它只能创建空文件。）

★ **绝不能用 `mkdir` 当锁**：作业随时可能被 `scancel`，锁会永久残留，之后
**所有**作业都再也起不来 sshd。

★ 只持久化**私钥**，`.pub` 用 `ssh-keygen -y` 现推。存两份就多一处"两份数据不
一致"的可能，而那个症状在客户端看来是"主机密钥不匹配"，根因却埋在计算节点的
日志里。

### 就绪判定：嗅探 SSH 版本行

```
连上 <NODE_IP>:<port>，读第一行，等它匹配 SSH-2.0-* → 就绪（最多 20 秒）
```

**为什么不判"端口在监听"**：那不能证明回话的是 SSH（可能是同节点别的进程抢到了
端口）。**为什么不看日志里的 `Server listening on ...`**：`ListenAddress` 写错
它照样这么说，而客户端连不上。嗅探是**端到端**的判据。

★ 用 `read -t 2`，不用 `head -c N <&3`：后者收不到 EOF 时会**挂满
`LoginGraceTime`（默认 120 秒）**，作业看起来就是卡住了。读完立刻关掉 fd，否则
sshd 要干等到 `LoginGraceTime`。

### `-D` 是必需的，不是风格问题

不加 `-D`，sshd 会 `daemon(1,0)` —— fork + setsid，**父进程立刻退出**：

- `$!` 当场变成一个死 pid；
- `wait` 立即返回 → 作业在服务起来的**同一秒**就结束；
- 心跳的存活门 `kill -0` 也失败 → 心跳根本不会写。

### `sshd_config` 里几项的由来

用 `-f` 指定配置后 sshd **不再读** `/etc/ssh/sshd_config`（含 `.d`）。这是刻意的：
站点级配置里任何一个非默认项都会让这个用户态实例的行为变得不可预测，而它必须与
作业里这一份严格一致。

| 项 | 值 | 为什么 |
|---|---|---|
| `ListenAddress` | `$NODE_IP` | 默认是 `0.0.0.0` + `::`，那会把端口挂到计算节点的**所有**接口上 —— 而 nft ACL 挂在登录节点的 output 链，管不到"从外部直连计算节点"那条路径 |
| `UsePAM` | `no` | 非 root 的 sshd 用不了（`pam_loginuid` / `pam_systemd` 要写 `/proc` 与 `/run`），而且我们也不想要它 |
| `PasswordAuthentication` | `no` | 关掉 PAM 之后口令只剩"读 `/etc/shadow`"一条路，而那是 root 的权限。**显式关掉，而不是依赖"它恰好读不到"** |
| `AuthenticationMethods` | `publickey` | 白名单式收口：即使上面某项将来被改回默认，认证方式也不会变宽 |
| `PermitUserEnvironment` | `no` | 默认 `no`，但它是**危险默认值**里最隐蔽的一个：开了它，`~/.ssh/environment` 能把 `LD_PRELOAD` 注入会话 |
| `AllowAgentForwarding` | `no` | 默认 `yes`。agent 在客户端，不该被转发到共享的计算节点 |
| `X11Forwarding` | `no` | 默认 `yes`：会去起 `xauth`、开一个监听端口 |
| `GatewayPorts` | `no` | **必须显式关掉**：一旦是 `yes`，`-R` 转发会绑到非回环地址，而那条**入向**路径不经过登录节点的 nft ACL —— 等于在计算节点上开了一个谁都能连的端口 |
| `AllowTcpForwarding` | `yes` | VS Code Remote-SSH 的端口转发走 `direct-tcpip`，关了它直接连不上 |
| `LoginGraceTime` | `20` | 默认 120 秒：未认证连接会一直占着槽位 |
| `StrictModes` | `no` | ★ **唯一一个"关掉更安全"的项**。它会检查 `authorized_keys` **整条路径**上每一级的权限，而我们在 `/tmp` 下（`1777`）—— 它会因此拒绝登录，**报在服务端日志里，客户端只看到一句"认证失败"**。而它在这里没有保护对象：文件是我们自己用 umask 077 建在 0700 私有目录里的，同节点其他用户既不能预创建这个路径、也不能往里写 |
| `PidFile` | `none` | 非 root 写不了 `/run/sshd.pid`，而 `-D` 前台运行也不需要 pid 文件 |
| `Subsystem sftp` | `internal-sftp` | Remote-SSH 会用到 sftp；`internal-sftp` 不依赖发行版各异的 `sftp-server` 路径 |

### 公钥形态检查是安全关键

只接受 `^ssh-ed25519 [A-Za-z0-9+/]{68}$` —— **一行、以算法名开头、后面只有
base64**。

`authorized_keys` 的语法允许**选项前缀**（`command=`、`environment=`、
`cert-authority`…）和任意多行。所以这个正则一次性排除掉：

- 追加第二条（别人的）公钥；
- 注入 `authorized_keys` 选项（例如把一整把 CA 拉进来）；
- **逗号** —— 它会破坏 `sbatch` 的 `--export` 逗号分隔，把一个环境变量变成两个。

ed25519 的 blob 恒为 51 字节 → base64 恒为 68 字符且无填充，所以长度可以卡死。
客户端只生成 ed25519，不会误伤。

★ 守护进程提交时有**同款**的一道，这是第二道。**两道都要有**：守护进程那道挡的
是正常路径，这道挡的是手工 `sbatch`、以及两端版本不一致时的老作业。

★ 正则放进**变量**，不直接写进 `[[ x =~ ... ]]`：那个空格会被 bash 当成**词分隔
符**，于是条件表达式被劈成两半、报 `syntax error in conditional expression`。

## 计算节点上需要什么

| 命令 | 用在哪 | 缺了会怎样 |
|---|---|---|
| `sshd` | `start_sshd` | 明确报错（`$bin 不存在或不可执行`）→ 每个候选端口都失败 → `exit 22` |
| `ssh-keygen` | 生成/复用主机密钥 | 明确报错。**首代会失败**；已生成过主机密钥的用户不受影响 |

`sshd` 与 `ssh-keygen` 都来自 `openssh-server` / `openssh-client`，绝大多数集群上
都有。作业通用地还需要 `mktemp` —— `precheck_sshd` 会显式检查私有临时目录存不
存在，不存在就**明确失败**，而不是退到某个可预测的路径上。
