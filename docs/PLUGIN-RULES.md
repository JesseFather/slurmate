# 插件的基调

这份文件里的每一条，都是**不可推翻、无视升级**的。改它不等于改一个功能 ——
等于换一个产品。

**可以演进的东西不在这里** —— 见〈不属于基调的〉。列那一节是为了让"基调"这个词
有边界：一份什么都是基调的清单，等于没有基调。

---

## 怎么读这份文件

> **一条基调 = 一个性质 + 一条「改坏了它就会红」的用例。**

这条元规则不是洁癖。一份没有用例的规则会退化成一句谁都不看的愿望，而
**"文件里写着、实际什么也没发生"**正是这个项目一路在清的那一类问题。
**挂不上用例的，不进这份文件** —— 它降级成设计说明，写在各处的注释里。

现状标记：

| 标记 | 意思 |
|---|---|
| **已是** | 今天的代码就是这样，用例已经在跑 |
| **部分** | 有，但缺一块；缺的那块写在下面 |
| **待做** | 定了，还没做；用例还没写 |

★ **只有「已是」的那些，今天可以被读成对现实的描述。** 其余各条是对**契约**的
描述，不是对现状的描述。这句话要一直留着，直到每一行都变成「已是」。

## 甲 · 身份

### 甲1 · 一个插件 = 一个 id，铸一次，永不改变

`id` 是一个 ULID（见 `client/src/main/plugins/ulid.js`），在插件**诞生时铸一次**，
此后永不改变。**只有打包器铸 id**；客户端与守护进程**只读**。

- **为什么**：id 是「会在用户工作站上跑的那段代码」的身份，而同意台账按
  `id@版本` 记。允许第二个地方铸 id，就等于允许同一个插件有两个身份 ——
  而"一份内容、多份引用"整条规则，是建立在"同一个 id 就是同一个构件"上的。
- **用例**：生产代码里不存在铸 id 的调用点；打包器在缺 id 时**拒绝出包**。
- **现状**：**待做**。★ 打包器还不存在；而且 `ulid.mint` 今天在**整个生产代码里
  没有任何调用点**（只有测试在用）—— id 必须已经躺在 `plugin.json` 里，否则
  `inspectDir` 直接拒绝。所以本条今天是**空真**，不是"已实现"。

### 甲2 · id 是标识，不是名字

名字（短名 `name`、`displayName`）随时可改；短名只需**站点内唯一**；两者
**都不参与任何判定**。目录名同样不参与。

- **为什么**：同一个插件被两个站点分发时能被认出来是同一个，靠的是 id 相同；
  两个站点各写一个同名插件时能被分开，靠的是 id 不同。**名字做不到这两件事**。
- **用例**：改 `displayName` ⇒ 摘要变而 id 不变；两个站点各有同名插件 ⇒ 两个 id
  并存，各自标明来源。
- **现状**：**已是**（`inspectDir` 分别校验 `id` 与 `name`；`findPluginDirs` 里
  两层的目录名都不参与判定）。

### 甲3 · 一个 `(id, 版本)` 只能有一份内容

内容不可变。**改了内容就必须升版本号**；同一个 `(id, 版本)` 出现两份不同内容时，
**两个都不加载并报错** —— 绝不挑一个。

- **为什么**：池模型唯一的危险处就在这里。取错的那一方会**静默地跑另一个插件的
  代码**，而用户完全看不出来。宁可让这个插件暂时不可用 —— 那种失败是**看得见**的
  （会话变成"未知服务"，仍然接得上隧道、停得掉）。
- **用例**：同键不同摘要 ⇒ 两个都不加载（`Registry.reload`）；安装器与分发换入
  都**拒绝**覆盖内容不同的同版本。
- **现状**：**已是**。

### 甲4 · 身份 = 内容的规范摘要

用来判"是不是同一份构件"的那个值，**是内容的函数**：不看容器的字节、不看包装、
不看任何作者写的字段。（`description` 这类字段进摘要，只是因为它们躺在
`plugin.json` 这个文件里 —— 不是因为它们是"描述"。）

- **为什么**：如果这个值跟打包器有关（信封格式、时间戳、压缩参数），"同一份内容"
  就会算出两个身份，而 `(id, 版本)` 只有一个槽位 —— 按甲3，两个都不加载。于是
  甲2 要保的那件事（同一个插件被两个站点分发 ⇒ 识别为同一个）会变成一件坏事。
- **用例**：同一棵树、两个不同的信封 ⇒ 摘要**相同**。
- **现状**：**部分**。今天 `digestOf` 确实是内容的函数 ✓；缺的那一半是**"摘要的
  计算不依赖树的种类"** —— 见 乙2′。今天它还要处理符号链接、权限位、空目录、
  遍历顺序四件事。

### 甲5 · 分支 = 新 id

一份 fork 出来的插件**必须铸一个新 id**。判据是**机械的**：包里带的签名者与本机
台账里这个 id 的签名者不同 ⇒ **拒绝**。

- **为什么**：fork 沿用 id 会让两个不同的东西抢同一个 `(id, 版本)`（甲3），后果是
  **一个站点的 fork 能把另一个站点正在用的插件弄坏** —— 这是"会给插件起个名就能
  发动"的跨站拒绝服务。
- ★ 这也是**签名被做进这一版的理由**。`SECURITY.md` 原来的论证是"在**单站点 +
  站点即作者 + 站点那份由 root 装**这三个前提下，签名不降低安全性"；而
  **"作者换了"不在这三个前提的射程内** —— 它问的是同一个身份下面作者换人没有，
  这件事**只有签名能判**。摘要（一致性）判不了：fork 升个版本号，在台账上就是
  一条全新的正常条目，用户看到的是一次普通的"要不要装新版本"。
- **用例**：同一个 id 用两把钥匙签 ⇒ 客户端**拒绝**后一个，并点出两个指纹。
- **现状**：**待做**（签名未做）。

### 甲6 · 分支判定必须本地可判

打包器判断"这是不是一份分支"**不能依赖作者读过文档** —— 判据必须本地算得出来。

- **为什么**：文档拦不住没读文档的人。而**台账放进源码树并提交**之后，clone 下来
  的树带着台账 —— "这个 id 是谁签的"本地就有答案，**手滑的情形全部机械可判**。
- ★ 剩下唯一无法机械判的是**台账被人从树里删掉**。那是故意的，不是手滑 ——
  而故意的那些本来也拦不住（他可以直接手改 `plugin.json` 换一个 id）。
- **用例**：一棵带着 `KA` 台账的树，用 `KB` 打包 ⇒ **拒绝**，不静默换 id。
- **现状**：**待做**。

## 乙 · 包（信封）

### 乙1 · 一个插件是一个包，包里同时有作业侧与客户端侧

插件以**单个文件**（一个包）分发。包里同时含作业侧（`plugin.json` 的 `site` 段、
`job/start.sh`）与客户端侧（`client/index.js`）；**基座按需激活** —— 客户端不读
作业侧，守护进程不读客户端侧。

- **为什么**：作业侧与客户端侧是**配套的**（`PROTOCOL.md` 里"两半是配套的"那一条）。
  分开发就等于让"两半版本不一致"成为可能，而"两边配套"正是分发要解决的问题。
- **用例**：任一侧缺席的包**合法**（一侧可以为空）；两侧都在时都能跑。
- **现状**：**待做**（今天是目录）。

### 乙2′ · 包里只允许普通文件，权限位由格式定死

包里**没有目录条目**（目录结构由路径里的斜杠表达），**没有符号链接**，
**没有空目录**，**没有命名管道 / 设备节点**；所有文件的权限位由格式规定
（今天全部 `0644`）。

- **为什么**：这是**摘要退化成一句话**（甲4）的前提。今天 `readPluginFiles` 要处理
  四件事，每一件都是一次"摘要相同而内容不同"的机会：

  1. **符号链接 vs 普通文件** —— `client/x.js` 是指向 `../y.js` 的链接，与它是
     "内容恰好为 `../y.js` 的普通文件"，两者行为天差地别（一个加载 `y.js`，
     一个导出一个字符串），而摘要可以完全相同；
  2. **权限位** —— `0644` 与 `0755` 内容相同；不入哈希的话"摘要相同 ⇒ 树相同"是假的；
  3. **空目录** —— 只差一个空目录的两棵树，不入哈希就摘要相同，而安装器的
     `copyTree` 会把空目录建出来，两边对不上；
  4. **顺序** —— `readdir` 的顺序在两个文件系统上可能不同，不排序则同一棵树在
     两台机器上算出不同摘要。

  格式不允许这四种东西之后，摘要只剩

  ```
  sha256( 按路径排序，逐份：路径 \0 sha256(文件内容) \n )
  ```

  —— **两种语言各写一遍会逐字一致**，不需要谁复现谁。

- ★ **可执行位不需要。** `job/start.sh` 在集群侧是被 `cat` 进 sbatch 的
  （`cluster/deploy.sh`），**它的权限位不参与任何事**；`client/index.js` 是被
  `require()` 的，也不需要。而且 git 本来就只记一个可执行位，所以"从 commit
  打包"（乙3）天然满足本条。
- ★ **要放宽的正确方式是"在清单里声明"**（例如 `plugin.json` 里写"这个路径要
  `0755`"），**不是把权限位还给文件系统** —— 因为清单是一份文件、在负载里，
  所以"需要可执行"仍然是内容的一部分，仍然进摘要。
- **用例**：带符号链接 / 空目录 / `0755` / 命名管道的包 ⇒ **拒绝**。
- **现状**：**待做**。

### 乙3 · 打包的输入是一个 commit，不是工作树

打包器**拒绝在脏工作树上工作**；输入必须是一个 commit。

- **为什么**："同一份源码"需要一个精确的定义，否则工作树里多一个编辑器临时文件
  就是"两个结果"—— 而那是打包器再确定也救不了的。从 commit 打包时，可复现性是
  **git 保证的**：`git archive` 对同一个 tree 的输出是确定的（uid/gid 写 `0`、
  mtime 取 commit 时间），不是我们写规格去守的。
- **用例**：脏工作树下打包 ⇒ **拒绝**；同一个 commit 打两次 ⇒ 字节相同。
- **现状**：**待做**。

### 乙4 · 信封里的负载，逐字节等于源码树里那棵树

- **为什么**：这一条就是「**不混淆、不加密、没有隐藏字节**」那句话的判据形式。
  那句话本身钉不住，这条钉得住 —— 任何混淆、加密、藏字节都会让这条红。
- ★ 而这个性质是**结构性**的，不是锦上添花：`SECURITY.md` 的"无签名"论证，前提
  之一是"站点那份插件树由 root 从源码装"，而 `deploy.sh` 的信任门
  （`plugin_src_files` + `source_is_trusted`）存在的唯一理由就是**有人能看**。
  更要紧的是：**同意闸是这一版唯一的安全边界**（进程隔离未做），代码一混淆，
  用户就没法有意义地同意 —— 含糊的"是否信任此插件"会让用户以为自己在同意 A
  而实际同意了 B，那正是 `SECURITY.md` 自己写着要防的事。
- **用例**：解包仓库里的插件 ⇒ 与源码**逐字节相同**。
- **现状**：**待做**。

### 乙5 · 签名覆盖内容摘要，不覆盖信封字节

- **为什么**：信封的格式会演进（今天加签名槽，明天加别的）。签名盖在字节上，
  每动一次信封所有签名全废，而且"同一份内容两个包"要两个签名。
- **用例**：信封加一个字段 ⇒ 老签名**仍然有效**。
- **现状**：**待做**。

### 乙6 · 一个插件一把钥匙；丢钥匙只能 fork 你自己

私钥属于**这个插件**，不属于这台机器（换机器 ⇒ 复制私钥）。**丢了钥匙 ⇒ 只能给
这个插件铸一个新 id**，所有已同意的客户端重新问一遍。

- **为什么**：钥匙就是"血统"的载体，丢了就是血统断了 —— 这是**诚实的结果**，
  不是需要兜掉的失败。★ 而正因为这个后果明确、不致命，**密钥管理从"绝不能出错"
  降级成"最好别出错"** —— 这是签名方案能够落地的原因。
- **用例**：用另一把钥匙签同一个 id ⇒ **拒绝**，并点出两个指纹。
- **现状**：**待做**。★「私钥要备份」要写进作者文档 —— 它是本条唯一的可操作建议。

### 乙7 · 版本号规范

`major.minor.patch` 三段十进制：

1. **不许前导零**；
2. `minor` 与 `patch` ∈ `0..255`，**满则进位到上一位**；`major` 无上限；
3. **比较方式**：逐段按十进制字符串比 —— **先比长度，再比字典序**。

- **为什么**：

  - 前导零会造出**同一个版本的两个字符串**（`1.007.0` 与 `1.7.0` 数值相等、
    字符串不等），而两侧查表都是**精确字符串比对**（守护进程的 `_plugin_by_key`
    就是 `c.spec.version == version`）⇒ 两个槽位、两次同意、两份目录；而"升版本号"
    用 `cmpVer` 比会判成"没升"；
  - 比较**不能转成数字**：JS 的 `Number` 在 2^53 以上失精 ⇒
    `9007199254740993.0.0` 与 `…992.0.0` 判等，而 Python 的 `int` 是任意精度
    ⇒ **两侧不一致**。按字符串比与数值序完全一致，且不依赖任何整数精度 ——
    这样第 2 条里那个"`major` 无上限"才是真的无上限；
  - `0..255` 的价值是**挡住把日期或提交号塞进版本号**（`1.0.20260916` 今天合法）。
    而版本号是**甲3 的唯一执行手段**：它要是能随手造新值，"改了内容就升版本号"
    就退化成"改了内容就换个号"。

- **用例**：打包器与两侧清单校验器**都拒绝** `1.256.0` 与 `1.007.0`；比较函数对
  `9007199254740993.0.0` 判得出大小。
- **现状**：**待做**。规则要改**三处**：客户端 `VERSION_RE`、守护进程
  `PLUGIN_VERSION_RE`、打包器 —— 三处必须一致，建议纳入
  `.github/workflows/checks.yml` 已有的那条跨语言常量 lint。

## 丙 · 客户端

### 丙1 · 池子唯一的写入者是安装流程

插件进池**只有一条路：安装一个包**。往池目录里手放一份，**不是一条路** ——
不是"一条被拦住的路"。

- **为什么**：只要"往文件夹里拷"还能工作，池子里的东西就与台账可能不同步，而台账
  是同意、回收、会话解析三件事的**共同依据**。让它**不成立**，比拦着它便宜。
- **用例**：往池里放一份合法的树 ⇒ 它**不出现在插件列表里**、也不加载。
- **现状**：**部分**。今天手放一份进去**不会被执行**（摘要不在台账里 ⇒ `allows`
  为假），会以"没有任何站点要它"出现在界面上，并会在下一次对账被回收。缺的两块：
  ① 插件卡片上那句「点一下同意就能用它」对它是**死胡同**（`app:consentPlugin`
  只在 `pendingConsent` 里找，回一句"没有这个待同意的插件"）；
  ② "站点发下来的"与"不知道是谁放进来的"在界面上**长得一样**。

### 丙2 · 同意闸按内容摘要记，每次都问，没有例外

带客户端代码的插件第一次要用户点一次同意；台账（`cfg.trustedPlugins`）按
`<id>@<版本>` 记，值是**全长摘要**（截断只留给显示）。**不给"纯声明式插件免同意"
开口子。**

- **为什么**：① 一个恶意的 `plugin.json` 也在往这台机器上放东西（`contributes.login`
  能让客户端往一个 URL POST 一个口令 —— 那是**数据**不是代码，但仍然是站点的指令）；
  ② **规则一有分支，绕过它的路就会长出来**。
- **用例**：纯声明式插件也走闸；`allows` 对**每一个**目录都问，没有例外。
- **现状**：**已是**。

### 丙3 · 一致性判据 ≠ 认证判据

**摘要**回答"还是不是我同意的那一份"（一致性）；**签名**回答"是不是我以为的那个人"
（认证）。两者**不合并**。

- **为什么**：合并会得到一个看起来更强的检查，而它挡不住"第一次给的就是坏的"——
  摘要跟内容同行、由同一个工具写下，它挡得住事后偷换，挡不住首次欺骗。
- **用例**：内容**没变**、签名者**变了** ⇒ **拒绝**。（两者一合并，这条就会绿。）
- **现状**：**部分**。今天的 TOFU 台账是**一致性**那一半（`config.isTrusted`）；
  认证那一半（签名）未做。

### 丙4 · 删除本机那一份 = 撤回同意

删掉池里的一份 ⇒ 台账里那条**一并消失** ⇒ 下一次对账**重新走一遍同意闸**。
并且**不断言"是你删的"** —— 客户端不知道，它只知道"不在了"（可能是你删的，
可能是清理工具，可能是磁盘坏了，也可能压根没装上）。

- **为什么**：删除是一个**没说出口**的决定，而对账不认识它。若只删目录、台账那条
  还在，下次同步会按"摘要与台账相符"**静默装回来，一个字都不问** —— 那不是
  "当作从来没有过"，那是"用户想让它消失，它自己回来了"。
- **用例**：删掉目录 ⇒ 台账那条消失 ⇒ 下次重新问。
- **现状**：**待做**（今天的行为恰好相反：静默装回来）。

## 丁 · 分发

**丁1 – 丁3 不在这里重述** —— 它们已经写在 `client/src/main/site-plugins.js` 的
文件头。**重述会漂**：同一件事写两遍，两遍迟早不一样，而那时没人知道哪一遍是真的。
这一节只把它们**登记为基调**：

- **丁1 · 绝不谎报成功** —— 任何一份文件没到手或对不上，这一次分发就报失败；
  而报成功的时候，磁盘上的内容**按字节**就是站点那一份。
- **丁2 · 判据是能力缺席，不是这次失败** —— "站点不支持分发"只看 `plugins` 里
  有没有文件清单。拿"这次下载失败了"当判据，等于给一个能让下载失败的人（断流、
  丢包、中间人）一个把用户降级到旧本地副本的开关。
- **丁3 · 不知道谁在引用时，什么都不删** —— 记录读不出来 ⇒ 只报告，不回收。

★ 三条的**现状都是「已是」**。

### 丁4 · 在有权威的那一侧执行

**同一个站点里，不许两个插件自报同一个 id** ⇒ `deploy.sh` **拒绝部署**。

- **为什么**：作业脚本按 `<id>.sbatch` 命名（一个插件一份），两个插件同 id ⇒
  **后织的覆盖先织的** —— 而那是**静默**的（账本里记作 **F21**）。`deploy.sh`
  手里已经逐个插件读出了 id 并断言了形状，检查就落在它那儿；而且它**在发货之前**、
  在**有权威的那一侧**，比让每个客户端去兜好得多。
- ★ 它拦不住**跨站**的那一种（fork 在 T 站、原件在 S 站）—— 那一种归 甲5 的签名管。
- **用例**：两个目录自报同一个 id ⇒ 部署中止，说清是哪两个目录、内容摘要各是什么。
- **现状**：**待做**。

## 不属于基调的

下面这些**可以演进**，改它们不动基调：

- 各种上限：单文件 256 KiB、整包上限、`max_files`、路径深度
- 暂存目录的布局与命名、对账锁的实现、退避重试的次数
- `limits` 的字段名、`plugin_file` 这个 op 名、错误 kind 的取名
- `id` 用 ULID 这个具体编码（换成别的东西，只要是"铸一次"就可以）
- 包的容器格式（tar / zip / 自造）—— 只要满足 乙2′ 与 乙4
- 打包器放在哪个目录、用什么语言写、`--fork` 这个选项叫什么
- 引用计数与 `.sites.json` 的具体形状

## 怎么改一条基调

**不能"顺手改"。** 要改，得**先证明它那条用例是错的** —— 而不是先改代码、再改用例。

★ 一条基调的用例被改成永远绿，就是它被废掉的时刻，而那时候**没有人会注意到**。
所以这份文件唯一需要的维护纪律是：

> **用例红了，先假设是代码错了。**
