# 已知问题

这份文件是**账本**：记下当前代码里确实存在、但**还没修**的东西。

它存在的理由很直接 —— 这个项目一路在清的是同一类问题：**系统报告成功，而事情
没成**。而这类问题有一个共同的坏性质：**它们的证据只存在于发现它们的那一次对话里**。
代码本身看不出「这里少了一道确认」，测试也测不出来（没写的东西不会红）。所以必须
有一个地方把它写下来，否则下一个人（包括半年后的自己）会重新踩一遍。

一条离开这份文件的唯一方式是：**修掉它，并附上一条能真的红的用例**。删掉一行而
没有对应用例，等于把它降级成"没有人知道它存在"。

★ **编号（`F12` 之类）是稳定标识，不要改。** 源码注释里按编号引用它们
（`client/src/main/session.js` 等）—— 改编号会让那些引用指空。

## 一、已核实的缺陷

代码就在那儿，读一遍就能确认。

### F12 — `goodbye` 返回 `ok:true` 不代表作业被取消了

**位置**：`cluster/slurmate-sessiond` 的 `op_goodbye` —— 那一行是
`self.slurm.cancel(s["job_id"], "goodbye")`。

`Slurm.cancel()` 在 `scancel` 失败时**返回 `False` 并只记一条 warning**，
而 `op_goodbye` **不看这个返回值**，照样 `begin_release()` 然后回 `ok:true`。

**后果**：客户端和用户都以为会话结束了，而作业可能还在跑。

**修法**：`cancel()` 失败时不要静默 —— 要么回 `ok:false`，要么在响应里带一个
`warning` 字段（协议里已经有 `warning` 的先例，见 `op_submit` 对内存参数的处置）。

### F13 — `phase_release` 从不确认作业真的停了

**位置**：`cluster/slurmate-sessiond` 的 `phase_release`。

顺序是：删 ACL → 删口令文件 → 删会话文件 → 置 `released`。**全程没有一次
`scancel`，也没有任何一步确认作业是否还在。**

**后果**（叠加 F12 之后才完整）：

1. 守护进程报告「已释放」，而作业占着节点跑到 `TimeLimit` —— GPU 分区上这是
   **12 小时的实打实算力**；
2. 会话文件被删了，所以**再也没有东西能从作业侧把它找回来**；
3. `released` 不在 `phase_running` 的扫描集合里，**永远不会被回收**。

这条比 F12 严重：F12 是"说了句不准的话"，F13 是"把它从账上划掉"。

**修法**：`releasing` 的会话要重新 `scancel` 并**确认作业真的消失**（`scontrol`
查不到，且不是 `JOB_UNKNOWN`），再置 `released`。注意别把「问不到」当成「不存在」
—— 那正是 `Slurm.job_state()` 三态存在的原因。

### F14 — `max_active_per_user` 拦不住并发的第二个提交

**位置**：`cluster/slurmate-sessiond` 的 `Store.count_active`，以及 `op_submit`
开头那两道配额检查。

`count_active()` 只数 `ACL_STATES`（`enrolled` / `suspect` / `orphaned` /
`releasing`）—— **`submitted` 不在内**。所以在「已提交、尚未登记」这个窗口里，
`max_active_per_user = 1` 那一道**恒为 0**，拦不住第二次提交。

实际生效的上限因此退化成了 `max_pending_per_user = 4`：同一个用户可以
**同时存在 1 个活跃 + 4 个未完成**。

**叠加的事实**：`op_submit` **非幂等** —— 每次调用都生成新 `sid`、插新行、提交新
作业。所以「一次超时重试」就等于「两个作业」。

**客户端已经做了应对**（这部分不要动）：`submit` 超时 ≥45 秒且**绝不重试**，改用
不带 `session_id` 的 `status` 去认领那个"已创建但响应丢了"的会话
（`client/src/main/session.js`）。

**修法（一个产品决定，不是一个纯技术改动）**：两条路，选一条 ——

- **合并**：`count_active + count_pending >= max_active`，删掉 `quota_pending`
  与 `MAX_PENDING_PER_USER`；
- **拆开**：把 `max_pending_per_user` 变成配置键，明确表达"活跃上限"与"并发提交
  上限"是两件事。

选哪条取决于你想要的是「每人一个会话」还是「每人一个会话 + 一个并发提交窗口」。
**在决定之前不要顺手改** —— 改错了的表现是"用户开不了会话"，而根因在一个他觉得
跟自己无关的配额上。

### F15 — 插件清单里没有 `defaultGpus`

`site` 段有 `defaultCpus` / `defaultMem`，**没有 `defaultGpus`**。而
`op_submit` 里 `gpus = clamp_int(req.get("gpus"), 0, 0, MAX_GPUS_REQUEST)`
—— 缺省是 **0**。

**这是一个悬而未决的产品决定，不是疏漏。** 它的前身是 `slurmate.conf` 里
`[purpose:*]` 段的 `gres` 键，那一版**被解析、被推送给客户端、被 `--check` 打印，
但从不参与 `sbatch` 命令构造** —— 是死配置（v0.2 把整节删掉了，见
[CONFIGURATION.md](CONFIGURATION.md) 的「不再是配置项的东西」）。

现在这个问题换了形状活下来：**用户能在高级选项里手填 `gpus`，但没有"这个插件默认
占几张卡"这一层。** 两条路：

- 让插件清单能声明 `defaultGpus` ⇒ 但"开发会话默认占住 A6000 的卡"是稀缺算力
  政策的决定；
- 保持不声明 ⇒ 那就别在任何地方暗示"选某个插件就有卡"。

**不要"顺手修"**：现在改会牵动 GPU 分区的占用策略。

### F16 — 宿主的「候选端口全失败」路径没有用例

`run.sbatch` 的 `pick_port_and_start` 在**每一个**候选端口都失败时的行为（写
`failed` 墓碑 + `exit 22`）在仓库里没有任何一条用例覆盖 —— 第 22 节跑的是
「没有作业侧实现」「零插件」「precheck 没过」这三条路，不包括这一条。

不是缺陷，是**防线上的一个洞**：这条路径正是「计算节点上没装 code-server」时的
表现，而 deploy.sh 的 `bin` 解析在登录节点上做的，**猜不到计算节点**。

## 二、从未实测过的

这些不是"代码有问题"，是**这些事实至今只有推断，没有一次真实输出**。

### U1 — 客户端从没连过真集群

SSH 握手、exec channel、`direct-tcpip` 端口转发 —— 三条都没有一次真实运行。
`client/src/main/backend-ssh.js` 的实现是完整的，但"完整"和"能用"之间隔着这三条。

它们各自依赖一个**前置假设**，任何一条不成立都要换方案：

- 登录节点放行公钥认证；
- `ForceCommand` 守卫放行固定 argv 的命令串；
- `direct-tcpip` 可以转发。

### U2 — `deploy.sh` 整条没有在真机上跑过

`--check` / `--dry-run` / 编织这三条路本机只用**等价方式**验过
（`--check-plugins` 在模拟前缀上真跑、编织用 deploy.sh 里同一段 awk 真跑、
`bash -n` 与三道硬断言真跑）。但整条路需要 root、需要一台控制节点，**至今没跑过**。

**第一次真机部署要重点看的**：

- 编织后的成品是 902 行（479 行模板 + 插件块），`bash -n` 过了没有；
- `<prefix>/share/slurmate/plugins/` 的属主与权限对不对（root 拥有、组/其他不可写）；
- 卸载时插件目录被清干净了没有（卸载读删除标记，删之前先读）。

### U3 — 编织出来的作业脚本从没在真集群上执行过

`test-sessiond-logic.py` 第 22 节是**真执行**，但环境是假的（假 HOME、桩
`scontrol`）。真机上作业会被 Slurm 接管、有 `KillWait` 窗口、有真实的计算节点。

### U4 — sshd 会话的端到端没验过

要部署到控制节点后手工提交一个 `service_kind=sshd` 的会话，从登录节点
`ssh -W` 连一次。今天这个插件的作业侧只有静态检查与桩测试。

### U5 — 界面的真机渲染没验过

插件那一块的改动本机只能做静态检查（语法、纯函数测试）。**画出来对不对要人眼
看一遍**：零插件时那一屏是不是安装指引、站点有本机没有的插件时那句话对不对、
布局组切换之后有没有死页面盖住面板。

### U6 — 线上部署的守护进程比仓库 HEAD 旧

线上那份里 `slurmate submit` **从来没有成功过**：`Config.__init__` 没把
`job_log_subdir` 从配置里取出来，于是每次提交都抛 `AttributeError`，被 dispatch
兜成 `code 9 / internal`。错误信息里没有任何与「日志路径」有关的线索。

**已经修了**（`cluster/slurmate-sessiond` 的 `[slurm]` 段，并已进公开仓库），
但**线上那台要重新部署才会生效**。

★ 重新部署之后，**提交会第一次真正创建 Slurm 作业** —— 这是**行为变化，不是
回归**。在把客户端接上去之前，先用普通用户身份跑一遍：

```
slurmate submit  →  slurmate wait --session <id>  →  nft list chain inet slurmate output
                 →  slurmate goodbye <id>  →  确认规则在两个 tick 内消失
```

（**不能以 root 跑** —— 身份取自 `SO_PEERCRED`，root 跑验的不是同一条路。）

## 三、结构性的欠账

设计上还没做的东西。它们不是缺陷 —— 缺的东西不会假装自己在。

### S1 — 站点分发插件还没有

没有"从集群取插件文件"那个 op。本版做了**安装点**：一个插件目录放进池就生效
（`client/src/main/plugins/install.js`），而将来站点分发走的是**同一个函数** ——
区别只在文件从哪来。

### S2 — 插件跑在主进程里，没有任何隔离

没有签名、没有钉公钥、没有逐插件同意、没有进程隔离。

★ **今天这四条还不是前提**，因为唯一的路是「用户自己放进去的东西」。**一旦有
一条从远端来的路（S1），它们就是前提** —— 那条路会引入一条**反向**的信任路径
（集群管理员 → 用户的工作站）。

### S3 — 插件的测试还住在 `client/test/` 里

插件已经是独立项目了，但它们的客户端侧测试仍然在客户端的测试目录里。一个单独的
项目应该有自己的测试项目 —— 否则"把插件拆出去"这件事只做了一半。

### S4 — `slurmate rpc` 一次一请求

每次调用都是一个完整的 SSH exec channel。稳定态下客户端每 90 秒开 3 个，这对
**单线程**的守护进程是有压力的。根治要给 CLI 加 `--stream`（argv 仍是编译期常量，
所以防注入那条不变量不受影响），尚未实现。

### S5 — 三项检测工作，一项都没做

1. **auth canary（优先，成本最低）** —— 作业里 code-server 起来后自己 `curl` 一次
   **不带 cookie** 的 `GET /`，预期 302 → `/login`；**若是 200 就自杀 + 写审计**。
   防的是：code-server 升级后口令语义变了，作业正常启动、正常能用、**口令却完全
   没生效** —— 那会让 `auth_mode = password` 唯一的价值消失，而正常使用中**永远
   看不出来**。
2. **`doctor` 从健康检查升级为不变量检查** —— 现在只查"进程活没活、表在不在、
   数量对不对"，攻击成功时**全部显示正常**。应改成断言不变量：活跃 claim 集合
   **==** nft 规则集合（双向，不只数量）、每条规则的 comment 能反解出 claim、
   **所有活跃会话的 `auth_mode == password`**、`released` 的 claim 一定没有规则。
   并且必须**定期输出「我检查了 N 项，全部通过」** —— 否则"没有告警"和"检查根本
   没跑"无法区分。
3. **故障注入演练清单（一次性验收）** —— 这些路径正常使用中永远跑不到：
   `systemctl restart nftables`（表要自愈）、`restart slurmate-sessiond`（规则
   收敛）、**停 munge / 重启 slurmctld（会话绝不能被拆）**、`kill -9` 作业、
   断网 60 秒（应进 `suspect` 且**不拆规则**）、手工 `rm` 掉数据库（应从 nft
   comment 反向恢复）、`scancel` 作业、并发跑两次部署（`flock` 挡不挡得住）。

   核心结论：**安全的失效表现为沉默** —— 正常使用 = 所有校验都返回 OK = 与
   "校验代码根本没运行"无法区分。所以解药不是更强的监控，而是**主动扮演攻击者**
   和**写下不变量**。
