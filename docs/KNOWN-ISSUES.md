# 已知问题

这份文件是账本：记下当前代码里确实存在、但还没修的东西。

理由很直接。这个项目一路在清的是同一类问题：系统报告成功，而事情没成。这类问题有
一个共同的坏性质：它们的证据只存在于发现它们的那一次对话里。代码本身看不出"这里少
了一道确认"，测试也测不出来，没写的东西不会红。

所以必须有一个地方把它写下来，否则下一个人（包括半年后的自己）会重新踩一遍。

一条离开这份文件的唯一方式是：修掉它，并附上一条能真的红的用例。删掉一行而没有对应
用例，等于把它降级成"没有人知道它存在"。

**编号（`F12` 之类）是稳定标识，不要改。** 源码注释里按编号引用它们
（`client/src/main/session.js` 等），改编号会让那些引用指空。

## 一、已核实的缺陷

代码就在那儿，读一遍就能确认。

### F23 — 记录文件丢了/坏了之后，站点池里每个版本的引用数都变成 0

`.sites.json` 是唯一记得"哪个站点要哪个版本"的地方。它一旦丢了或读不出来，按引用计数
的规则算下来，池里每一个版本都没有任何站点引用，于是整个站点池会被清空。

那不是"回收了几个旧版本"，那是"因为读不到一张表而删掉用户的文件"。

本版的防线是一条纪律：**读不到记录就不回收，只报。** 集群侧安装器有一条同一个先例：
目录里有东西、却没有本工具的部署标记就中止，不是删。

不知道谁在引用的时候，唯一安全的动作是什么都不删。用例在
`client/test/site-plugins.test.mjs`（"记录丢了不回收"）。

但它仍然记在账上，因为这是一条只能靠纪律维持的边界。下一个人很自然会把"记录不存在"
当成"没有站点要它们"，而那一步没有任何代码在拦。

**修法（本次不做）**：把"这个版本被谁引用"也写进版本目录自己（一份 `.refs`），让引用表
不可能被整体丢失。丢一份只影响那一个版本，而不是全池。

### F24 — `node_modules`：摘要永远不看、而 `require()` 会读

`COPY_SKIP` / `PLUGIN_COPY_SKIP` 把 `node_modules` 排除在插件内容之外，这一条是对的，
分发一份依赖树既慢又没意义。但它同时是一个摘要看不见的位置：`client/index.js` 里一行
`require('some-pkg')` 会去读它，而整套校验（逐文件 sha256、双向声明比对、整目录摘要）
一个字都不覆盖那里。

今天没有实际的隐藏向量。客户端只写包里的记录表列出来的那些文件，而 `copyTree` 也不拷
它。所以池里那棵树里根本不会有 `node_modules`，`require` 会失败并报出来，那是说得出口
的失败。

**记的是将来**：若哪天改成由插件自己声明一份白名单，而不是从包里读那张记录表，这一条
要一起解决。否则"白名单之外的东西不被校验"就从"不存在"变成"存在但没人看"。

包正是那样一份白名单，而它没有让这一条变糟：负载里不可能有 `node_modules`，打包器
不装它、解析器拒绝它，客户端解出来的树里也就没有它，`require` 仍然会说得出口地失败。

要留意的仍然是同一件事：哪天有人把"负载从哪来"改成另一种扫描，这条就活了。

### F30 — `phase_running` 每会话每 tick 一次 `scontrol show job`

**位置**：`cluster/slurmate-sessiond` 的 `phase_running()`，逐个调
`self.slurm.job_state(s["job_id"])`，每个活跃会话每 tick 一次。

**量级（本机实测，slurm-wlm 23.11.4）**：`scontrol show job <id> -o` 是 **7.3 ms**，
`squeue -h -j <id> -o "%i"` 是 6.6 ms；`scontrol show jobs -o` 拿全部 54 条作业要
47 ms / 75 KB，`squeue --json` 拿全部要 196 ms / 448 KB。

一个会话 **30 次/分钟**打控制器。N 个用户同时有会话时是 N 次/tick，而每次都在事件循环
线程里同步 fork。

**今天够不到**：`max_sessions_per_user` 缺省 1，所以本站的会话数与用户数同阶。
这个缺陷的代价是**延迟**（一个 tick 里 N×7.3 ms 的同步阻塞），不是正确性，所以它排在
F 类里靠后的位置。

**不能缓存**：每个 job_id 都是不同的对象，没有"同一份答案服务所有连接"可言。快照
那一侧的放大已经由 `tick_job()` 的记忆化挡住了（见 26.14）。

所以唯一的路是**批量**，而两个批量方案都实测过、都不成立：

- `squeue --json -j a,b,c`：23.11.4 上静默无视 `-j` 的过滤，把全集群的作业都吐出来
  （54 条 / 448 KB / 196 ms），`rc=0`、无任何提示。那是一个静默的错误答案：看上去拿到
  的是三个作业的状态，实际是全部。过滤得自己做，而过滤写错的方向是把别人的作业状态
  当成自己的（见 F31）。文本形式 `squeue -j a,b` **是**正确过滤的。
- `scontrol show jobs -o`（复数）：47 ms 拿到全部作业，字段一个不少，与单条查询同一套
  键。代价随**别人**的作业量无界增长，而它跑在保活 ACL 的那个 tick 里，一个几万
  作业的集群上，别人的排队长度会拖慢甚至拖垮本站的对账。

**判据**：一个随站点自己能控制的量（会话数，有 `max_sessions_per_user` 兜着）有界的
代价，胜过随谁也控制不了的量（全集群作业数）无界的代价。

还有一条更硬的：用全量倾倒来判"我的作业还在不在"，是拿"它不在那一大坨里"推断"它没
了"。那比"`scontrol show job <我的 id>` 失败"弱得多，而那条推断落在 `job_is_terminal`
那条路上，是判错一次就不可逆的地方（见 F25）。

**什么时候值得重做**：本站的并发会话数上了两位数，或者 `squeue --json -j` 的过滤在
目标 Slurm 版本上被修好。第一件事是量：`scontrol show jobs -o` 在本站真实作业量下的
字节数与耗时，以及它随作业数怎么长。

### F31 — `squeue --json` 与 `-j` 同时用时**静默返回全集群**

**位置**：不是本项目的代码，是 Slurm 23.11.4 的行为。记在这里是因为它骗过一次。

```
$ squeue --json -j 5709            -> 1 个作业   ✓
$ squeue --json -j 5709,5746       -> 54 个作业  ✗（全集群）
$ squeue -h -j 5709,5746 -o "%i"   -> 2 个作业   ✓（文本形式正确）
```

`rc=0`，stderr 空，没有任何提示。同一个 `-j` 参数，文本形式过滤，`--json` 形式只认
单个 id。

它之所以值得记：本文件里好几处都在说"三态"与"静默的错误答案"，而这一个来自外部工具。
它落在一条看起来很合理的优化上（"一次查询拿全部作业的状态"），而写错了不会红任何
东西，直到有人发现某个作业的状态报告得莫名其妙。

**教训**（写在这里给下一个人）：把一条外部命令的输出形状当成契约之前，先量一次它在
参数边界上的行为。「文档说 `-j` 接受逗号分隔的列表」与「这个版本在这个子命令上真的
这么做了」是两件事。

### F40 — `sbatch` 返回 job_id 之后、写进库之前进程死掉，那个作业没有任何记录

**位置**：`op_submit()`（`cluster/slurmate-sessiond`）里紧挨着的两行：

```python
job_id, why = self.slurm.submit(...)          # ← 作业从这一刻起已经在集群里了
if job_id is None: ...                        #    而库里那一行还是 reserved / job_id=NULL
self.store.update(sid, job_id=job_id, state=ST_SUBMITTED, submitted_at=now_ts())
```

**机理**：`slurm.submit()` 一旦返回一个数字，作业就真的存在了。而从那一刻到
`store.update()` 落盘之间，库里那一行仍然是 `reserved` 且 `job_id` 为 NULL。这段窗口
里守护进程被杀（systemd 重启、OOM、节点重启），那个 job id 就丢了。

**后果**：`phase_pending()` 在 `reserved_ttl`（600 秒）之后把那一行判成 `expired`，
而它取消不了作业，它手上没有 job id。

- 那个作业继续占着节点跑到 `TimeLimit`。`MAX_TIME` 允许到 7 天，GPU 分区上那是
  实打实的算力。
- 它在节点上起着服务、也写了一份会话文件到用户家目录，但守护进程永远不会去登记它：
  `try_enroll()` 只对库里 `submitted` 的行跑，而那一行是 `reserved`。
- 一个字的日志都没有。`expired` 那条审计说的是 `reserved_ttl`，看起来与"提交中途被
  打断"毫无关系。

**为什么与 F32 是两条**：F32 那两条路手里有 job id，所以修法是"过同一道闸、确认作业
停了再拆"。这一条根本没有 job id，闸修不了它，因为闸要问的那个问题（"那个作业停了
没有"）在这里无从问起。

**修法（本次不做）**：没有便宜的答案，因为信息在崩溃的那一刻就不在库里了。候选是
"过期时反查一次"：拿 `SLURMATE_SESSION_ID` 去这个用户当前的作业里找。`squeue` 过滤
不了环境变量，得 `scontrol show job` 逐个看 `Environment`。只有在 `reserved` 超期
这种极少见的情况下才跑一次，代价可以接受。

但它是一个产品决定：要不要为了这个窗口让守护进程去翻别人的作业环境。这不在这一版的
范围里。

**为什么记在这一版的账上**：它是 F27 / F32 那一族的第三条，"一条作业再也没人回收"。

**0.24 收窄，未结清。** `slurmate service restart`（安装器、修复、日常运维都走它）
在重启之前先发 `drain`：窗口内的新提交被拒，而 `dispatch` 是同步的，应答 drain 时
没有在途 op —— 于是"重启恰好落在提交中途"这一段被关掉了。直接 `systemctl restart`、
OOM 与节点重启仍然有这一段，上面的修法（过期时反查）仍然欠着。
核 F32 的时候顺手撞见的，与那两条不同源、不同修法。

### F52 — 只有客户端那一半的插件，界面上是一条死路（待拍板）

用户 2026-10-16 在插件那一屏上看到一块「笔记本服务」，写着「本站装了它，但它没有作业侧
实现，提交不了」，「开始会话」灰着。他的原话是"虽然没用作业侧实现，但也应该可以启动，
或者某种方式打开，因为按理来说，这确实是一个单机插件，也不需要作业侧实现，但不能一刀
切掉不让启动"。

**核过的事实**：`op_plugins` 那一项的 `can_submit`，是"站点开着它"与"这个包的负载里有
`job/start.sh`"的合取。没有作业侧是**合法状态**，包装得上、看得见，而提交时回
`code 4 / service_kind_no_job`。在这个架构里会话就是作业：没有作业侧，就没有可跑的
东西、没有端口、没有隧道、没有界面。所以界面把按钮置灰并给出一句话，与服务端的事实是
一致的，不是一刀切。

**还悬着的那一半**：这句判断对不对是产品语义，不是实现。守护进程的注释说它合法，而协议
文档那条错误表把它写成"部署不完整"，两处口径不同。用户另外指出这个例子本身不合理：
笔记本是个人用的东西，站点不会分发它（探针夹具里那一块已经换掉了）。

**所以这要你拍板**：①维持现状（这类插件不可启动，措辞按"合法状态"改，不再说部署不完整）；
②给它一条别的出路（那要先说清"打开"到底打开的是什么 —— 没有作业侧就没有进程）；③把
"没有作业侧"从合法状态改成不合法（部署脚本在 `deploy.sh` 那一层就拒）。三条的代价不同，
选之前先定这一条。

## 二、没有完整实测过的

2026-10-17/18 在一台真实站点上把主流程走了一遍（提交、隧道、界面、释放、站点分发

### U1 — 客户端那一跳：端口转发也验过了；常驻通道与两台电脑的接管没有

**已经有一次真实输出的**（2026-10-17，一台真的 Slurm 集群）：SSH 握手、公钥认证、
exec 通道、版本握手，以及那几项站点查询（分区、队列、节点、最近作业）—— 报回来的是
那台集群的真实数据。三条前置假设里前两条因此不再是推断：

- 登录节点放行公钥认证 ✓
- `ForceCommand` 守卫放行固定 argv 的命令串 ✓

**2026-10-18 补上了第三条**：提交一个会话、把 code-server 跑起来之后，
`direct-tcpip` 端口转发把 `127.0.0.1:18080` 上的页面送过来了 —— 界面真的打开过，
临时离开之后也接得回来。所以"转发通不通"不再是推断。

**常驻通道那一半没有确认过**，而它的形态在界面上看不出来：客户端连上之后先建
`slurmate stream` 那条常驻通道（省掉每次 RPC 一次的 exec），建不起来就安静地退回
exec。已经验到的是它这一侧 —— `ResidentChannel` 的字节层（只认字节与行、不连 SSH）、
推送的消费（`session.js`）、假后端照同一条规则推，以及两侧字面量的交叉校验（子命令名、
通知的键名、看门狗与快照周期的大小关系）。没验到的是真的 `ssh -T … slurmate stream`
那条链路上，一条连接里请求与通知混在一起的样子。
**要看它在不在**：连着的时候在登录节点上 `pgrep -af 'slurmate stream'` —— 有一条
常驻的 python 就是通道在用，一条都没有就是退回了 exec。另一处是
`SshBackend.resident`（`true` 在 / `false` 试过不通 / `null` 还没连上）。
**别把上面那几条跨文件校验读成"常驻通道验过了"**：它们钉的是同一份契约被写了两遍这
件事，不是"这两半接得上"（转发那一半已经验过，这里说的是常驻通道）。真机上再看三样：① `resident` 是不是 `true`；② 一条 `ping` 有没有
回填 `rid`；③ 收到过 `seq` 吗。

**「两台电脑同时在看同一个作业」也落在这一档里，而且它比上面那条更难验。**

> 这一节从前写的是 v0.8 的「两台电脑顶替」：后到者赢、`displaced` 通知、被顶掉的那台
> 禁止自动重连。那个形状在 v0.9 阶段 3 整条删掉了，连"顶掉"这件事都不存在了（见
> 「已经不再是问题的」里的 S28），所以那一笔账连同它引用的
> `client/test/displaced.test.mjs` 一起消失。

> 留下来的不是同一个问题。今天要验的是接管，而它是一件完全不同的事：显式、按会话、
> 只改一格。

- **验到了**：服务端那一半（`cluster/test-sessiond-logic.py`：心跳的四档判据、
  `takeover` 只动 `keeper` 一格、`leave` 清空看护者、连接上限是拒绝而不是顶掉），
  以及客户端那一半（`client/test/suspended.test.mjs`：`ignored: not_keeper` 会进入
  「被接管」且这一拍不算数、`resume()`、被接管的会话不发 `goodbye`；`boot.test.mjs`
  里那一条端到端的「被接管之后又点【接管】」）。
- **没验到**：真的两台电脑。会话在甲机上跑着、乙机连上来点【接管】、甲机界面上那一
  句话、以及乙机是不是真的接上了心跳（`last_hb_socket` 继续推进）。这一整条要两台
  机器加一台真的登录节点。
- **2026-10-18 真机上见到了这一整条的前一半**：甲机在看一条会话，乙机连上来之后
  守护进程回 `ignored: not_keeper`（乙机没有接管，甲机的作业与插件照常），乙机的
  作业页上那颗「接管」可用。**仍然没见到的**：真的点下「接管」之后那一跳 ——
  看护者换人、甲机收到那句「已被接管」、乙机的心跳把 `last_hb_socket` 推起来。
  这一次同时暴露出两处界面缺陷（乙机那句话写成了「已被接管」、断线遮罩把没有
  页面的会话也整屏盖住），两条都已修，见 `CHANGELOG.md` 0.29。
- 假后端能演到什么程度：`app:debug foreign-keeper` 造的是一层覆盖（"服务端此刻认为
  谁在看"），它能演出甲机收到 `ignored` 之后的样子。而它造不出"另一边真的存在"：
  那台电脑、那条常驻通道、它自己的心跳，一个都没有。
- 于是"乙机会接手心跳"这句话今天仍然是一条推断。它依赖的是已有的 `reattach`
  （`list` → 看到会话 → 逐个接上 → 开始心跳）加上客户端接管成功后补打的那一拍，
  而两条路各自都有覆盖（见 `boot.test.mjs`）。但它们没有在"两台真机"这个场景下一起
  跑过。

### U2 — 安装与升级：首次安装跑过了，诊断、修复与升级没跑过

**v0.13 给这一段加了一条要看的东西**：站点侧的插件落盘形状变了，从 `<id>.splug`
一个文件变成 `<id>/` 一棵树加 `<id>.json` 一份记录表。

卸载那一步读删除标记（`.installed`，目录模式下每行一个 id）然后逐个删，而次序是先删
记录表、再删树。这是撤回提交的写法：崩在中间就是一个没表的目录，下一轮收敛。

"清干净"的判据也跟着变了。`plugins/` 下除了装着的那些树与记录表不该留下别的东西，
而没有记录表的目录是刻意不删的，那一格可能有管理员手放的东西。真机上要确认这一条
不会把谁的东西带走。

**已经跑过的：单文件包那条路整条跑完过**（2026-10-17，一台真实的集群，以 root）。
它解压到临时目录、转发给 `install-base.sh`、退出时删干净，而那个脚本把首次安装的
每一段都走完了：复制文件、建目录、设权限、渲染并安装 systemd 单元、首次装
`slurmate.conf`、enable / start。判据是守护进程真的在 systemd 下起来了、客户端连得上
它 —— 而它顺手把下面那两条也答了：文件与属主权限对得上（对不上时守护进程起不来），

### U7 — 分发跑通过一次；签名、上限余量与文件系统没有

**v0.13 改了这条路上几乎每一个字节**，所以要验的东西换了一批，而"押后"的理由因此
更强：形状在这一版里又动了一次。

- 站点发的是只含客户端侧的那一份（`client/**` + `plugin.json` + `lineage.json`），
  所以下面那个 2 MiB / 4 MiB 的余量要重新量一遍。包更小了，余量比从前宽，但"到底
  多宽"要用一个真插件的真负载量出来。
- 容器是 `format 2`（四元组签名），而客户端要从自己手里那一半重算 `digestClient`
  再与信封比。那一半的字节必须逐字节对得上，这是整条链上最值得亲眼确认的一步。
- 客户端池现在是平铺的 `<id>_<版本>/` 加一份同名的记录表，容器解完就扔。真机上要
  确认池子里确实没有 `.splug`，以及 `require()` 真的从那棵平铺的树里加载得到。
- 用户机器上不该有 `job/`。这是本版的主题判据，而它在真机上的形式就是一次实测：
  同意一个插件，然后 `find` 一遍池子。

> **2026-09-17：这一条被明确决定「现在不跑」。** 理由是明确的，而且它站得住：插件
> 这一块接下来还会大动，此刻在真集群上验的是一个马上就要再变的形状，测出来的结论
> 留不住。

> 那不是"省一次事"，是不让一次测试冒充一个结论。所以它不是"排期上还没轮到"，是刻意
> 押后，押到形状稳定为止。到期之前，下面这一段留着，它记的是"要验的是什么"。

连带的一处：`files` 与 `plugin_file` 的删除原来挂在这一条上。CHANGELOG 里写着"要等
U7 那次真集群分发跑过之后，在那之前旧路一直能当退路"。那道闸 2026-09-17 一并撤了。

撤它的理由不只是"不用等了"，那道闸的推理比它读起来弱。客户端从阶段 5 起就优先走包
（`deliveryOf` 只要 `package` 说得通就选它），所以 U7 无论删不删 `files`，跑的都是
`plugin_package` 那条路。这条实测的覆盖面与被删掉的那条退路无关。

退路真正保护的是一个老的客户端二进制，阶段 5 之前编出来的那一个，而那不是一次实测能
验的东西。

**账单上多了一笔（v0.7 加握手时记的）**：连接期现在多问一次 `ping`（版本握手，见
`docs/PROTOCOL.md`〈三方：谁不低于谁〉）。一次 RPC 就是一个 exec channel，而守护进程
是单线程同步的。稳态下一次连接多这一笔可以忽略，但它属于"真机上才成立的规模问题"
这一类，所以要记在这里，而不是靠"应该没事"。

**2026-10-18 验到了主路径**：站点上装一份包 → 客户端对账取回 → 同意 → 会话用起来；
版本升级（1.0.0 → 1.0.1）也走过 —— 那一次还撞到了"旧版本不回收"的缺陷，已修。
池子是平铺的、`require()` 从那棵树里加载得到，这两条由会话真的跑起来证明过。

下面这些是那一次没有覆盖到的。客户端把插件取回来的每一步本机都仍有用例
（`client/test/site-plugins.test.mjs`）：

```
plugins（一个含 package{format,bytes,digest} 的清单）
  → 一次 plugin_package（整个 .splug，base64，走 ssh -T 的一行 JSON）
  → 自己解析容器 / 逐份校 sha256 / 重算内容摘要 / 验签
  → 暂存校验 → 同意闸 → rename → 对账收尾
```

要重点看的几件事，都是只在这种规模下才成立的：

- **上限够不够。** `cluster/slurmate` 的 `rpc()` 一次最多读 4 MiB 或读到第一个换行
  （`RPC_MAX_RESPONSE_BYTES`）。整包上限 2 MiB（`PLUGIN_PACKAGE_MAX_BYTES`，base64
  膨胀 4/3，约 2.7 MiB）是按这个反推出来的，余量约 1.5 倍。这两个数有跨文件用例钉着，
  所以它们不会各改各的。而超限时 `json.loads` 必失败，症状是客户端把它归成
  `daemon_unreachable`（code 5）并退避重试：一次"包太大"会被报成"控制节点上的守护
  进程没有响应"。文案已经改对了，但余量在真集群上一次都没被撑到过，只有真机能答。

  单文件上限 256 KiB 那条不再算一笔链路账：删掉 `plugin_file` 之后它只在负载内起
  作用，由打包器与客户端读方各自执行，不再走线。

- **限流。** 2026-10-18 真机上见过 `rate_limited`：接回站点那一阵的突发会把桶打满
  （心跳也在同一个桶里），那一次因此改了心跳的处理。插件那一轮对账现在是 `1` 次
  `plugins` + `1` 次 `list` + `1` 次
  `plugin_package` = 3 次，而桶是每 uid 每秒 100 次（`max_rpc_per_second`，0.28 起；
  见 [docs/PROTOCOL.md](PROTOCOL.md) 的限流一节）。删掉逐份那条路之前它是约 11 次，
  在当时的 10 次/秒上正好压边。这一条从"要看着它别溢出"变成了"有余量"，但真机上
  心跳还在同一个桶里抢，所以仍然只有真机能答。

  常驻通道（v0.8 阶段 3）没有改变这个数：它把同样的这些 RPC 从"每个一个 SSH exec"
  变成"一条连接上的一条消息"，而桶数的是 RPC，不是 exec。变化的是桶之外的那笔开销，
  每次 fork 一个 python。

- **单线程守护进程的开销。** 开销的形状变了：从前是 N 次往返、每次一个小 base64；
  现在是一次往返、一个最大 2 MiB 的响应。峰值内存与单次编解码，而不是 N 次调度。
  哪一样对这台正在服务所有人的进程更贵，没有量过。

- **暂存与换入在真实文件系统上**（家目录是 NFS 的时候尤其）：`rename` 的原子性、
  `fsync` 的口径，见 `site-plugins.js` 里那段"不出现半棵树，但不保证断电后它还在"。

  0.7 把三份原子写收成了一份（`atomic-write.js`），但那只是"三处规矩变成一处"。
  "断电之后新内容还在不在磁盘上"这一条一个字都没动，全仓仍然没有一处 `fsync`。
  别让"统一原子写"这个名字读起来像是把那笔账解决了。

**签名与余量那几项一项都没有专门验过。** 客户端与站点之间那条**分发**路径已经真的
走了不止一次，但包里没有签名块、体积只有二十几 KiB —— 所以"验签""2 MiB 上限"
"单线程守护进程解码一次大响应"这几样都还没有被真实的字节撑到过。

   一台 `Gres=gpu:a100:2`，`client/src/main/backend-fake.js` 的 A6000 也是这样），
   否则那条路一次都不被测到。见 [KNOWN-ISSUES.md](KNOWN-ISSUES.md) 里 F26 的教训。
2. **"已用几张"。** 0.30 起 `cluster` op 的 GRES 项带 `used` / `free`，来源是
   `squeue` 的 `%b`（**已经**在本集群上取到过真实输出：运行中的作业报
   `gres/gpu:1`，没要卡的报 `N/A`）。它仍然是一格推算值，边界如实写着：中钟
   30 秒刷新；作业没写型号而分区里同名多型号时不给；一台节点跨多个分区时不给。

**夹具比真集群"脏"这件事在这里是故意的**，而它有个代价必须记着：这条路上的缺陷只有
在带型号的真集群上才会现形。

所以阶段 2 的用例尽量把判据放在"代码有没有第二份表示"上（结构化存储 + 唯一的拼法），
而不是"某个型号拼得对不对"，后者只能靠夹具。第一次接上带型号的集群时，第一件事是跑
一次 `slurmate-sessiond --check` 看 `GRES` 那一段，再提交一个带型号的会话看界面。

### U10 — Windows 上那条起假站点的路，一行都没在真机上跑过

**位置**：`client/src/main/fake-job.js` 的 `defaultBashSearch()` 与 `findBash()`。

**是什么**：假站点的作业侧是一份 bash 脚本。POSIX 上按 PATH 找到 `bash` 就完了，
Windows 上不是：PATH 用 `;` 分、可执行文件带 `.exe`、Git for Windows 装在几处惯例
位置，而系统自带的那个 `bash.exe` 是 WSL 的入口（它跑的是另一个文件系统里的东西，
路径要翻译）。

2026-10-14 把这几条写了进去：按 `;` 切 PATH、候选名带 `.exe`、补上 Git for Windows
的三处惯例位置、WSL 认但排在最后（走它要 `bash -s -- <入口>` 从 stdin 喂，路径用
`wslpath` 那一套翻）。找到的那一个仍要问一句 `BASH_VERSINFO`。

**验过的是哪一半**：只有纯函数那几条 —— Windows 形状的 PATH 怎么切、候选顺序
（Git Bash 在 WSL 之前）、`C:\…` 怎么翻成 `/mnt/c/…`、翻不动时返回 `null`、
一个 bash 都没有时说的是哪一句。判据在 `client/test/fake-job.test.mjs`。

**没验过的是哪一半**：这台开发机是 Linux。Git Bash 与 WSL 两条路各只有一件事是
推出来的 —— 它们真的跑得动那份宿主脚本、真的收得到 stdin 那一份、真的读得到翻译过
的路径。用户在 Windows 上跑的那一次用的是**没有这一段**的那一份客户端（见 S14）。

**它不会红，所以**：Windows 上这条路到今天只有纯函数那一半的保证。

## 三、结构性的欠账

设计上还没做的东西。它们不是缺陷：缺的东西不会假装自己在。

### S2 — 插件跑在主进程里，没有任何隔离

四条护栏（签名、钉公钥、逐插件同意、进程隔离）里，现在只剩最后一条：
`client/index.js` 仍然 `require()` 进 Electron 主进程，完整 Node 权限、没有沙箱。
S2 因此从"四条一起欠"收窄成了这一条。

**那张逐条对账表不在这里抄第二份。** 它只有一份，在
[SECURITY.md](../SECURITY.md) 的〈站点分发的插件：四条护栏的对账〉。哪一条做了、
哪一条用什么替代了哪一条、还欠哪一条、以及欠着的那条在界面上是怎么说出口的，全在
那里。

抄一份过来等于让"四条里还剩几条"有两个各自会漂的答案，而漂了不会红任何东西。

在它做到之前，同意界面的措辞就是唯一的安全边界，所以那一屏必须把话说满：没有进程
隔离、那段代码会在这台机器上跑。一句含糊的"是否信任此插件"会让用户以为自己在同意 A
而实际同意了 B。

> **2026-10-05：已拍板，本轮不做。理由写在这里，免得下一次重新论证。**
>
> 它不是"排期还没轮到"，是撞了两处硬冲突，而这两处各自都是接口问题：
>
> 1. **`ctx.win.surfaceSession` 是一个活的 Electron `session` 对象。**
>    `client/src/main/index.js` 的 `pluginContext()` 里那个取值器写的是
>    `get surfaceSession() { return win.surfaceSession(rec.slot); }`，插件拿它去配
>    存储分区。一个活对象跨不了进程边界，所以要隔离就得先设计一种"跨进程的句柄"，
>    或者把这个导出整个换掉。
> 2. **`contributes.prepare` 必须同步**（`docs/CONTRACT.md` §3.1.1）。它守着的是
>    「认领实例 → 写进表」之间不让出控制权这条不变量。两条 `app:start` 同时在飞时，
>    让出控制权会让它们都看到"没有持有者"，后一条顶掉前一条的记录，而前一条的作业
>    从此没有心跳、1800 秒后被 `scancel`，界面上只剩一条会话。而跨进程调用必然是
>    异步的。
>
> 两条合起来意味着：**隔离不是"把 `require` 挪个地方"，是一次接口设计。**
>
> 在那之前，表达这件事的地方只有两处：`SECURITY.md` 的〈四条护栏的对账〉与〈不在
> 威胁模型内〉，以及上面那句"同意界面的措辞就是唯一的安全边界"。`SECURITY.md` 那一
> 节现在也记着第 2 条耦合，做隔离的人必须先处理它。

### S5 — 三项检测工作，一项都没做

1. **auth canary（优先，成本最低）**：作业里 code-server 起来后自己 `curl` 一次不带
   cookie 的 `GET /`，预期 302 → `/login`；若是 200 就自杀并写审计。防的是
   code-server 升级后口令语义变了，作业正常启动、正常能用，口令却完全没生效。那会
   让 `auth_mode = password` 唯一的价值消失，而正常使用中永远看不出来。
2. **`doctor` 从健康检查升级为不变量检查**：现在只查"进程活没活、表在不在、数量对
   不对"，攻击成功时全部显示正常。应改成断言不变量：活跃 claim 集合 **==** nft 规则
   集合（双向，不只数量）、每条规则的 comment 能反解出 claim、所有活跃会话的
   `auth_mode == password`、`released` 的 claim 一定没有规则。

   并且必须定期输出「检查了 N 项，全部通过」，否则"没有告警"和"检查根本没跑"无法
   区分。
3. **故障注入演练清单（一次性验收）**：这些路径正常使用中永远跑不到：
   `systemctl restart nftables`（表要自愈）、`restart slurmate-sessiond`（规则收敛）、
   停 munge / 重启 slurmctld（会话绝不能被拆）、`kill -9` 作业、断网 60 秒（应进
   `suspect` 且不拆规则）、手工 `rm` 掉数据库（应从 nft comment 反向恢复）、
   `scancel` 作业、并发跑两次部署（`flock` 挡不挡得住）。

   核心结论：安全的失效表现为沉默。正常使用等于所有校验都返回 OK，也就与"校验代码
   根本没运行"无法区分。所以解药不是更强的监控，而是主动扮演攻击者，以及写下不变量。

### S9 — 摘要的算法版本字段今天还不可观测，而换公式本身也还没做

同意台账的一条现在是 `{digest, alg, site, at}`，`isTrusted` 要求 `alg` 与当前算法
相符，缺失时按"公式没变过"解释（`TRUST_ALG_LEGACY`，见 `client/src/main/config.js`）。

但 `TRUST_ALG_LEGACY` 与 `TRUST_ALG` 今天都是 1，于是"把缺省值改成当前值"那一处
改与不改行为完全一样，变异验证跑它一条都不会红。这不是用例没写好，是这件事今天确实
没有可观测的差别。

它是为下一次换摘要公式准备的。在那之前它不是一条防线。按这个仓库的规矩，这件事写在
明处，不假装有测试钉着它。

连带记着的是它准备的那件事本身还没做：摘要公式（`plugins.digestOf`）今天仍然是
v0.6 那一套（按相对路径排序 / 类别入哈希 / 权限位入哈希 / 符号链接记 `readlink`
字串不跟随 / 空目录入哈希）。

换公式技术上已经可行了，挡在它前面的那个洞（"池里有一份、台账对不上，界面上彻底看
不见"）已经修掉。但那是一件能独立验证的事，刻意没有和前一段叠在同一个提交里。

### S40 — 测试后端的假站点不跑**中转站**那一类插件的作业侧

**位置**：`client/src/main/backend-fake.js` 的 `_submit`（判据是 `sitePlugin.surface`）。

**是什么**：有界面的那一类插件，假站点今天真的把它的作业侧跑起来。而要公钥的那一类
（中转站，比如那棵 sshd 样例）不跑：会话照样登记，隧道目标是一个没有东西在监听的端口
（`DEMO_SSHD_PORT`），`ssh_host_key` 是一个形状正确的假值。

**为什么不跑**：那一类的作业侧起的是一个真的 sshd，它要站点侧装好的 sshd、主机密钥、
以及那一套认证配置。那不是"在这台机器上 `node` 一下"能补上的东西，与"插件的依赖得装
在本机"是同一条限制，只是这一种连本机装了也未必起得来。

**出路**：本机真的有一个能用的 sshd 时，那一类照着有界面的那一类做即可，把
`sitePlugin.surface` 那个判据换成"这份树里有没有作业侧"。

在那之前，它在测试后端里的失败形态是"隧道连不上"，而那与真站点上一个起不来的 sshd
是同一个现象。所以它不骗人，只是验不到。

> **2026-10-14：按上面那条出路试过一次，退回了。** 把 `if (sitePlugin.surface)`
> 换成"这棵树里有没有作业侧"，12 条用例当场红。**这一道闸比中转站宽**：
> `debugAddSitePlugin` 造的那些"站点上有、本机不认识"的条目也没有 `surface`，
> 而好几条用例（未知服务、数据空间、崩溃重连）靠的正是 `_enroll` 里那个编出来的
> 端口与主机公钥。它们测的是别的正经事，只是"会话得先跑起来"这一点踩在那儿。
>
> 要真的改，得先让那个调试开关造得出一棵**真有作业侧**的树 —— 那样"未知服务"
> 这条路仍然是"站点真的有它、只是本机不认识"，比现在更 faithful。在那之前别动它。

**它不会红，所以**：中转站那一半的作业侧（`start_sshd` 那一整套、主机密钥怎么进

### S25 — RPC 次数随会话数**线性增长**，而没有任何东西会告诉用户他开太大了

> **2026-10-05：这一条原先的量级算错了约 25 倍，就地更正（下面的数字是按代码算的）。**
>
> 原话说「10 是每秒的桶，所以 N ≤ 10 时余量很足；但……用户真的开到十几条时，会撞上
> `7 rate_limited`」。那句把"每秒 10 次"读成了"总共 10 条会话"。按代码重算：
>
> - 每条会话的稳态速率等于心跳，`HEARTBEAT_MS = 45000`，约 **0.0222 次/秒**。再加上
>   状态轮询，`STATUS_MS = 60000`，0.0167。但轮询只在推送不健康时才发
>   （`client/src/main/session.js` 的 `_startStatusPoll()` 里那句
>   `if (this._pushHealthy()) return;`），所以它是两档：
>
>   | 常驻通道 | 每条会话 | 撞上 100 次/秒需要 |
>   |---|---|---|
>   | 在（推送健康，只有心跳） | ≈ 0.0222 次/秒 | **≈ 4500 条会话** |
>   | 不在（退回轮询） | ≈ 0.0389 次/秒 | **≈ 2570 条会话** |
>
> 阈值是两三千条会话这个量级，不是十几条。而 `max_sessions_per_user` 缺省 **1**
> （`DEFAULT_MAX_SESSIONS_PER_USER`），单个用户今天离那道线还差 **4500 倍**。
>
> **顺带更正一处符号名**：`max_rpc_per_second` 不是配置键。守护进程里写的是
> `self.max_rpc_per_second = MAX_RPC_PER_SECOND`，一个模块级常量，没有走
> `getint(...)`。所以下面「把它也变成配置键」是一条真的还没做的路，不是一句现状
> 描述。

> **2026-10-18：0.28 把上限从 10 提到 100；上面那张表已经按 100 重算（原先是
> ≈450 / ≈257，差 450 倍）。结论不变。**

**位置**：`client/src/main/session.js` 的心跳（`HEARTBEAT_MS`）与状态轮询（`STATUS_MS`），
以及 `cluster/slurmate-sessiond` 的限流桶（`rpc_allowed()`：按 uid、1 秒滑窗、上限
`cfg.max_rpc_per_second`）。

**事实**：每条会话各自心跳，N 条会话约 N × 0.022 次/秒，推送不健康时再加 N × 0.017。
桶是按秒算的，所以上面那张表就是它们之间的距离。

**症状**：会话看起来卡住（状态不再刷新），而没有任何一处说"你把客户端开太大了"。
客户端对 `rate_limited` 的处理是退避重试（`client/src/main/classify.js` 的
`RATE_LIMITED`："限流，退避重试，不要弹错给用户"），所以它多半表现为"慢"而不是"错"。
那正是最不容易被归因的一类。

**修法（未定）**：要么客户端在会话数变多时拉长轮询间隔（总速率封顶），要么把这个上限
也变成配置键并让它可观测。**在决定之前不要顺手改。**

**v0.7 之后这件事变得更容易发生**：一个声明了 `concurrent: true` 的插件现在真的能开
第二份（见 S24），于是"N 条会话"第一次成为用户随手做得到的事，而不必先配几条连接。

但量级更正之后要说清："随手做得到"到"两三千条"之间仍然隔着三个数量级，所以这一条
不是正在发生的。

**它仍然留在这里，因为它是一笔真账。** 那个桶是按"人点一下按钮"设计的，而会话数是
一个可以线性增长的量。站点把 `max_sessions_per_user` 调大（那正是 v0.7 引入那个配置
键的用途之一）就能把它推到表里那一档，而推到了以后没有任何东西会告诉用户。这是
"设计上够不到"，不是"已经解决"。

**2026-10-16 补一句**：站点这一侧现在多了一格更窄的闸（每个插件自己的
`max_sessions`，见 [CONFIGURATION.md](../cluster/docs/CONFIGURATION.md)），它管的是
"这个插件上你能同时开几个"，而且拦下来时会说清是哪一个上限到了。这一条**不受它
影响**：这一条说的是限流桶与用户对"我开太大了"这件事一无所知，那是客户端的可观测
性问题，与上限有几格无关。

### S30 — `systemctl reload` 的结果，外面读不到

**记于 2026-10-07（v0.12 阶段 3 落地时发现，用户当场点名记下来、后面要讨论修复）。**
它不是缺陷，缺的东西不会假装自己在；它是一条**说准了的限制**。

**限制**：`systemctl reload slurmate-sessiond` 的退出码不表达「配置生效了没有」。它
只说信号送到了：systemd 把 `SIGHUP` 发给主进程就算成功，它无从知道守护进程内部接不
接受。

而 v0.12 拍的那一条是「校验不全过就一个字都不改」：守护进程碰到必须重启的键会整个拒绝
这次重载，继续用旧配置照常服务，而 `systemctl reload` 照样返回 0。

**影响**：脚本与自动化判不出来。`slurmate plugin install` / `slurmate plugin sync` /
`cluster/install-base.sh` 今天只能如实说「已给它发了重载信号」并指路 `journalctl`。
说得准，但调用方拿不到「成没成」这个布尔值，人也得多跑一条命令才知道。

**修复方向**：让 `ExecReload` 走一条会等的路。守护进程加一个一次性的 `--reload` 模式
（或让 `slurmate` CLI 直接发一条 socket 请求），把结果（接受 / 拒绝 + 拒绝的键名
列表）作为退出码与输出带回来，单元的 `ExecReload` 改成它。

这是协议改动（新增一个 op），也牵动 `slurmate` 的重载文案与安装脚本的那个分支。

**要回答的**：

1. **拒绝时退出码取什么**：非零最自然，但 `systemctl reload` 于是会失败，而「服务好
   好的、只是这次没热成」并不是运维意义上的失败。要不要用一个专门的非零码，还是仍然
   返回 0 而把结论写进 stdout？
2. **要不要区分三件事**：信号没送到 / 送到了但被拒绝 / 送到了且生效了，今天它们
   在退出码上是同一个 `0`。
3. **socket 请求的鉴权**（今天 socket 的信任模型是什么，一次性模式走不走同一条）。
4. **拒绝的理由要结构性地带回来**（键名列表），不是一句人话。否则调用方还是只能把它
   打印出来，等于没解决。

**0.24 结清软件侧。** 新增 `daemon` op：`config.last_reload` 报出
`seq / ok / error / cold_keys / notice_keys`。`slurmate service reload` 先记下
`seq`，发 `SIGHUP`，等它前进，然后报「接受」或「拒绝 + 原因 + 键名」，被拒时退出
非零；插件命令也走这条路，于是"包装好了、服务没接受"能被调用方看见。四个问题的答案：
① 拒绝用非零（这个命令的职责就是回答"成没成"）；② 三件事分开说（信号没送出去 /
送到但被拒 / 接受），只有前两种非零；③ 复用同一条 socket 与 `SO_PEERCRED`，没有
一次性模式，`daemon` 只读、任何用户可问；④ 拒绝理由结构化带回（`error` 是原因，
`cold_keys` 是键名列表）。

**仍然成立的限制**：直接 `systemctl reload` 依旧是信号语义 —— systemd 看不到服务
内部的结论。知道结果的路只有 `slurmate service reload`，文档已写明。

拿一个机械判据把两份排障的**每一节**过了一遍：**这一节里有没有给管理员的命令**
（`sudo` / `journalctl` / `nft` / `systemctl`）或 `slurmate` CLI。

#### 结论：按**节**挑，挑不出来

原来以为能整节挑出"只对用户成立"的那几节。**核完发现一节都没有。**
33 个小节里：**22 节带管理员的命令**（那些是管理员自己的工具，用户既看不懂也不该跑），
其余 11 节里的大多数**讲的是实现者的纪律**，不是给用户的指引，例如

| 节 | 它其实写给谁 |
|---|---|
| 排障〈隧道连上但页面空白〉 | **管理员**：主体是 `slurmate status --json` 与一张 `curl` 结果对照表；对用户只有一句"点重新加载" |
| 排障〈中文输入法在会话窗里失效〉 | 6a 是用户动作（点一下编辑区），**6b 是实现者的代码规矩**（`if (input.isComposing) return;` 那一行） |
| 排障〈面板上「剩余时间」显示「未知」〉 | **实现者**：整节讲的是"界面必须容忍 `undefined`，不许显示 `0` 或 `NaN`" |
| 排障〈本地监听端口不是首选端口〉 | **实现者**：讲 `_listen` 的校验与顺移逻辑 |

**原因是结构性的：这两份文档按症状组织，而一个症状的读者天然是混合的。**
"页面空白"这个症状，管理员要知道怎么查、用户要知道点哪里、实现者要知道为什么会静默。

####，于是所以待办要改成**按句挑**

**对用户说的那些话，散在各节的句子里**，不在节的边界上。要挑的是句子，逐句判三种归宿：

1. **进界面**，变成界面上的一句话、一个提示、或一个 tooltip；
2. **删**，本来就不必说；
3. **留在这儿**，因为它同时是管理员查这件事的一部分。

已探明**最该判**的一处：排障〈「我点了【临时离开】，作业什么时候会停？」〉：
它的核心事实（**35 分钟倒计时**）是**用户必须知道**的，而它整节都在对读者说话。
它在界面上有没有对等的一句话，**没有核过**。

判据写成一句可执行的：**这一句话，用户在没有文档的情况下，能不能从界面上得到？**
不能，于是它就是 1 或 2 的候选。

### S35 — 判据 F 有一条**已知的欠报**，它**不会红**

**位置**：`tools/check-doc-prose.py` 的判据 F（公开文档不叙历史）。

**是什么**：有一类历史叙述**它抓不到**，而且抓不到这件事**没有任何东西会报**：
所以它会安静地留在文档里，直到有人手工读出来。（第二类「反引号里的版本号」已在
0.29 补上，见本节末尾的注记。）

#### ① 反引号里的「已死标识符」

`` `DEFAULT_CPUS` ``、`` `max_clients_per_user` ``、`` `plugin_file` `` 这类**已经不存在**
的名字，写在文档里而不说它是旧的，F **不判**。

这是**有意的取舍**，不是疏漏：要判它就得维护一张正列表（哪些标识符已经死了），
而**那是一张会漂的表**，删一个常量、改一个键名，都要顺手加一条，漏一条就永远
漏下去。「同一条规矩两份实现会漂开」是这个仓库记过的教训，一张靠人维护的判据表
是它的另一种形态。于是**宁可欠报，不要一条会悄悄失效的判据。**

它属于**另一类问题**：文档说的和事实不一致，与「叙历史」是两件事。
路径类的那一半**已经有主**（`tools/check-doc-links.py` 的 A1 报"写的路径不存在"），
符号类的那一半今天**没有主**。

#### ② 版本号在**反引号里**、时间词在**反引号外**

**这一条是 v0.15 收尾时实测出来的**，而 `SECURITY.md` 里就有这个形态的真实句子：

    > **`0.6` 起到今天（`0.18`）都尚未发布**：……

探针（构造一个 mini git 仓库喂给判据）的四个样本：

| 样本 | F |
|---|---|
| `` `0.6` 起到今天（`0.18`）`` | **不报** |
| `0.6 起到今天（0.18）`（版本号不在反引号里） | 报 |
| `` `v0.6 起到今天` ``（整段都在反引号里） | 报 |
| `v0.13 起不再发整个包`（校准样本，必须报） | 报 |

于是欠报的精确条件是：**版本号被反引号包着，而时间后缀在那个反引号之外**。
判据的正则要求版本号**紧跟**时间词，中间夹一个反引号就断了。

**为什么值得单独记**：这个形态**很自然**，把版本号放进反引号是写文档时的习惯
动作，所以它会**重复出现**，不是一次性的。而 `SECURITY.md` 那一句至今仍然在。

**要与另一件事分开**：`S35` 讲的两条是**正则**没覆盖到的形态（判据在正常地看，
只是那两种写法不在它的词表里）。v0.15 收尾时还发现过**另一类**问题，判据的
**遮罩**（哪一段算引用、因而豁免）会**静默失明**：`packer/docs/PLUGIN-SPEC.md`
有 38.1% 的正文从来没被看过，而判据照样打印「全过」。**那一类已经修掉了**
（遮罩 + 三条守遮罩的自测样本，见 `CHANGELOG.md` 的〈Fixed — 判据的遮罩会静默失明〉）。
两件事的性质不同：**这条是词表不够长，那条是判据闭上了眼睛。**

**修法（本次不做）**：让正则容忍版本号与时间词之间夹一个反引号。
但那是**改判据**，要按本仓库的老规矩配上坏样本（新形态必须被抓住）**与假红样本**
（`` `0.15` 不是 `0.1` `` 这类举例句不能被误伤），并且**分开证明**：
判据扩了一条 ≠ 文档新长出了违规。

> **2026-10-18（0.29）：第 ② 条修掉。** 反引号里的版本号后面跟「起 / 之前 /
> 以前 / 之后 / 后 / 时」时都会报；后面紧跟「是 / 为 / 进位 / 变成」的不判 ——
> `0.255` 之后是 `1.0` 那类版本进位算术长得与历史叙述一样，而它是规范本身。
> 自测加了两条坏样本与两条假红防线。第 ① 条（已死标识符）原样留着，理由不变
> —— 那需要一张会漂的正列表，宁可欠报。

### S38 — 浮窗那一层多了一个 renderer 进程，而它常驻

**位置**：`client/src/main/windows.js` 里浮窗那一块（它自己的 `hover.html` /
`hover.js` / preload）。

**是什么**：浮窗**必须**由一块原生视图画，它在插件那块界面**之上**，而那块界面
是原生的，画在面板的 DOM 里会被物理盖住，一个像素都露不出来。于是这一版多了一个
`WebContentsView`，**也就是多一个 renderer 进程**，而它**懒建之后一直活着**
（收起只是把它移出视野，不是销毁）。

代价：一个常驻的 renderer（Chromium 的多进程模型下，每个 renderer 有自己的 V8
堆与事件循环）。对一个桌面客户端来说不算什么，但它是**结构上多出来的那一个**：
记在这里，免得以后有人数进程数时把它当成泄漏。

**为什么这一版不做掉**：三个候选各有代价，**收起即销毁**会让"停靠"这个随手
就会发生的动作每次都付一次冷启动；**与面板共用一个 renderer** 要面板那边也改结构；
**改成在面板 DOM 里画**在物理上不可能（会被原生视图盖住）。这一版选的是
「懒建 + 常驻 + 尺寸与位置先定死」。

**它不会红，所以**：看到客户端有两个 renderer 时，这一条就是答案。

### S41 — 测试后端的假站点演不出来的那几样，逐条留着

**位置**：`client/src/main/backend-fake.js`。

**是什么**：测试后端的要求是"测试用到的那几个 op 与真守护进程形状一致"，

### S42 — 并发上限只在**点下去之后**拦得住，界面不预告

**位置**：`client/src/renderer/panel.js` 的 `pluginBlock()`，与
`client/src/main/index.js` 的 `pluginsView()`。

**是什么**：站点给每个插件设的并发上限（`max_sessions`）在插件那一块上只读地摆着
（"最多同时 2 个会话"）。它**不预告**"你还能不能再开一个"：那个数要看用户此刻有几个
这个插件的会话，而插件那一块只在站点对账、连接、提交那几处重画。于是已经到上限时，
那颗「开始会话」仍然是亮的，点下去才拿到 `4 quota_active`，以及一句带着当下个数的
拒绝。

**为什么这一版不做**：那个个数在 `pluginsView()` 里没有来源（会话表在主进程的另一
处，而插件视图是按站点清单画的）。补它要引一条"会话变化 → 重推插件视图"的线，而
那条线上每一处都得回答"会不会把一个陈旧的数目报给用户"—— 报一个会过期的数比只说
上限更坏，用户会照着它决定按不按。它与 `can_submit` 不是同一类：那个拦的是"现在
提交得出去吗"，一个不出错就不会变的站点事实。

**它不会红，所以**：界面说得出上限，而"现在还能不能开"只有服务端那一句话说了算。

### S44 — 自解压包下载被截断时，如果截在壳里那一段，它会安静地什么都不做

**位置**：`cluster/run-header.sh`（壳）、`cluster/make-run.sh`（拼包）。

**是什么**：包体是 `tar.gz`，而它自带 CRC —— 传输截断落在包体里时，
`--extract` 与安装那条路都会非零退出并说"包体不完整"（有用例钉着）。壳那一半是
一段 shell 脚本，**它自己报不出自己被截断**：bash 读到一个中途结束的脚本，就在
那里收尾，前面那些注释不产生任何动作、退出码是 0。

**什么时候会发生**：下载在最初那百分之几就断（壳约占整个文件 3%）。截在包体里
（99% 的字节）都是响的，所以这条的窗口很小 —— 但它的失效形状正是这个项目一路在清
的那一种：什么都没做，却回了 0。

**为什么这一版不做**：能想到的两条路都不成立。让壳在开头自检"包体在不在"没用 ——
截断点在它前面时那一行自己也不在了。外部校验（发出方给一个 sha256）是唯一真正的
办法，而那要另一条信道上传来一个值，今天没有这条信道（包只有一个文件，
`make-run.sh` 打出的 sha256 印在构建输出里）。

**它不会红，所以**：用例里那一条测的是"包体被截"，不是"壳被截"。壳被截之后没有
任何东西留下可供断言的痕迹 —— 它连一行输出都没有。


### S46 — 基座不做文件传输（2026-10-18 已拍板）

> **2026-10-18：已拍板，不做。理由写在这里，免得下一次重新论证。**

**是什么**：基座不提供浏览站点文件、上传、下载与断点续传。文件传输归插件那一侧。

**为什么不**：三条路已经覆盖了这一块。

- code-server 的资源管理器：工作区内，作业活着时。
- SSH 中转站：作业里开了 `Subsystem sftp internal-sftp`（`plugins/sshd/job/start.sh`），
  scp、rsync、sftp 全套，端点在计算节点，连本地 scratch 都看得见。
- 用户自己的 ssh 工具。

基座自建（登录节点 SFTP）独占的场景只有两个：会话没起来之前或结束之后；工作区
之外。性能上也不占优：落点在登录节点，读写走 NFS，而会话数据的最短路径通常在
计算节点。

**什么时候重新论证**：两条触发器，任一成立就启动。

1. 站点上出现一种确实没有传输能力的插件类型，并且有人在用。
2. 实测到上面两个独占场景是真实痛点（大文件、闪断、无会话时段、工作区之外）。

**真做的时候做薄的**：上传、下载、队列、断点续传、工作区快捷入口。不做双栏浏览、
预览、重命名与删除 —— 那些 IDE 已经有了，基座只补够不到的空档。

### 保留 ① — 写进磁盘的 schema 编号沿革

S13 那一行末尾那句话就是同一件事。凡是从前删东西时留下的，都属于这一条。

判据只有一句：**它教了有用的东西没有。** 只讲"以前叫什么名字"而不教任何东西的，删。

它们解释的是**已经做过的删除**，不是待办，与保留 ② 同一条判据。

### 保留 ⑤ — 不给插件数据的身份加「站点」段（**查过了，是键选错了**）

用户提过：不同的 ssh 连接（不同的集群）应当各自一份数据，同一个集群的应当共享。听起来
只要往身份里加一段站点就完了。查下来那条路走不通，而且方向是反的。

**为什么**：客户端算不出「集群」。协议里没有集群身份，`whoami` 只有
uid/gid/user/home/account，`site-plugins.js` 自己写着这一句。

唯一能算的候选是 `siteKeyOf(conn)` = `sha256("user@host:port")` 的前 16 位。而那个串
与连接键逐字相同（`config.js` 的 `connectionKey` 就是 `user@host:port`），连接正是按
它去重的。于是该键在连接上单射：两条连接不可能有同一个 siteKey。

于是把它放进身份就等于每条连接各自一份数据，工作区的「多对一」彻底失效。而「多对一」
正是用户要的那件事：两条连接共享同一份编辑器布局。

**还有第二处**：`user@host:port` 是用户能手改的字段。它一旦进身份，改一次 host/port
就把那份数据变成孤儿。而 `plugin-data-audit.js` 的「没人用」判据照现存连接算，于是旧
键下那份数据会立刻出现在界面上，带着一个删除按钮。

**真正在承担这件事的是工作区本身**，它是用户对"这几条连接算同一个"的显式声明。而"不靠
记得"那一半落在别处：`ensureConnectionWorkspace` 的默认行为，见
`cluster/docs/TROUBLESHOOTING.md` 的〈工作区〉一节。用户已决定这一轮不做站点段。

### 保留 ⑥ — `relay` 那一档**仍然不能**按插件 id 拆细

`plugin-data.js` 的 `slotOf` 里，不要数据空间的那一整类共用一个槽。它有过两条理由：
"端口由插件的 `preferredPort` 自己挑" + "ssh 别名是插件自己的常量"。

**第一条已经不成立了。** 那个钩子收掉了，无组会话的端口现在是基座的常量
`RELAY_PORT_BASE`，基座核对得了。

**v0.7 之后这一档换成"两层"来说**（见 PLUGIN-SPEC §2.8）。架构层：不要数据空间的插件
没有第二份实例的来源（一份数据就是一个插件在一个工作区里的那一份），所以基座发不出第
二份对外身份。作者层：写进用户 ssh 配置的那个别名是插件自己的常量，基座无从核对两个无
组插件的别名会不会撞。

于是别因此就把 `slotOf` 的 `relay` 那一档按插件 id 拆细。拆细的前提是插件把别名也交给
基座声明，清单里加一格，基座才核对得了、才拒得掉两个撞名的无组插件。在那之前拆细会让
两个互不认识的无组插件并存着去抢同一个 `ssh slurmate`，而症状是"连到哪一个是不确定
的"，两边都报"已就绪"。

而 `contributes.concurrent: false`（sshd 写的就是它）不能替代上面那条。它是作者对"我的
代码能不能有两份"的回答，管的是"同一个插件的第二份"。而拆细要解决的是两个**不同**的无
组插件之间的撞名，那件事仍然是基座核不了的。

**v0.7 的"认领"（见 S24 那一行）没有动这一档，而那是结构决定的、不是顺带。**
`claimInstance` 对没有实例段的插件（`hasInstance` 为假）恒返回原来那个组，而
`concurrent: true` 要求 `layout: true`，所以一个无组插件在清单校验那一关就拿不到实例
键，`relay` 这一档因此永远不会被认领碰到。

反过来说：要拆细它，先得让无组插件有实例键可发，而那正是上面那条"插件把别名交给基座
声明"要解决的问题。

### 保留 ⑦ — **不**给插件加"集群信息推送"这个 API（**查过了，它已经在了**）

v0.8 阶段 5 的推送（服务端每 tick 把变化推给客户端）看起来该带出一个新问题：
"插件怎么拿到这些更新？"

**查过了：它已经在了。** `index.js` 调的是 `plugin.attach(pluginContext(rec), snap)`，
而那一行在每一次快照变化时都会跑，`snap` 就是刚渲染出来的那一份会话视图。

换句话说，插件看到的"推送"与客户端看到的"推送"是同一次。加一层 `ctx.onPush(...)` 只会
让同一件事有两个入口，而两个入口会漂。

而这条路上真正的风险不在阶段 5，记在 S2：插件是同步跑在客户端主进程里的，所以一个慢
插件会拖慢整个客户端，而它在推送频率变高之后更容易被撞上。那一条要修，修法是隔离
（子进程 / 超时），不是再开一个推送 API。

### 保留 ⑧ — 给 `sessions` 加一列，从此就要删库（**保持**）

**位置**：`cluster/slurmate-sessiond` 的 `Config._db_schema_errors()` 与
`_required_session_columns()`。

**是什么**：v0.7 删掉了 `Store._migrate()`（旧库自动 `ALTER TABLE ADD COLUMN`），换成
一道**两头都查**的启动闸门：库里 `sessions` 的列集合与本版 `SCHEMA_SQL` **现算**出来的
那一个只要对不上（多一列或少一列），**启动就拒绝**，并让人 `rm -f claims.db`。

**为什么删**：自动补列只在旧库上跑，而旧库不存在（见【前提】`0.y` 不考虑兼容性）。
留着的代价是"加一列"这件事有**两种走法**（自动补 / 删库），而它们的区别**没有任何
东西会说**。

**为什么保持删库（而不是把自动补列加回来）**：自动补列是**为兼容而留**，而这一版
明说不考虑兼容性，加回来的唯一效果是让"加一列"重新有两条路，而那正是删它的理由。
**代价写在明处、而且是刻意接受的**：加列从此要删库。删库本身是安全的（会话归属能
从 nft 规则重建），所以这一格的代价是**一次上机动作**，不是数据损失。
它今天离"付得起"还差一层：这个项目至今没有任何部署（见 U2），所以"加一列要上机删一次
库"这件事今天的值是零。这也是"保持"能成立的全部依据。

### 保留 ⑨ — `TRUST_ALG_LEGACY` 与 `TRUST_ALG` 今天同值（**保留**）

**位置**：`client/src/main/config.js`（同意台账的算法版本）。

**是什么**：台账每条记录带一个 `alg`（算摘要用的公式版本）。`TRUST_ALG_LEGACY` 是
"记录里**没有** `alg`"时的解释，而它今天与 `TRUST_ALG` 都是 1。也就是说，它防的是
"将来"换公式，不是"以前的数据"。

**为什么保留**：它不属于"为迁移而留"那一类，而是**为下一次换公式留的那一层**。
注释里的推理成立：没有 `alg` 只能解释成公式 1；默认成"当前公式"会让换公式那天所有
老条目被读成新公式，而那正是这个字段要防的事。

**它今天是一层空的分支，而这件事写在明处**（不假装有测试钉着它）：
两个常量同值时，"把缺省值改成当前值"那一处**改与不改行为完全一样**，所以变异验证
跑它**一条都不会红**（见 S9）。留着它的理由是**那一天**，不是今天。

### 保留 ⑩ — `client/hosts.example.*` 删掉了，不重写（**不写**）

**是什么**：那一对文件（`hosts.example.json` + 它的 README）教用户手写一个
`host`/`port`/`label`/**`priority`** 的数组，并说地址会存进本地配置的 `extraHosts`
字段。**三个东西今天一个都不存在**（那个文件没有读取者、`priority` 在当前连接模型里
没有、`extraHosts` 在 v0.7 被删掉）。文件自己第一行就写着"客户端不会去读它"，全仓也
没有第二处引用它，所以 v0.7 把它们删了。

**`client/src/main/hosts.js` 是活的**（并发探测 + 校验 SSH banner），删的只是那对模板。

**为什么不重写**：它本来就只是给人看的，不写也不影响任何行为。而"给人看的模板"有一个
更合适的落点：添加连接那一屏自己，用户在那儿手填 `host`/`port`。那是界面即文档那条
原则。另起一份会被读成"有第二条配置通路"的静态文件，正是这一版在清的那种东西。

顺带：`priority` 与 `extraHosts` 都是已经删掉的形状，重写一份就得先把它们解释一遍，
那是给一个不存在的字段写说明书。

### 保留 ⑪ — 插件运行时数据的对账只在打开客户端时跑一次（**保持**）

**位置**：`client/src/main/index.js` 的 `auditPluginData()`（入口 `app:pluginData`）。

**是什么**：本机的插件数据在**界面进来时对一次账**，之后只有用户主动删掉一份时重算。
而磁盘上的东西会**在客户端跑着的时候**变（站点回收一个插件版本、用户在别处删了
`Partitions/` 里的目录），于是那一块清单可能陈旧。

**0.7 起它是两个根**（`Partitions/` 与 `<userData>/plugin-data/`），所以"陈旧"的影响面
比从前大一倍：插件那一刻正在写的文件也进了这份清单。

**后果**：界面上写着"有 3 份没人在用"，而其中一份已经不在了（或者反过来：新出现
一份孤儿，界面上看不到，得重启才出现）。

**为什么保持"打开时算一次"。** 第一，它不会让人删错东西：删除那一刻会重新对一遍账
（`deletionVerdict` 的 `stale`），所以陈旧只会让清单少说或多说一句，不会让它动错文件。

第二，与站点分发那条对账不同，这里没有网络、没有"每次连接一次"的自然时机。可选的做法
是"每次会话状态变化时重算一次"，那是拿每次会话事件一次 `readdir` 去换一句可能更新的
文案，而那一屏是低频的。

判据是代价换来了什么：这一格换来的是"文案可能旧"，代价是每个会话事件一次磁盘遍历，
不成比例。**"打开时算一次"是一个决定，不是一处遗漏。**

**v0.12 阶段 6 起，这一次对账还会顺手把孤儿收掉**（`reclaimOrphans`），所以"只在打开
客户端时算一次"同时也是自动回收的时机：一次启动最多收一轮。

而它仍然不会删错东西：能进那一档的只有"按当前注册表再也算不出来"、并且没有任何活会话
认领的那些（`held` 两个根都收），而清单上那些还读得到的（`unused`）一份都不碰。见
`plugin-data-audit.js` 的 `reclaimable`。

**保留 ⑫ 已搬进 §四**（v0.12 阶段 6 起自动回收接手，它不再是"永久漏删"而是
"晚一轮才收"），根因没变的那一半照实留在那儿。编号**不重用**：`⑫` 从此是个空号。

### 保留 ⑬ — 接回来的会话落在**哪一份数据**上，可能和上一次不同（**接受这个代价**）

**位置**：`client/src/main/index.js` 的 `reattachOne`；`client/src/main/plugin-data.js`
的临时实例身份那一格。

**是什么**：一条会话接回来之后，作业一个字都没动（`reattach` 按 `session_id` 认领，
接回来的就是服务端那一条），但它落在哪一份数据上可能和上一次不一样。

临时实例的实例键活在内存里，所以重启客户端之后接回来的那条会话会拿一个新的临时键，
于是有新分区，重启前那份临时的浏览器存储成了残留。

**用户 2026-10-05 表态，原话**：

> 「**布局之类的不同无所谓，但后台作业是同一个是根本原则**。」

所以这一格的判法是：**不接受**的是"接回来之后作业不是同一个"（那一条由按
`session_id` 认领保证，作业一个字都没动）；**接受**的是"落在哪个组上可能不同"。

**写在这里，是为了让它显示成「接受」而不是「遗漏」。** 它是 S24（多开）与 S26 两条线
交叉处的一个已知取舍，不是一件还没做的事。

而"临时的那一份重启之后会空"**必须说出来**，因为用户会看到"我重启了一下，那一份
又空了"。今天说它的地方是状态条与面板上那条常驻提示（`temporary`），而重启之后那条提示仍然在
（新的一份也是临时的）。所以用户看到的是一句一直成立的话，不是一句骗人的话。

与它相对的另一半（`ctx.connection()` 对**接回来的**会话取当前活跃连接）已经在
v0.10 阶段 6 结清，见 §四 的 **S26(a)**。

**保留 ⑭ 已随 v0.12 收口删掉**（2026-10-07 用户拍板）。它当初是
「`--check-plugins` 末尾那段机器可读的 `plugin-packages:` 留着还是删掉」这条**待拍板**
的取舍。判据是"**没有读者**"：它唯一的读者是基座安装脚本，而插件那一半 v0.12
阶段 4 已经搬进安装器（Python，直接调 `scan_plugins()`，不经过那一屏）。删掉的同时
钉它形状的那三条用例跟着删了，"从 shell 里枚举本站的插件"这件事由 `--check-plugins`
**人读的那一屏**接手（每个插件的 id@版本、启用状态、作业脚本路径都在那儿，比那四列
说得更全）。编号**不重用**：`⑭` 从此是个空号。

### 保留 ⑮ — `SCHEMA_SQL` 里那三条 SQL 注释、以及两处**字符串里**的历史（**保留**）

**位置**：`cluster/slurmate-sessiond` 的 `SCHEMA_SQL`；`client/src/main/plugin-data-audit.js`
的 `label:`；`client/test/site-plugins.test.mjs` 的一条断言消息。

**是什么**：v0.15 的主题之一是「源码注释里的历史清掉」。这三处**形态上像注释、
实际上是值**：

| 处 | 为什么是值 |
|---|---|
| `SCHEMA_SQL` 里的 `-- v0.2 删掉了 purpose 列` | 它在三引号**字符串**里（引号前有 `=`），是**SQL 文本的一部分**，会被喂给 sqlite |
| `plugin-data-audit.js` 的 `label: '0.7 之前的旧分区'` | 界面文案，**面板上真的会显示** |
| `site-plugins.test.mjs` 的一条断言消息 | 用例失败时会被打印 |

`SCHEMA_SQL` 那三条**改它们不改行为**，已查清：`_required_session_columns()` 把
这段 SQL 喂给 sqlite 再 `PRAGMA table_info` 读回来，读的是**解析后的列**，不是原文。

**为什么保留**：因为判据本身的可信度比这三条历史值钱。

v0.15 阶段 6 造了一张网，断言「相对 HEAD 的每一处改动都落在注释里」。那张网靠一条简明
的规则活着：**值字符串不是注释**，判法是看引号前面有没有 `=`。

一旦开口子说"值字符串里的注释也能改"，那张网就要开始分辨"这条值字符串里的注释算不
算"。而能分辨的那一天，它就不再是一条机械判据了。它退化成一个需要人来判的东西，而需要
人判的东西在忙碌的提交里会被跳过。

**代价（如实写）**：

- `sqlite3 .schema` 会看到那三句历史。读者极少（直接开库的人）。
- 面板上那一行 `0.7 之前的旧分区` **用户看得到**。这一条代价最大。
- 断言消息只在用例失败时出现。

**要清的话，另开一条有名字的口子**：把这三处逐条列进一个名单，而不是放宽「注释」的
定义。名单是可以数清、可以复核的；放宽定义不行。

### 保留 ⑯ — 「＋ 另开一份」会把旧那一份删掉（**保留现状**）

**位置**：`client/src/main/index.js` 的 `app:setWorkspaceRef`；面板上插件块那一格。

**是什么**：在插件块上把某个插件换到另一份数据、而旧那一份没有别的工作区指着、也没有
活会话拿着时，旧那一份会被 `pruneSpaces` 收掉。它的浏览器存储（登录状态、窗口布局）
与插件写在磁盘上的文件一起没。界面会先弹一个确认框把那句话说全，但不可逆。

这不是额外做的事，是模型的直接后果：「引用表是唯一的所有权凭据」，引用没了那一份就归
零。想改成"留着"的话，得给数据另开一条回收路径，否则它会永远攒着，而用户没有任何入口
把一份没人引用的数据删掉。

**用户 2026-10-09 拍板**：「保留现状，回收就行」。

**代价（如实写）**：用户按「＋ 另开一份（从空白开始）」这个动作时，读到的是一次
"换一份"；实际后果还包含"把旧的删掉"。确认框说了这件事，但**动作的名字没说**。

### 保留 ⑰ — 插件改了口径之后，它旧的那一份**引用**没人清

**位置**：`client/src/main/config.js` 的 `refs`；`client/src/main/index.js` 的
`app:setWorkspaceRef` 与 `pluginBlock`。

**是什么**：一个已装好的插件把清单里的端口个数从 1 改成 0（或者改了共享组），
工作区那张引用表里属于它的旧格子**仍然指着旧那一份**。而：

- `pluginData.needsSpace(plugin)` 现在是假，于是界面**不再画**那一格（`p.ports > 0` 才画），
  用户没有入口把它改掉；`app:setWorkspaceRef` 对这类插件直接拒（"它没有『用哪一份数据』
  这回事"）。
- 那一格还在，于是 `pruneSpaces` 眼里它"被引用着"，于是**永远不会被收**。

于是留下的是**配置里的两行**（`workspaces[].refs` 的一格 + `spaces[]` 的一条），
以及映射图右列**一直挂着的一个数据节点**（还标着"1 个工作区"）。

**磁盘那一半不在此列**：它算不出"该有的"（`ports: 0` 的插件不进那张表），于是判成
`orphan`，于是下一次打开客户端的那一次对账会把它清掉，并留一行。分区那一半同理。

**为什么这次不修**：清那一格要回答"什么时候算改了口径"。那要么在每个插件的数据上加
一格"最后一次声明的端口个数"（把身份从推导变成记录，与 §五 保留 ⑫ 拒绝的那条路同源），
要么在每次插件更新后扫一遍全部工作区（一处更新牵动全表）。两样都比留下的那两行贵。

**它够不着灾难**：收不掉的是两条配置，不是用户的数据。

### 保留 ⑱ — 家目录不要求私有（只保证 `.slurmate` 及其子目录）

**位置**：`cluster/slurmate-sessiond` 的 `check_private_dir_chain()` 两个调用点
（`load_session_file()` 与 `op_job_log()` 里的日志目录链）。

**是什么**：目录链的检查从 `.slurmate` 开始，**不含家目录**。`.slurmate`、
`.slurmate/sessions`、`.slurmate/logs` 仍然要求属主是本人或 root、组/其他不可写。

**为什么**：家目录归用户处置。站点的缺省可能是 `0775`（组是用户自己的私有组），
要求用户为了本系统去改家目录，是拿走他对自家目录的处置权。用户 2026-10-18 的原话：
「用户的家目录你不能严格要求，用户有自己处置的权利，你要保证也只能保证 `.slurmate`
这个文件夹及其子文件夹的权限」。

**可以这么做的依据**：会话文件自己还要求属主、`0600`、硬链接数为 1；
`.slurmate` 与子目录要求属主与模式。家目录可写时，同组的另一个人能改名
`.slurmate`（拒绝服务），但替换不了里面的内容 —— 目录与文件那几项检查挡着。

**代价如实记**：同组攻击者可以让登记失败（改名或删除 `.slurmate`），会话最终
`enroll_timeout` 并被取消。接受它，因为另一边是用户对自己家目录的处置权。

**产出那一侧的保证**：客户端连上站点时建出并 `chmod 700` 那三格；作业脚本的兜底
同样做一次。`mkdir -p` 只对新建生效，所以 `chmod` 是必须的那一半。
用例：`cluster/test-sessiond-logic.py` 第 7 节 —— 家目录 `0775` 时登记照常通过，
而 `.slurmate/sessions` 组可写仍然被拒。
