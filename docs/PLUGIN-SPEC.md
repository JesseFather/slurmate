# Slurmate 插件规范

**规范版本：1**

---

## 0. 关于本规范

本规范定义一个 **Slurmate 插件**是什么：它的身份、它的包格式、以及三种实现
（打包器、客户端、分发端）各自**必须**做什么。

**它是契约，不是说明。** 任何人可以照着它写一个插件、一个打包器，或者一个能
装这些包的客户端，而不需要读本仓库的任何一行代码。

### 0.1 规范性措辞

| 措辞 | 含义 |
|---|---|
| **必须** / **禁止** | 规范要求。不满足即不合规 |
| **应当** / **不应当** | 有理由的推荐。偏离要有说得出的理由 |
| **可以** | 真正可选的 |

### 0.2 三种角色

| 角色 | 做什么 | 本规范的哪些节约束它 |
|---|---|---|
| **打包器** | 把一棵源码树做成一个包 | §2、§3、§4.1 |
| **客户端** | 装包、加载插件、跑插件 | §4.3、§5 |
| **分发端** | 把包送到客户端 | §6 |

同一个程序可以是多种角色（本仓库的打包器也是插件作者用的工具）。

### 0.3 本规范不写实现进度

★ **本规范的正文里没有"做完了没有"这一栏，这是有意的。**

一份把实现进度写进正文的规范，会让读者把**承诺**读成**现状** ——
而"文件里写着、实际什么也没发生"正是这套东西最想消灭的一类问题。
每种实现各自记自己的进度（README、缺陷账本），**不写在这里**。

### 0.4 怎么改一条

**不能"顺手改"。** 要改，得**先证明它对应的那条符合性用例是错的** ——
而不是先改实现、再改用例。

★ 一条要求被改成永远通过，就是它被废掉的时刻，而那时候**没有人会注意到**。
所以维护本规范的唯一纪律是：

> **用例红了，先假设是实现错了。**

**一条要求 = 一条「改坏了它就会红」的符合性用例。** 挂不上用例的要求不进本规范。

## 1. 术语

- **插件（plugin）** —— 一种服务。一个会话提供哪种服务，就由哪个插件负责接起来。
- **包（package）** —— 插件的分发单位，一个文件。见 §3。
- **负载（payload）** —— 包里装的那棵树。包里除负载之外只有信封头。
- **清单（manifest）** —— 负载里的 `plugin.json`，声明插件的身份与能力。
- **构件（artifact）** —— 一份具体的内容，由内容摘要标识。见 §3.4。
- **内容摘要（content digest）** —— 内容的规范哈希，判"是不是同一份构件"。见 §3.4。
- **分身（fork）** —— 从一份已有插件派生出来、**内容不同**的一份新插件。见 §2.4。

## 2. 身份

### 2.1 id

一个插件**必须**有一个 `id`：一个 26 字符的 ULID（Crockford base32，
字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`，前 10 字符是 48 位毫秒时间戳，
后 16 字符是 80 位密码学随机）。

- **只有打包器可以铸 id**，且只在源码树里没有合法 id 时铸一次。**客户端与分发端
  禁止铸 id**，只读。
- 打包器铸出 id 之后**必须**把它写回源码树（`plugin.json`），使这棵树此后带着
  同一个 id。写回**禁止**用字符串替换实现：**必须**解析 JSON、只改 `id` 一个键、
  再写回，并**应当**保持原有的缩进与键序 —— 写回前后的差异**应当**只有这一处。
- **应当**拒绝在源码树不干净时铸 id（写回会弄脏它），并提示作者先提交。
- 打包器**禁止**替作者提交版本控制 —— 那一步由人做。

> **为什么**：`id` 是「会在用户工作站上跑的那段代码」的身份，而客户端的同意台账
> 按 `id@版本` 记（§5.2）。允许第二个地方铸 id，就等于允许同一个插件有两个身份，
> 而"一份内容、多份引用"整条规则建立在"同一个 id 就是同一个构件"上。
>
> 写回要保 diff 最小，是因为**打包顺手重排源码树**会让这个工具没人敢用。

### 2.2 名字不是身份

- 短名 `name`（匹配 `^[a-z][a-z0-9-]{0,31}$`）与 `displayName`（非空字符串）
  **可以**随时修改。
- 短名**必须**在**单个分发端内**唯一。它**不**需要全球唯一。
- 名字、以及插件目录的目录名，**禁止**参与任何判定。

> **为什么**：同一个插件被两个分发端分发时能被认出来是同一个，靠的是 id 相同；
> 两个分发端各写一个同名插件时能被分开，靠的是 id 不同。**名字做不到这两件事。**

### 2.3 版本号

`version` **必须**匹配 `major.minor.patch`：三段十进制数字，点分隔。

1. **禁止**前导零。每一段**必须**是 `0`，或不以 `0` 开头的十进制串。
2. `minor` 与 `patch` **必须** ∈ `0..255`。`major` **可以**任意大。
   超出上界时**必须**进位到上一位（`1.255.255` 之后是 `2.0.0`）。
3. **比较规则**：逐段比较，**先比十进制字符串的长度，长度相同再比字典序**。
   **禁止**把段转成有界的机器整数再比较。

> **为什么**：前导零会造出**同一个版本的两个字符串**（`1.007.0` 与 `1.7.0`
> 数值相等、字符串不等），而按 `(id, 版本)` 查表是**精确字符串比对** ——
> 于是同一个插件会出现两个槽位、两次同意、两份目录，而"升级"会被判成"没升"。
>
> 不转机器整数是因为：IEEE 754 双精度在 2^53 以上失精，会让 `9007199254740993.0.0`
> 与 `…992.0.0` 判等，而任意精度整数不会 —— **两侧于是不一致**。按字符串比与
> 数值序完全一致，且不依赖任何整数精度，这才让第 2 条里那个"`major` 可以任意大"
> 真的成立。
>
> `0..255` 的价值是挡住把日期或提交号塞进版本号。版本号是 §2.4 的**唯一执行
> 手段**：它要是能随手造新值，"改了内容就升版本号"就退化成"改了内容就换个号"。

### 2.4 一个 `(id, 版本)` 只有一份内容

- 内容**不可变**。**改了内容的任何字节就必须升版本号**。
- 同一个 `(id, 版本)` 下出现两份内容不同的构件时，客户端**必须**两个都不加载
  并报错，**禁止**挑一个。

> **为什么**：这是池模型唯一的危险处。取错的那一方会**静默地跑另一个插件的代码**，
> 而用户完全看不出来。宁可让这个插件暂时不可用 —— 那种失败是**看得见**的。

### 2.5 分身必须铸新 id

- 从一份已有插件派生、且**内容不同**的插件，**必须**铸一个**新的 `id`**。
- 判据是机械的：包的签名者与本机台账里这个 `id` 的签名者不同 ⇒ **拒绝**（§4.3）。
- **禁止**在一棵树带有 `id` 的情况下、无法确认它是同一个作者时，静默换 id 或
  静默沿用 id —— 打包器**必须**停下来，把两种可能（真分身 / 换了钥匙）
  连同各自的后果说清，由人决定。

> **为什么**：分身沿用 id 会让两个不同的东西抢同一个 `(id, 版本)`（§2.4），
> 后果是**一个分发端的分身能把另一个分发端正在用的插件弄坏** —— 这是"会给插件
> 起个名就能发动"的跨端拒绝服务。
>
> 停下来问而不是自动铸新 id，是因为"真分身"与"我丢了自己的钥匙"**后果相反**：
> 后者铸新 id 意味着所有已同意的客户端重新同意、正在跑的会话变成"未知服务"。
> 那是把"我丢了钥匙"变成"我换了个插件"，**不能替作者选**。

## 3. 包

### 3.1 一个插件是一个包

一个插件**必须**以单个文件（一个包）分发。包里**必须**同时容纳作业侧与客户端侧，
基座按需激活 —— 客户端不读作业侧，分发端不读客户端侧。

包**必须**能表达"某一侧为空"：只有声明式一侧、或只有作业侧的插件是合法的。

> **为什么**：作业侧与客户端侧是**配套的**。分开发就等于让"两半版本不一致"
> 成为可能，而"两边配套"正是分发要解决的问题。

### 3.2 负载里只允许普通文件

包的信封头**必须**记录一个格式版本号（`format`，本规范版本 1 即 `1`）。

负载里**禁止**出现除普通文件之外的任何条目：

- **禁止**目录条目。目录结构**必须**由文件路径里的 `/` 表达。
- **禁止**符号链接、硬链接、命名管道、设备节点、套接字。
- **禁止**空目录 —— 它没有表达形式，因此不可能出现。
- 所有文件的权限位**必须**由格式规定，不随包携带。版本 1 规定为 `0644`。

> **为什么**：这是 §3.4 那条摘要公式成立的前提。磁盘上的一棵树可以含符号链接、
> 空目录、各种权限位，每一种都是一次"摘要相同而内容不同"的机会 ——
> 比如 `client/x.js` 是指向 `../y.js` 的链接，与它是"内容恰好为 `../y.js` 的
> 普通文件"，两者行为天差地别（一个加载 `y.js`，一个导出一个字符串），
> 而摘要可以完全相同。**格式不允许这些东西，问题就不存在。**
>
> 权限位定死 `0644` 不疼：作业侧脚本是被内容拼进作业脚本的，权限位不参与任何事；
> 客户端侧代码是被加载器读的，也不需要可执行位。
>
> ★ **要放宽的正确方式是"在清单里声明"**（例如声明"这个路径要 `0755`"），
> **不是把权限位还给文件系统** —— 因为清单是一份文件、在负载里，
> 所以"需要可执行"仍然是内容的一部分，仍然进摘要。

### 3.3 路径规则

负载里每一条路径**必须**是以 `/` 分隔的**相对**路径，并且：

- **禁止**为空、**禁止**含 NUL、**禁止**含反斜杠（**禁止**把 `\` 翻译成 `/` ——
  一侧翻译而另一侧不翻译就是歧义的来源）；
- **禁止**以 `/` 开头、以 `/` 结尾、含连续的两个 `/`；
- 每一段**禁止**为空、为 `.`、为 `..`；每段**必须** ≤ 255 字节；
- 段数**必须**不超过深度上限（版本 1 为 8）；
- **禁止**出现下列跳过集合里的任何一段（逐字，区分大小写）：
  `.git`、`.github`、`.gitignore`、`.gitattributes`、`node_modules`；
- **禁止** Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`–`COM9`/`LPT1`–`LPT9`，
  不区分大小写，含带扩展名的形式）、**禁止** Windows 上不合法的字符
  （`: * ? " < > |`）、**禁止**任何一段以空格或点结尾；
- 同一次打包里，两条路径**禁止**只差大小写。

任何一条不满足 ⇒ 收包方**必须**拒绝**整个包**（不是拒绝那一条）。

> **为什么**：收包方会对同一条路径**再判一遍** —— 发包方可能被换过，
> "对面已经判过"不构成省略的理由。而"一个说不清的清单"本身就是"这份东西不能信"。
>
> 大小写那一条的坑在**落盘之后**：macOS 与 Windows 的文件系统不区分大小写，
> 两条只差大小写的路径会互相覆盖，而摘要是**写入之后的磁盘上**算的 ——
> 于是用户同意的是另一棵树。

### 3.4 内容摘要

**内容摘要**是判"是不是同一份构件"的唯一判据，**必须**按下面的公式计算：

```
内容摘要 = sha256(
    对全部文件按路径排序（逐字节比较，与语言/区域设置无关）之后，
    依次拼接： 路径的 UTF-8 字节 ‖ 0x00 ‖ sha256(该文件内容的字节) 的十六进制小写 ‖ 0x0A
)  的十六进制小写
```

**禁止**把任何别的东西拌进这个哈希：**禁止**包含容器字节、信封头、压缩参数、
打包器版本、时间戳、作者身份、目录名。作者写在清单里的字段**会**进摘要 ——
但仅仅因为清单是一份文件。

> **为什么**：如果这个值跟打包器有关（信封格式、时间戳、压缩参数），"同一份内容"
> 就会算出两个身份，而 `(id, 版本)` 只有一个槽位 —— 按 §2.4，两个都不加载。
> 于是 §2.2 要保的那件事（同一个插件被两个分发端分发 ⇒ 识别为同一个）会变成坏事。

### 3.5 打包的输入是一个提交，不是工作树

- 打包器**必须**以版本控制里的一个**提交**为输入，**禁止**以工作树为输入；
  工作树不干净时**必须**拒绝打包。
- 对同一个输入，打包器**必须**产出**逐字节相同**的包。

> **为什么**："同一份源码"需要一个精确的定义，否则工作树里多一个编辑器临时文件
> 就是"两个结果"—— 而那是打包器再确定也救不了的。从提交打包时，可复现性由版本
> 控制系统保证（例如 `git archive` 对同一个 tree 的输出是确定的：uid/gid 写 `0`、
> mtime 取提交时间），不需要自己写规格去守。

### 3.6 负载等于源码树

包的信封头**禁止**对负载做任何变换、混淆、加密或隐藏。解包得到的树**必须**
与源码树里那棵树**逐字节相同**。

> **为什么**：这一条就是「不混淆、不加密、没有隐藏字节」那句话的**判据形式** ——
> 那句话本身钉不住，这一条钉得住：任何混淆、加密、藏字节都会让这条红。
>
> 而这个性质是**结构性**的，不是锦上添花：客户端**必须**让用户在装之前能读到
> 将要在这台机器上执行的东西（§5.2），一个装包的实现**必须**让运维能读到将要
> 分发给所有人的东西。一旦不透明，同意就变成走过场 —— 而"让用户以为自己在同意 A
> 而实际同意了 B"正是这套东西要防的事。

## 4. 签名

### 4.1 密钥属于插件

签名是**可以**选的：包**可以**不带签名。但一旦带，本节全部适用。

- 一个插件**应当**对应**一把**签名密钥。私钥属于**这个插件**，不属于某台机器 ——
  换机器的方式是复制私钥。
- **丢了私钥** ⇒ **只能给这个插件铸一个新 id**（§2.5），所有已同意的客户端
  重新同意一遍。
- 包的签名**必须**带公钥（自签名即可，本规范**不**要求任何证书颁发机构或注册表）。
- 公钥**必须**以可复制的形式暴露给用户（指纹），以便人工核对。

> **为什么**：私钥是"血统"的载体，丢了就是血统断了 —— 这是**诚实的结果**，
> 不是需要兜掉的失败。★ 而正因为这个后果明确、不致命，**密钥管理从"绝不能出错"
> 降级成"最好别出错"**，这才让签名方案能够落地。
>
> 私钥**应当**备份 —— 这是本节唯一的可操作建议。

### 4.2 签名覆盖内容摘要

签名**必须**覆盖 §3.4 的内容摘要。**禁止**覆盖信封字节，也**禁止**覆盖包文件的
整体哈希。

> **为什么**：信封的格式会演进（今天加签名槽，明天加别的）。签名盖在信封字节上，
> 每动一次信封所有签名全废，而且"同一份内容、两个包"要两个签名。

### 4.3 钉公钥

- 客户端第一次接受某个 `id` 的构件时，**必须**记下它的签名公钥（首次即信任）。
- 此后任何自报同一个 `id` 的包，**必须**核对其签名者是否为**同一把**公钥；
  不同 ⇒ **必须拒绝**，并**必须**把两把公钥的指纹都说出来。
- 内容**没变**而签名者**变了** ⇒ **必须拒绝**。

> **为什么**：这是"分身"唯一能被机械判出来的地方（§2.5）。一致性判据判不了它 ——
> 分身升个版本号，在一致性台账上就是一条**全新的正常条目**，用户看到的是一次
> 普通的"要不要装新版本"。
>
> ★ **一致性判据与认证判据不是一回事，禁止合并**：摘要回答"还是不是我同意的那一份"，
> 签名回答"是不是我以为的那个人"。合并会得到一个看起来更强的检查，而它挡不住
> "第一次给的就是坏的"—— 摘要跟内容同行、由同一个工具写下，它挡得住事后偷换，
> 挡不住首次欺骗。
>
> ★ 首次即信任的**固有弱点**：全新的、从没见过这个 `id` 的客户端会被先到的包
> 钉住。这条**没有**本地解法；本规范不假装有。

## 5. 客户端的义务

### 5.1 池子只有一个写入者

- 插件进池**必须**只经由"安装一个包"这一个动作。
- 往池目录里手工放置内容，**必须**不产生任何效果：那些内容**禁止**出现在插件
  列表里、**禁止**被加载，**禁止**被当作"某个分发端要给你装的东西"呈现给用户。
- 客户端**必须**能区分并分别陈述这三种"你没有这个插件"：① 分发端不支持分发；
  ② 分发端支持但这一份没下来（给出原因）；③ 本机有一份，但**没有任何分发端报过它**。
  第③种**禁止**复用①②的措辞。

> **为什么**：只要"往文件夹里拷"还能工作，池子里的东西就与台账可能不同步，而台账
> 是同意、回收、会话解析三件事的**共同依据**。让它**不成立**，比拦着它便宜。
>
> 三种情况必须分开说，是因为含糊的措辞会让用户以为插件没装上、跑去重新同步 ——
> 而同步本来就已经成功了。

### 5.2 同意闸

- 装一个带客户端代码的插件之前，**必须**要用户点一次同意。
- 台账**必须**以 `(id, 版本)` 为键、以**全长内容摘要**为值。**禁止**用截断后的摘要
  做判据（截断只可以用于显示）。
- **禁止**给任何一类插件开免同意的口子。
- **应当**先写台账、后激活插件（次序颠倒会让"同意过了"在崩溃后丢失，导致反复问，
  或者被实现者"修"成默认同意）。
- 同意界面**必须**说清用户在同意的到底是什么：至少包括——这段代码**会在这台机器上
  以完整权限执行**、它来自哪里、以及内容与上一次相比变了什么。
- 台账条目**必须**绑定摘要值：回写之前**必须**再核一次当前摘要与用户看到的那个
  值相同。

> **为什么**：一个恶意的清单也在往这台机器上放东西（一个登录契约可以让客户端往
> 某个地址提交一个口令 —— 那是**数据**不是代码，但仍然是分发端的指令）。
> 而**规则一有分支，绕过它的路就会长出来**。

### 5.3 池子的写、删除与撤回

- 删掉本机那一个构件 ⇒ 台账里对应的那条**必须**一并消失 ⇒ 下一次对账**必须**
  重新走一遍同意闸。
- 这一条**禁止**被实现成"静默装回来"。也不得在文案里**断言是用户删的** ——
  客户端不知道原因，它只知道"不在了"。

> **为什么**：删除是一个**没说出口**的决定，而对账不认识它。若只删内容、台账那条
> 还在，下次同步会按"摘要与台账相符"**静默装回来、一个字都不问** ——
> 那不是"当作从来没有过"，那是"用户想让它消失，它自己回来了"。

## 6. 分发端的义务

### 6.1 绝不谎报成功

分发端**禁止**在任何一个字节没送达或与声明不符时报告成功。报告成功时，
客户端磁盘上的内容**必须**按字节就是分发端那一份。

**禁止**截断：单份文件超出上限时**必须**明确失败。

### 6.2 判据是能力缺席，不是这次失败

- "这个分发端支不支持分发"**必须**由一个**协议事实**判定（响应里有没有文件清单），
  **禁止**由"这次下载成不成功"判定。
- 下载失败时，**禁止**回退到本机自装的任何一份。

> **为什么**：把两者合并，等于给一个能让下载失败的人（断流、丢包、中间人）一个
> 把用户降级到旧本地副本的开关 —— 攻击成本从"改内容"降到"让下载失败"，
> 而后者便宜得多。**这是这套东西里最重要的一条安全边界。**

### 6.3 不知道谁在引用时，什么都不删

- 引用表读不出来或写不下去时，分发端**必须**只报告、**禁止**回收任何内容。
- 写引用表**必须**在回收之前。

> **为什么**：读不到引用表时，池里每个构件的引用数都算 0，按规则会把整个池清空 ——
> 那是"因为读不到一张表而删掉用户的东西"。而写在回收之后，会按一份**旧**引用表
> 动手，删掉另一个分发端还要的构件 —— **那是唯一会真正丢数据的地方。**

### 6.4 同一个分发端内禁止 id 并存

- 同一个分发端里，两个插件**禁止**自报同一个 `id`。检测到 ⇒ **必须**拒绝部署，
  并说清是哪两个、各自的内容摘要是什么。
- 这个检查**必须**落在分发端（有权威、且在发货之前的那一侧），**禁止**指望客户端兜。

> **为什么**：作业侧产物按 `id` 命名（一个插件一份），两个插件同 id ⇒
> **后写的覆盖先写的**，而那是**静默**的。
>
> ★ 它拦不住**跨分发端**的那一种（分身在一个端、原件在另一个端）—— 那一种归 §4.3。

下面这些**可以**演进，改它们不动本规范。列出来是为了让规范有边界 ——
一份什么都是规范的东西，等于没有规范。

- 暂存目录的布局与命名、对账锁的实现、退避重试的次数
- 信封头里字段的**命名**（但字段的**语义**属于本规范）

- 包的容器格式（tar / zip / 自造）—— 只要满足 §3.2、§3.4、§3.5、§3.6
- 打包器放在哪个目录、用什么语言写、命令行选项叫什么
- 引用计数与引用表的具体形状
- 三种角色的程序如何部署、装在哪、谁运维
