# Slurmate 插件规范

**规范版本：1**

---

## 0. 这份规范写给谁

**写给一个打算写插件的人。**

基座 —— 客户端、守护进程、部署脚本 —— 是**一份，且只有这一份**。这份规范
**不**承诺"照着它就能另写一个客户端"：没有那个需要，也没有那个打算。

它给你的是两样东西：

| | 在哪 | 是什么 |
|---|---|---|
| **你必须做什么** | §2 – §4 | 你的插件、你的打包器要满足这些，才能被装上、被分发 |
| **你可以依赖什么** | §5 – §6 | 基座会保证什么。写在这里是因为**你需要知道**（所以哪些事不用你自己想办法），**不是**因为它们是你的义务 |

★ 两者**都是可断言的**：§2–§4 的每一条都有打包器或收包方上的符合性用例；
§5–§6 的每一条都有基座自己的用例。**一份读起来像承诺、实际没人守的保证，
比一条明写的义务更糟。**

### 0.1 规范性措辞

| 措辞 | 含义 |
|---|---|
| **必须** / **禁止** | 规范要求。不满足即不合规 |
| **应当** / **不应当** | 有理由的推荐。偏离要有说得出的理由 |
| **可以** | 真正可选的 |

### 0.2 这份规范里不写"做完了没有"

★ **正文里没有实现进度这一栏，这是有意的。**

一份把实现进度写进正文的规范，会让读者把**承诺**读成**现状** ——
而"文件里写着、实际什么也没发生"正是这套东西最想消灭的一类问题。
进度各自记在各实现自己的 README 与缺陷账本里，不在这里。

### 0.3 这份规范自己怎么维护

★ **这一节写给维护这份规范的人**，放在这里是为了让你知道这份契约有多稳。

> **一条要求 = 一条「改坏了它就会红」的符合性用例。**

挂不上用例的要求不进这份规范 —— 它会退化成一句谁都不看的愿望。
所以**不能"顺手改"**：要改一条，得先证明它对应的用例是错的，
而不是先改实现、再改用例。

★ 一条要求被改成永远通过，就是它被废掉的时刻，而那时候**没有人会注意到**。
唯一的维护纪律是：

> **用例红了，先假设是实现错了。**

## 1. 术语

- **插件（plugin）** —— 一种服务。一个会话提供哪种服务，就由哪个插件负责接起来。
- **包（package）** —— 插件的分发单位，一个文件（`.splug`）。见 §3。
- **信封（envelope）** —— 包里除负载之外的全部字节：头 + 记录表 + 签名块。
  字节布局见附录 A。
- **负载（payload）** —— 包里装的那棵树。包里除信封之外只有负载。
- **清单（manifest）** —— 负载里的 `plugin.json`，声明插件的身份与能力。
- **构件（artifact）** —— 一份具体的内容，由内容摘要标识。见 §3.4。
- **内容摘要（content digest）** —— 内容的规范哈希，判"是不是同一份构件"。见 §3.4。
- **分身（fork）** —— 从一份已有插件派生出来、**内容不同**的一份新插件。见 §2.5。
- **血统表（lineage record）** —— 跟着源码树走的一份小文件，记着"这个 id 是谁签的"。
  见 §2.5。

## 2. 你必须做什么 · 身份

### 2.1 id

一个插件**必须**有一个 `id`：一个 26 字符的 ULID（Crockford base32，
字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`；前 10 字符是 48 位毫秒时间戳，
后 16 字符是 80 位密码学随机）。

- **铸 id 是你的打包器的活**：源码树里没有合法 id 时铸一次，此后**永不改变**。
  基座不铸 id，只读它。
- 铸出之后**必须**把它写回源码树（`plugin.json`），使这棵树此后带着同一个 id。
- 写回**禁止**用字符串替换实现：**必须**是一次**插入**（在对象里按原有缩进插入
  `"id": …` 这一行），**禁止**把整份 JSON 解析再序列化回去 —— 那会重排键序、
  丢掉 `\u` 转义与数字写法，于是"只改了一个键"对任何一份真实的清单都是假的。
- 写回会弄脏源码树，所以**应当**在写回之后停下来提示你提交，**禁止**替你提交。
- **应当**拒绝在源码树不干净时铸 id。

> **为什么**：`id` 是「会在用户工作站上跑的那段代码」的身份，而同意台账按
> `id@版本` 记（§5.2）。允许第二个地方铸 id，就等于允许同一个插件有两个身份，
> 而"一份内容、多份引用"整条规则建立在"同一个 id 就是同一个构件"上。
>
> 写回要保 diff 最小，是因为**打包顺手重排源码树**会让这个工具没人敢用。

### 2.2 名字不是身份

- 短名 `name`（**必须**匹配 `^[a-z][a-z0-9-]{0,31}$`）与 `displayName`
  （**必须**是非空字符串）**可以**随时修改。
- 短名**必须**在**单个站点内**唯一。它**不**需要全球唯一。
- 名字、以及插件目录的目录名，**禁止**参与任何判定。

> **为什么**：同一个插件被两个站点分发时能被认出来是同一个，靠的是 id 相同；
> 两个站点各写一个同名插件时能被分开，靠的是 id 不同。**名字做不到这两件事。**
>
> 这也意味着你可以随便改名、随便把仓库目录叫成什么，都不会让已装的用户出问题。

### 2.3 版本号

**插件版本**（这一节的前半段说的都是清单里的 `version`）**必须**匹配
`major.minor.patch`：三段十进制数字，点分隔。

1. **禁止**前导零。每一段**必须**是 `0`，或不以 `0` 开头的十进制串。
2. `minor` 与 `patch` **必须** ∈ `0..255`。`major` **可以**任意大。
   超出上界时**必须**进位到上一位（`1.255.255` 之后是 `2.0.0`）。
3. **比较规则**：逐段比较，**先比十进制字符串的长度，长度相同再比字典序**。
   **禁止**把段转成有界的机器整数再比较。

> **为什么**：前导零会造出**同一个版本的两个字符串**（`1.007.0` 与 `1.7.0`
> 数值相等、字符串不等），而按 `(id, 版本)` 查表是**精确字符串比对** ——
> 于是同一个插件会出现两个槽位、两次同意、两份目录，而"升级"会被判成"没升"。
>
> 不转机器整数是因为：IEEE 754 双精度在 2^53 以上失精，会让
> `9007199254740993.0.0` 与 `…992.0.0` 判等，而任意精度整数不会 ——
> **两侧于是不一致**。按字符串比与数值序完全一致、不依赖任何整数精度，
> 这才让第 2 条里那个"`major` 可以任意大"真的成立。
>
> `0..255` 的价值是挡住把日期或提交号塞进版本号。**版本号是 §2.4 的唯一执行手段**：
> 它要是能随手造新值，"改了内容就升版本号"就退化成"改了内容就换个号"。

★ **校验，不归一化。** 打包器与收包方**只判合不合上面三条**，
**禁止**把不合规的版本号**改写**成合规的（`1.256.0` 不许变成 `2.0.0`，
`1.007.0` 不许变成 `1.7.0`）—— 那是**静默改版本号**，与 §2.4 直接冲突：
两侧算出来的 `(id, 版本)` 会不是同一个键，而"升级"会被判成"没升"。
不合规就是不合规：**拒绝，并说出来**。

#### 2.3.1 你还会写第二个版本号：框架版本

清单里还有一个 `engines.slurmate`。它说的**不是你的插件**，而是**跑它的那个
基座** —— 客户端、守护进程、协议是**同一个号**（下面叫它**框架版本**）。

- 框架版本**必须**是 `major.minor`：**两段**十进制数字。
- 三条纪律与上面完全一样：**禁止**前导零、`minor` ∈ `0..255`、
  **逐段按十进制字符串比较**。只是没有 `patch` 那一段。
- `engines.slurmate` **必须**是一个空格分隔的比较式合取：`>=` `>` `<=` `<` `=`
  之一紧接一个框架版本，如 `>=0.5`、`>=0.5 <0.7`。
- **禁止**写三段（`>=0.5.0` 是一个**看不懂的片段**，不是"`>=0.5`"）；
  **禁止** `^`、`~`、`||`、逗号；两段之间**禁止**空格（`>= 0.5` 同样看不懂）。
- 整条范围**全部满足**才算通过；不满足、看不懂、或者是空的 ⇒ 这个插件
  **不被加载**。

> **为什么**：两套版本号长得像，但**段数不同**，而写错段数的后果是确定的 ——
> **拒绝加载**，不是"宽松地理解成对的那个"。理由与上面第 1 条是同一个：`0.5`
> 与 `0.5.0` 是同一个意思的两种写法，而任何一处"我以为它懂"的地方，最终都表现
> 为"升级之后我的插件忽然不加载，而报错只说清单不合法"。
>
> ★ 顺带一个后果：框架版本**没有**第三段，所以"补丁级兼容性"在这个字段里表达
> 不出来 —— 需要那个粒度就声明一个更大的范围（`>=0.5 <0.7`）。

### 2.4 一个 `(id, 版本)` 只有一份内容

- 内容**不可变**。**改了内容的任何字节，就必须升版本号。**
- 同一个 `(id, 版本)` 下出现两份内容不同的构件时，收包方会**两个都不加载**并报错。

> **为什么**：取错的那一方会**静默地跑另一个插件的代码**，而用户完全看不出来。
> 宁可让这个插件暂时不可用 —— 那种失败是**看得见**的。
>
> ★ 对你的实际含义：**发出去的版本号不能"回收再改"**。改了东西就发新版本号。

### 2.5 分身必须铸新 id

从一份已有插件派生、且**内容不同**的插件，**必须**铸一个**新的 `id`**。

- 判据是机械的：包的签名者与本机血统表里这个 id 的签名者不同 ⇒ 客户端**拒绝**。
- **禁止**在一棵树带有 `id`、而本机血统表又不认识它时**静默**换 id 或**静默**沿用 id。
  打包器**必须**停下来，把两种可能（真分身 / 换了钥匙）连同各自的后果说清，由你决定。

> **为什么**：分身沿用 id 会让两个不同的东西抢同一个 `(id, 版本)`（§2.4），
> 后果是**一个站点的分身能把另一个站点正在用的插件弄坏** —— 这是"会给插件
> 起个名就能发动"的跨站拒绝服务。
>
> 停下来问而不是自动铸新 id，是因为"真分身"与"我丢了自己的钥匙"**后果相反**：
> 后者铸新 id 意味着所有已同意的用户重新同意、正在跑的会话变成"未知服务"。
> 那是把"我丢了钥匙"变成"我换了个插件"，**不能替你选**。
>
> ★ **血统表跟着源码树走**（**应当**提交进版本控制）：这样别人 clone 下来的树
> 带着它，"这个 id 是谁签的"本地就有答案，手滑的情形全部机械可判。
> 唯一无法机械判的是**血统表被人从树里删掉** —— 那是故意的，不是手滑。
>
> ★ 血统表是插件目录根上的 **`lineage.json`**（`id → 签名者公钥`），**由打包器写**
> —— 它 `init` 时记一条、`keygen` 时把公钥填进去，你**提交**它。**不要手改**：
> 它进负载（它是一份普通文件），所以改它就是改内容，而按 §2.4 那要升版本号。

### 2.6 同一站点里不许两个插件同 id

- 同一个站点里，两个插件**禁止**自报同一个 `id`。犯了 ⇒ **安装会被拒绝**。

> **为什么**：作业侧产物按 `id` 命名（一个插件一份），两个插件同 id ⇒
> **后写的覆盖先写的**，而那是**静默**的。
>
> ★ 它拦不住**跨站点**的那一种（分身在一个站点、原件在另一个站点）——
> 那一种归 §2.5 的签名管。
>
> ★ 这一条本来在"分发端"那一节，现在移到这里：**它是对你的要求，不是基座的保证。**

## 3. 你必须做什么 · 包

### 3.1 一个插件是一个包

一个插件**必须**以单个文件（一个包，`.splug`）分发。包里**必须**同时容纳作业侧
与客户端侧，基座按需激活 —— 客户端不读作业侧，站点不读客户端侧。

包**必须**能表达"某一侧为空"：只有声明式一侧、或只有作业侧的插件是合法的。

> **为什么**：作业侧与客户端侧是**配套的**。分开发就等于让"两半版本不一致"
> 成为可能，而"两边配套"正是分发要解决的问题。

### 3.2 负载里只允许普通文件

包的信封头**必须**记录一个格式版本号（`format`，本规范版本 1 即 `1`）。
★ 信封的**字节布局**在附录 A（规范性）里写死了 —— 那不是"实现细节"，因为
你的打包器要把那个字节序列造出来，而收包方会一个字节一个字节地判它。

负载里**禁止**出现除普通文件之外的任何条目：

- **禁止**目录条目。目录结构**必须**由文件路径里的 `/` 表达。
- **禁止**符号链接、硬链接、命名管道、设备节点、套接字。
- **禁止**空目录 —— 它没有表达形式，因此不可能出现。
- 所有文件的权限位**必须**由格式规定，不随包携带。版本 1 规定为 `0644`。

> **为什么**：这是 §3.4 那条摘要公式成立的前提。磁盘上的一棵树可以含符号链接、
> 空目录、各种权限位，每一种都是一次"摘要相同而内容不同"的机会 ——
> 比如 `client/x.js` 是指向 `../y.js` 的链接，与它是"内容恰好为 `../y.js` 的
> 普通文件"，两者行为天差地别（一个加载 `y.js`，一个导出一个字符串），
> 而摘要可以完全相同。**格式不允许这些东西，问题就不存在。**
>
> 权限位定死 `0644` 不疼：作业侧脚本是被内容拼进作业脚本的，权限位不参与任何事；
> 客户端侧代码是被加载器读的，也不需要可执行位。
>
> ★ **要放宽的正确方式是"在清单里声明"**（例如声明"这个路径要 `0755`"），
> **不是把权限位还给文件系统** —— 因为清单是一份文件、在负载里，
> 所以"需要可执行"仍然是内容的一部分，仍然进摘要。

### 3.3 路径规则

负载里每一条路径**必须**是以 `/` 分隔的**相对**路径，并且：

- **禁止**为空、**禁止**含 NUL、**禁止**含反斜杠（**禁止**把 `\` 翻译成 `/` ——
  一侧翻译而另一侧不翻译就是歧义的来源）；
- **禁止**以 `/` 开头、以 `/` 结尾、含连续的两个 `/`；
- 每一段**禁止**为空、为 `.`、为 `..`；每段**必须** ≤ 255 字节；
- 段数**必须**不超过深度上限（版本 1 为 8）；
- **禁止**出现下列跳过集合里的任何一段（逐字，区分大小写）：
  `.git`、`.github`、`.gitignore`、`.gitattributes`、`node_modules`；
- **禁止** Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`–`COM9`/`LPT1`–`LPT9`，
  不区分大小写，含带扩展名的形式）、**禁止** Windows 上不合法的字符
  （`: * ? " < > |`）、**禁止**任何一段以空格或点结尾；
- 每一条路径**必须**是合法的 UTF-8 字节序列；
- 同一次打包里，两条路径**禁止**只差大小写，**也禁止完全相同**。

任何一条不满足 ⇒ **拒绝整个包**（不是拒绝那一条）。

★ **"只差大小写"的判据是只折叠 `A`–`Z`。** 禁止用"全 Unicode 的大小写折叠"
（JS 的 `toLowerCase()`、Python 的 `str.lower()`）—— 它们会把 `İ`（U+0130）
与 `i`、`K`（U+212A KELVIN）与 `k` 折到一起。这是一条**拒绝**规则，口径不一致
就意味着**同一个包在一台机器上装得上、在另一台上装不上**，而报错里一个字都不会
提到大小写。

★ **"完全相同"那半条是补上的。** 只禁"只差大小写"时，两条**逐字相同**的路径是
合法的 —— 而它们带着两份不同的内容时，内容摘要**有定义**（它按路径排序后拼接），
可**解出来的树是歧义的**（哪一个字节该落到那个路径上？）。

★ **"路径必须合法 UTF-8"那半条也是补上的。** 不合法的字节会被解码器**悄悄换成**
`U+FFFD`，于是摘要算的是一个被替换过的字符串 —— 两端算的不是同一份东西。

> **为什么**：收包方会对同一条路径**再判一遍** —— 发包方可能被换过，
> "对面已经判过"不构成省略的理由。而"一个说不清的清单"本身就是"这份东西不能信"。
>
> 大小写那一条的坑在**落盘之后**：macOS 与 Windows 的文件系统不区分大小写，
> 两条只差大小写的路径会互相覆盖，而摘要是**写入之后的磁盘上**算的 ——
> 于是用户同意的是另一棵树。

### 3.4 内容摘要

**内容摘要**是判"是不是同一份构件"的唯一判据，**必须**按下面的公式计算：

```
内容摘要 = sha256(
    对全部文件按路径排序（逐字节比较，与语言/区域设置无关）之后，
    依次拼接： 路径的 UTF-8 字节 ‖ 0x00 ‖ sha256(该文件内容的字节) 的十六进制小写 ‖ 0x0A
)  的十六进制小写
```

**禁止**把任何别的东西拌进这个哈希：**禁止**包含容器字节、信封头、压缩参数、
打包器版本、时间戳、作者身份、目录名。你写在清单里的字段**会**进摘要 ——
但仅仅因为清单是一份文件。

> **为什么**：如果这个值跟打包器有关（信封格式、时间戳、压缩参数），"同一份内容"
> 就会算出两个身份，而 `(id, 版本)` 只有一个槽位 —— 按 §2.4，两个都不加载。
> 于是 §2.2 要保的那件事（同一个插件被两个站点分发 ⇒ 识别为同一个）会变成坏事。
>
> ★ 对你的实际含义：**同一棵树，谁在哪台机器上打包，都必须得到同一个摘要。**
> 这是 §3.5 那条要求的来源。

### 3.5 打包的输入是一个提交，不是工作树

- 打包器**必须**以版本控制里的一个**提交**为输入，**禁止**以工作树为输入；
  工作树不干净时**必须**拒绝打包。
- 对同一个输入，打包器**必须**产出**逐字节相同**的包。

> **为什么**："同一份源码"需要一个精确的定义，否则工作树里多一个编辑器临时文件
> 就是"两个结果"—— 而那是打包器再确定也救不了的。从提交打包时，可复现性由版本
> 控制系统保证（例如 `git archive` 对同一个 tree 的输出是确定的：uid/gid 写 `0`、
> mtime 取提交时间），不需要自己写规格去守。

### 3.6 负载等于源码树

包的信封头**禁止**对负载做任何变换、混淆、加密或隐藏。解包得到的树**必须**
与源码树里那棵树**逐字节相同**。

★ **"源码树里那棵树"指的是过掉跳过集（§3.3）之后的那棵树。** 不这样读的话
这一条与 §3.3 是**字面矛盾**的：真实的源码树几乎总有一份 `.gitignore`，而它是
§3.3 禁止出现的路径 —— 于是"逐字节相同"永远不成立，"少了一份文件"也说不清。
唯一说得通的读法是：**负载 = 源码树减去跳过集**，而**减去的东西必须被说出来**
（打包器要把跳过了什么打出来，不许静默少东西）。

★ **字节取自版本控制里的 blob，不是检出之后的字节**（附录 A.5）。`text=auto`
一类的属性会在检出时改行尾，而 §3.4 要的是"谁在哪台机器上打包都是同一个摘要"。
**也正因为如此，打包**禁止**用 `git archive`** —— 它会读 `.gitattributes` 的
`export-ignore` / `export-subst`，于是**负载能被仓库里一份属性文件改掉**，
而打包的人看不出来。

> **为什么**：这一条就是「不混淆、不加密、没有隐藏字节」那句话的**判据形式** ——
> 那句话本身钉不住，这一条钉得住：任何混淆、加密、藏字节都会让这条红。
>
> 而这**对你自己也有用**：装包的人（站点管理员、以及最终的用户）**能读到**
> 将要在这台机器上执行的东西 —— 一份能被读的插件才有人敢装。

## 4. 你必须做什么 · 签名

### 4.1 密钥属于插件

签名是**可以**选的：包**可以**不带签名。但一旦带，本节全部适用。

- 一个插件**应当**对应**一把**签名密钥。私钥属于**这个插件**，不属于某台机器 ——
  换机器的方式是复制私钥。
- 私钥**禁止**出现在源码树里（也就是**禁止**进版本控制）。它**必须**放在源码树
  之外 —— 树里的东西会被提交、会被分发，而一个提交出去的私钥等于血统当场作废，
  且**没有办法收回来**。
- 包的签名**必须**带公钥（自签名即可，本规范**不**要求任何证书颁发机构或注册表）。
- 公钥**必须**以可复制的形式暴露给用户（指纹），以便人工核对。

> ★ **可操作的建议只有一条：私钥要备份。**
>
> **为什么**：私钥是"血统"的载体，丢了就是血统断了。而 §5 里那条"客户端会钉住
> 你的公钥"意味着**你丢了私钥就不能换一把接着发** —— 老用户会拒绝，
> 你只能给这个插件铸一个新 id（§2.5），让所有人重新同意一遍。
> 这是**诚实的结果**，不是需要兜掉的失败。★ 而正因为这个后果明确、不致命，
> 密钥管理从"绝不能出错"降级成"最好别出错" —— 这才让它是一件可做的事。

### 4.2 签名覆盖内容摘要

签名**必须**覆盖 §3.4 的内容摘要。**禁止**覆盖信封字节，也**禁止**覆盖包文件的
整体哈希。★ 签名块的字节布局与被签的到底是哪一个（摘要的**原值** 32 字节，
不是它的十六进制写法）在**附录 A.3** 里写死。

> **为什么**：信封的格式会演进（今天加签名槽，明天加别的）。签名盖在信封字节上，
> 每动一次信封所有签名全废，而且"同一份内容、两个包"要两个签名。

## 5. 你可以依赖什么 · 客户端

★ 这一节是对**基座**的要求，写在这里是因为**你需要知道**。它**不是**你的义务。

### 5.1 装插件只有一条路

- 插件进"池子"**必须**只经由"安装一个包"这一个动作。
- 往池目录里手工放置内容**必须**不产生任何效果：那些内容**禁止**出现在插件
  列表里、**禁止**被加载，**禁止**被当作"某个站点要给你装的东西"呈现给用户。
- 客户端**必须**能区分并分别陈述这三种"你没有这个插件"：① 站点不支持分发；
  ② 站点支持但这一份没下来（给出原因）；③ 本机有一份，但**没有任何站点报过它**。

> ★ 对你的实际含义：**别在文档里教用户"把目录拷到某处"**。那件事在设计上
> 不产生任何效果 —— 用户照做之后会看到"什么也没发生"，而那是这套东西里
> 最难查的一类症状。要发插件就发包。

### 5.2 装之前会问用户一次

- 装一个带客户端代码的插件之前，**必须**要用户点一次同意。
- 台账**必须**以 `(id, 版本)` 为键、以**全长内容摘要**为值。
- **禁止**给任何一类插件开免同意的口子。

> ★ 对你的实际含义：**你的插件第一次被装、以及内容变了之后，用户会看到一个
> 对话框**，里面是它的名字、它从哪来、以及摘要变成了什么。
> 所以 `displayName` 与 `description` 是写给**用户**看的，不是写给自己看的。

**注记（写给基座实现者）**：同意界面**必须**说清用户在同意什么 —— 至少包括
"这段代码会在这台机器上以完整权限执行"、它来自哪里、以及内容与上一次相比
变了什么。台账条目**必须**绑定摘要值（回写前再核一次）。
**应当**先写台账、后激活插件。理由：一个恶意的清单也在往这台机器上放东西
（一个登录契约可以让客户端往某个地址提交一个口令 —— 那是**数据**不是代码，
但仍然是站点的指令），而**规则一有分支，绕过它的路就会长出来**。

### 5.3 删掉本机那一份 = 撤回同意

- 删掉本机一个构件 ⇒ 台账里对应的那条**必须**一并消失 ⇒ 下一次对账**必须**
  重新走一遍同意闸。
- 这一条**禁止**被实现成"静默装回来"。也**禁止**在文案里断言是用户删的 ——
  客户端不知道原因，它只知道"不在了"。

> **为什么**：删除是一个**没说出口**的决定，而对账不认识它。若只删内容、台账那条
> 还在，下次同步会按"摘要与台账相符"**静默装回来、一个字都不问** ——
> 那不是"当作从来没有过"，那是"用户想让它消失，它自己回来了"。

### 5.4 客户端会钉住你的公钥

- 客户端第一次接受某个 `id` 的构件时，**必须**记下它的签名公钥（首次即信任）。
- 此后任何自报同一个 `id` 的包，**必须**核对其签名者是否为**同一把**公钥；
  不同 ⇒ **必须拒绝**，并**必须**把两把公钥的指纹都说出来。
- 内容**没变**而签名者**变了** ⇒ **必须拒绝**。

> ★ 这是**你**最需要知道的一条保证 —— 它就是 §4.1 那句"丢了私钥只能铸新 id"
> 的来源，也是 §2.5 里"分身"唯一能被机械判出来的地方。
>
> **为什么**：一致性判据判不了"作者换了人"。分身升个版本号，在一致性台账上就是
> 一条**全新的正常条目**，用户看到的是一次普通的"要不要装新版本"。
>
> ★ **一致性判据与认证判据不是一回事，禁止合并**：摘要回答"还是不是我同意的那一份"，
> 签名回答"是不是我以为的那个人"。合并会得到一个看起来更强的检查，而它挡不住
> "第一次给的就是坏的"—— 摘要跟内容同行、由同一个工具写下，它挡得住事后偷换，
> 挡不住首次欺骗。
>
> ★ 首次即信任的**固有弱点**：全新的、从没见过这个 `id` 的客户端会被先到的包
> 钉住。这条**没有**本地解法；本规范不假装有。

## 6. 你可以依赖什么 · 站点

★ 同样是对**基座**的要求，写在这里是因为**你需要知道**。

### 6.1 绝不谎报成功

站点**禁止**在任何一个字节没送达或与声明不符时报告成功。报告成功时，客户端
磁盘上的内容**必须**按字节就是站点那一份。**禁止**截断：单份文件超出上限时
**必须**明确失败。

> ★ 对你的实际含义：**要么完整送到、要么明确失败**。你不会遇到"用户那里是半个
> 插件"这种状态 —— 而那种状态是没法查的。

### 6.2 判据是能力缺席，不是这次失败

- "这个站点支不支持分发"**必须**由一个**协议事实**判定，**禁止**由"这次下载
  成不成功"判定。
- 下载失败时，**禁止**回退到本机自装的任何一份。

> **为什么**：把两者合并，等于给一个能让下载失败的人（断流、丢包、中间人）一个
> 把用户降级到旧本地副本的开关 —— 攻击成本从"改内容"降到"让下载失败"，
> 而后者便宜得多。

### 6.3 不知道谁在引用时，什么都不删

- 引用表读不出来或写不下去时，站点**必须**只报告、**禁止**回收任何内容。
- 写引用表**必须**在回收之前。

> ★ 对你的实际含义：**站点不会因为你这一版暂时没被报出来就把它删掉。**
> 内容不可变（§2.4）加上这一条，意味着一次网络抖动不会让用户丢掉已经装好的版本。

## 附录 A · 容器格式（**规范性**）

★ **这一份写给两种人**：写插件的人（你要能拿 `packer inspect` 的输出对着它逐行
核对，确认"我的包里就是那几份文件、没有别的东西"），以及**基座的实现者**（三份
实现 —— 打包器、守护进程、客户端 —— 要有一处共同指向的定义，否则它们会各自漂）。

★ 它**不是**"打算另写一个客户端的人"的说明书 —— 那种人不存在（见 §0）。

### A.1 布局

```
包 = 头 ‖ 记录表 ‖ 签名块 ‖ 负载
```

**头（固定 20 字节）**

| 偏移 | 长度 | 字段 | 值 |
|---|---|---|---|
| 0 | 8 | `magic` | `73 70 6c 75 67 1a 0d 0a`（`splug␦␍␊`）|
| 8 | 4 | `format` | 大端 u32。本规范版本 1 即 `1` |
| 12 | 4 | `file_count` | 大端 u32 |
| 16 | 4 | `sig_len` | 大端 u32。`0` 表示不带签名，否则**必须**是 97 |

**记录表**：`file_count` 条，每条按顺序：

| 长度 | 字段 |
|---|---|
| 2 | `pathlen`（大端 u16，路径的 **UTF-8 字节数**，不含结尾的 0）|
| `pathlen` | `path` —— **必须**是合法的 UTF-8 |
| 8 | `size`（大端 u64）|
| 32 | `sha256` —— 该份**内容的** sha256 **原值**（不是十六进制写法）|

**签名块**：`sig_len` 字节，`sig_len` 为 0 时不存在。见 A.3。

**负载**：按**记录的同一顺序**逐份拼接的文件字节。

★ 于是长度是**精确**的：

```
20 + Σ(2 + pathlen + 8 + 32) + sig_len + Σsize  ==  包文件的字节数
```

一个字节都不多、一个字节都不少。**尾随字节、空洞、多余记录一律拒绝** ——
信封不进摘要（§3.4），所以信封里任何一个"被忽略的字节"都是**无认证的夹带面**。

### A.2 两条与"怎么编这张表"无关的性质

- **内容摘要从解析出来的 `(path, sha256)` 对按 §3.4 重算**，不看容器怎么编那张表。
  于是**记录表按什么次序排都可以**，同一个内容永远算出同一个摘要；于是信封格式
  的演进不动摘要（与 §4.2 一致）。
- ★ **路径的次序不是格式的一部分，但摘要是。** 一个包可以把记录按任意次序排，
  读方必须能读；而算摘要时**必须**按 §3.4 的路径排序重排一次。
  （先按记录次序算、正好蒙对的实现，会在一个手写的包上算出另一个摘要，
  而那会以"签名验不过"的形式响 —— 排查的人会去查钥匙。）

### A.3 签名块

```
alg     u8      1 = Ed25519
pubkey  32 字节 裸公钥（不是 PEM、不是 DER / SPKI）
sig     64 字节 Ed25519 签名
```

- **签名的是 §3.4 内容摘要那 32 个字节的原值**，**不是**它的十六进制写法。
  两种写法只能选一种，这里选了原值。
- **公钥指纹** = `sha256(那 32 字节裸公钥)` 的小写十六进制（64 字符）。
  它是**给人核对**的那一串（§4.1）。
- `alg` 认不得 ⇒ **拒绝整个包**（不是"忽略签名继续装"）。
- 签名块**不进摘要**（§3.4 明确排除了信封头），所以同一份内容加不加签名，
  算出来的是**同一个**摘要 —— 这正是 §4.2"签名覆盖内容摘要、不覆盖信封"的
  可观测形式。

★ **站点不验签。** §6 没有给站点任何一条验签义务，验签是**客户端**的事（§5.4）。
站点需要做的是把签名者**报出来**给管理员看。

### A.4 读方必须拒绝的东西，以及**判的次序**

★ **次序是规范的一部分。** 一个包同时犯两条时，先判哪条决定了报出来的是哪个词；
三份实现照抄同一次序，"同一个坏包在三端得到同一个答案"才是一句可以断言的话。

| 次序 | 检查 | 不满足时报 |
|---|---|---|
| 1 | 长度放得下 20 字节的头 | `length` |
| 2 | `magic` 相符 | `magic` |
| 3 | `format` 是本实现认识的那个 | `format` |
| 4 | 记录表读得完（`pathlen` 不越界、每条记录不越过文件末尾）| `record` |
| 5 | 长度等式**精确**成立（见 A.1）| `length` |
| 6 | 每条路径合 §3.3，且**是合法的 UTF-8** | `path` |
| 7 | 没有两条路径重复，也没有两条只差 **ASCII** 大小写 | `duplicate` |
| 8 | 每一份的字节与它记录里的 `sha256` 相符 | `content` |
| 9 | 负载里有 `plugin.json`，且它是一个合法的 JSON **对象** | `manifest` |
| 10 | 有签名块而它不合 A.3 的形状（会验签的实现还要判它验不验得过）| `signature` |

**这十个词是三份实现共用的词表**，字面相同。★ 第 4 条先于第 5 条：`file_count`
说多了的时候，多出来的那一条会从**负载**里读表 —— 于是"记录表读不读得完"必须
先判，否则报出来的会是一句关于路径的胡话。

★ **第 10 条里的两半不是一回事**：形状（长度对不对、`alg` 认不认得）谁都能判；
**验签**只有持有密码学实现的那一端判得了。基座里验签的那一端是**客户端**。

### A.5 版本控制的来源

负载的字节取自版本控制里的 **blob**，不是检出之后的字节。理由：`text=auto`
一类的属性会让检出时行尾被改过，而 §3.4 要的是"谁在哪台机器上打包都是同一个
摘要"—— 只有 blob 满足这一条。

## 附录 B · 你（作者）不用管的东西

下面这些**可以**演进，改它们不动本规范。列出来是为了让规范有边界 ——
一份什么都是规范的东西，等于没有规范。

- 各种上限：单文件上限、整包上限、文件数上限、路径深度上限的**具体数值**
- 暂存目录的布局与命名、对账锁的实现、退避重试的次数
- `id` 用 ULID 这个具体编码（换成别的东西，只要是"铸一次、全球唯一"就可以）
- **打包器**放在哪个目录、用什么语言写、命令行选项叫什么
  （★ **容器格式本身不在此列** —— 它在附录 A，是规范性的）
- 引用计数与引用表的具体形状
- 三种实现如何部署、装在哪、谁运维
