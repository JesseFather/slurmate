# 基座 ↔ 插件：契约边界

**规范版本：1**

---

## 0. 这一页是什么，以及它为什么必须先有

这一页**不是 API 文档**（那要写签名、参数、示例、调用时机），也**不是插件规范**
（那要写"正确的做法是什么"）。它做的是**那两份文档共同的地基**：

> 把基座今天**真的**暴露给插件的每一样东西逐条列出来，
> 并对每一条判两件事：**它是承诺还是细节**，以及**它被什么守住了**。

没有这一页，那两份文档的每一句话都只能靠写的人当场判断 —— 而判断会漂。
有了这一页，"这句话该不该写进规范"就不再是一个品味问题，而是一次查表。

### 0.1 承诺等级

| 等级 | 含义 | 改它的代价 |
|---|---|---|
| **稳定** | 作者**可以依赖**它。不兼容地改它**必须**递增框架版本号的首段（`x`） | 升 `x` |
| **试验** | 今天存在，但**不承诺**跨版本一致。作者**可以**用它，**应当**预期它在某个 `y` 里变 | 升 `y`，并在 `CHANGELOG.md` 里写明 |
| **内部** | 作者**禁止**依赖它。它随时可变，不另行通知 | 无 |

这三个等级不是修辞，它们直接挂在既有的版本机制上（"同 `x` 且客户端不低于
服务端 ⇒ 保证兼容"）：**稳定**的东西只在 `x` 递增时才能破，**试验**的可以在 `y`
里破。所以「把一条从**试验**提成**稳定**」是一个**有后果的动作** —— 它把那条
要求挪进了"必须升 `x`"的那一档。反方向（稳定 → 试验）是一次**降级**，
按 §0.2 的口径它应当被当成缺陷处理。

### 0.2 保证方式

| 方式 | 含义 | 违反了会怎样 |
|---|---|---|
| **机器** | 有一条校验、类型检查或断言挡着 | **当场失败**：装不上 / 提交被拒 / 抛错 |
| **一句话** | 只在文档里写着，没有任何东西挡 | **要么没有任何症状，要么在很远的地方以别的形状出现** |
| **无** | 今天连一句话都没有 | 没有症状，而且作者无从知道 |

**第二栏是这一页存在的理由。**

`PLUGIN-SPEC.md` §0 自己写着：**"一份读起来像承诺、实际没人守的保证，比一条
明写的义务更糟。"** 而本仓库全部的实现纪律建立在同一条判据上 ——
**变异打不红的东西不算被守住**。这一栏就是把那条判据搬到契约上来。

⇒ 因此这一页的读法是：

| 组合 | 怎么用 |
|---|---|
| **稳定 + 机器** | 可以照着它写代码。它成立，而且违反了会当场知道 |
| **稳定 + 一句话** | **今天靠不住**。它是一条设计意图，不是一条保证 —— 改它不需要通知 |
| **试验** | 现在可以用，但**不要围绕着它设计**。它随时可能变 |
| **内部** | 不要用。插件作者没有理由知道它 |

**对 API 成员（§4），这一栏判的是「语义」，不是「存在性」。**

成员不存在、参数个数不对、返回值类型不对 —— 这些**总是**当场失败
（`TypeError`），所以它们**不构成风险**，也不值得逐条标注。真正会漂的是
**字段集、返回值形状、调用时序**（比如"`connection()` 一定给我 `user`"
或者"`attach` 只调一次"），而它们**没有任何东西挡**。

⇒ 逐条填下来会看到一个结论：**`ctx` 的成员大多只被"存在性"守着。**
这个结论本身是这一页的产出之一，见 §8.1 T7。

### 0.3 规范性措辞

本页与它派生出的文档共用同一套措辞（与 `PLUGIN-SPEC.md` §0.1 一致）：

| 措辞 | 含义 |
|---|---|
| **必须** / **禁止** | 规范性要求。不满足即不合规 |
| **应当** / **不应当** | 有理由的推荐。偏离要有说得出的理由 |
| **可以** | 真正可选的 |

**一条要求必须能被判定**。"写得清楚一点"、"尽量不要"这类句子不进本页 ——
它们无法被判定，因此无法被守住，也无法被变异验证。

### 0.4 这一页怎么维护

> **每一条「机器」都必须指得出挡它的那个校验在哪。**
> 指不出来的，就改判成「一句话」。

这条规则的作用是让**退化**变得可见：「机器」改判成「一句话」是一次实质性的
降级，而它在代码里可能只是一个 `if` 的消失 —— 那是评审时最容易看漏的一类改动。

## 1. 框架与插件的关系

一个**插件** = 一种服务。一个会话提供哪种服务，就由哪个插件负责把它接起来。

| 方向 | 东西 | 强制性 |
|---|---|---|
| 插件 → 基座 | **清单**（`plugin.json`）：身份与声明 | **必须**有 |
| 插件 → 基座 | **客户端代码**（`client/index.js`）：三个可选钩子 | **可以**没有 |
| 插件 → 基座 | **作业片段**（`job/start.sh`）：起服务的那一段 | **可以**没有（那样的插件装得上、看得见，但提交不了） |
| 基座 → 插件 | 清单被读取、校验、注册 | 总是 |
| 基座 → 插件 | 窗口里那一块视图（`WebContentsView`） | 声明了 `contributes.surface` 才有 |
| 基座 → 插件 | 本地隧道（`127.0.0.1:<本地端口>` → 计算节点） | 会话进入 RUNNING 才有 |
| 基座 → 插件 | 存储分区（`localStorage` 的归属） | 同上 |
| 基座 → 插件 | 插件数据目录（`ctx.dataDir()`） | 总是 |
| 基座 → 插件 | 自动登录（`ctx.login()`） | 声明了 `contributes.login` 才有 |
| 基座 → 插件 | 作业宿主（把作业片段织进 `run.sbatch` 并执行） | 站点部署时 |

**基座不认识任何插件名。** 上面每一格都由声明驱动，没有一处按名字分支 ——
所以"加一个插件"= `plugins/` 下多一个目录，框架一行都不用改。

## 2. 清单（`plugin.json`）

**未知键一律报错，不是忽略**（等级 **稳定**，保证 **机器**，**两侧都拒**）。
理由：打错一个键名（比如把 `contributes` 拼成 `contribution`）不该静默变成一个
"配了但不生效"的插件。

判据只有一份**书面形式**：[`tools/manifest-keys.json`](../tools/manifest-keys.json)。

| 位置 | 客户端 | 守护进程 |
|---|---|---|
| 清单顶层键 | 有白名单，**报错** | 有白名单，**报错** |
| `contributes` 子键 | 有白名单，**报错** | 有白名单，**报错** |
| `contributes.surface` / `.login` / `.data` 的子键 | 有白名单，**报错** | 有白名单，**报错** |
| `engines` 子键 | 报错 | 报错（判据在 [`tools/version-fixtures.json`](../tools/version-fixtures.json)） |
| `site` 段内部 | **只查形状**（是不是对象） | 逐键校验，但**不查未知键** |

**判的只是键名，不是值的形状。** 值那一层两边仍各管各的：客户端查全部
（`contributes.ports` 必须是 0 到 1 的整数、`surface.path` 必须以 `/` 开头……），守护进程
只查它真读的那几个（`submitPubkey` 的类型、`site.defaultCpus` 的范围……）加上
`engines`。所以"两侧一样严"这句话今天在**键名**上成立，在**值形状**上不成立。

`site` 段内部是**刻意保留**的不对称：那一段只有站点侧读，客户端只把它当不透明
数据。代价是一个拼错的 `site.defaultCpuss` 会被**静默忽略** —— 与未知键那条规则
要消灭的正是同一类东西。它在 §2.4 的 T8 那一行里记着。

**两侧为什么各持一份、不在运行期读那一份 JSON**：守护进程是**一个文件**装到
`/usr/local/sbin/slurmate-sessiond`（集群上没有 `tools/`），客户端是一个**分发
单元**（运行期只读 `client/` 里的东西）。两侧各写一条相对路径的话，**从源码跑得
通、装出去就断**：键表成了空集，于是"什么都不拒" —— 而那只在装出去的机器上露出来。
完整理由与代价写在那份 JSON 的 `_` 段里。⇒ 这条保证由**三处守卫**支撑：客户端用例
（`client/test/manifest-keys.test.mjs`）、守护进程用例（`cluster/test-sessiond-logic.py`
的 19.16）、以及 CI 的 lint。

### 2.1 身份

| 键 | 形状 | 缺省 | 等级 | 保证 | 说明 |
|---|---|---|---|---|---|
| `id` | ULID（26 字符） | 无，**必填** | 稳定 | 机器 | **身份**。诞生时铸一次，此后永不改变 |
| `name` | `^[a-z][a-z0-9-]{0,31}$` | 无，**必填** | 稳定 | 机器 | **短名**。站点内唯一；进配置块名、会话文件、日志 |
| `displayName` | 字符串 | 同 `name` | 稳定 | 机器 | 给人看的名字 |
| `version` | `x.y.z`（无前导零，`y`/`z` ≤ 255） | 无，**必填** | 稳定 | 机器 | 插件版本。`(id, version)` 是池里的槽位键 |
| `description` | 字符串 | `''` | 稳定 | 机器 | |
| `author` | 字符串 | `''` | 稳定 | 机器 | |

**目录名不参与任何判定。** 身份来自 `id`，版本来自 `version`；目录名纯粹是给人看的。

### 2.2 `engines`

| 键 | 形状 | 缺省 | 等级 | 保证 | 说明 |
|---|---|---|---|---|---|
| `engines.slurmate` | 范围片段（如 `>=0.5`） | 无，**必填** | 稳定 | 机器 | 声明"我要求基座不低于哪一版" |

**两套版本号不是一回事**：框架版本是 `x.y`（客户端、守护进程、协议三合一），
插件版本是 `x.y.z`。`engines.slurmate` 比的是**前者**。

### 2.3 `contributes` —— 作者对基座的声明

| 键 | 形状 | 缺省 | 等级 | 保证 | 说明 |
|---|---|---|---|---|---|
| `concurrent` | 布尔 | **无缺省，必填** | 稳定 | 机器 | 插件能不能同时开两份。缺省取哪边都是基座替插件作者表态 |
| `ports` | 整数 `0`–`1` | `0` | 稳定 | 机器 | 这个插件的一份数据要占几个**本地端口**（端口 = origin = 一份浏览器存储）。`≥1` ⇒ 它在每个工作区里都有一份**自己的数据**；`0` ⇒ 不要数据空间，整台机器上只有一份 |
| `surface` | `{kind, path}` | 无（不要界面） | 稳定 | 机器 | 界面。`kind` 今天只有 `'web'` |
| `surface.kind` | `'web'` | — | 稳定 | 机器 | 枚举。别的值**装不上** |
| `surface.path` | 以 `/` 开头的路径 | — | 稳定 | 机器 | 拼在隧道 origin 后面，构成视图加载的 URL |
| `login` | `{path, field, cookie}` | 无（不自动登录） | 稳定 | 机器 | 网页表单登录的三个事实 |
| `submitPubkey` | 布尔 | `false` | 稳定 | 机器 | 提交时要不要带一把一次性公钥 |
| `data` | `{inherit}` | 无 | 稳定 | 机器 | 运行时数据的共享方式。见 §2.3.1 |

**组合判定**（违反即装不上；等级 **稳定**，保证 **机器**）：

| 组合 | 结论 | 理由 |
|---|---|---|
| `concurrent: true` 而 `ports` 不是 `≥1` | **拒绝** | 第二份就是第二份**数据**（一份临时的副本）；不要数据空间的插件没有「第二份」可指 |

**这是 `contributes` 底下唯一的一条组合判定。** `data` 与 `ports` 之间
**没有**约束 —— 它们回答的是两个不相干的问题（"和谁共用"与"要几个端口"）。

#### 2.3.1 `data.inherit` 与**身份**

一个插件的运行时数据身份是**三段**：

```
<插件 id> @ <共享组> [ @ <数据空间 id> ]
```

| 段 | 值从哪来 | 什么时候存在 |
|---|---|---|
| **插件 id** | 清单 | 总是 |
| **共享组** | `data.inherit`（两个键都不写时是一个固定常量） | 总是 |
| **数据空间** | **那一份数据自己**（它的 id 由框架铸，而它挂在一个工作区那张引用表上） | 仅当 `ports ≥ 1` |

| `data.inherit` | 共享组那一段 | 效果 |
|---|---|---|
| 写了（如 `"editor"`） | 就是这个串 | **该插件的多个版本共用这一份数据** —— 升版本号，数据还在 |
| 缺席 | **该插件的版本号** | 每个版本一份：**升版本号 = 换一份全新的数据** |

**这一格回答的是「升级版本时，数据跟不跟着走」**，不是"和谁共用"。

- **缺席**（缺省，合法且安全）：每个版本一份 ⇒ 一个新版本读到自己读不懂的旧格式时，
  用户看到的是**界面一片错乱**，而不是一句"升级之后要重配"。
- **写了**：这几个版本共用共享组名 ⇒ 升级之后数据还在。

**共享组名由插件作者自己起。** 两个互不相干的插件都写 `editor` **完全正常** ——
身份的第一段是插件 id，所以**不同插件之间永远不会共用数据**。

取值**必须**匹配 `^[a-z][a-z0-9-]{0,31}$`（等级 **稳定**，保证 **机器**）——
不是任意字符串：那一段会进磁盘目录名。

**两个键都不写时共享组是一个固定常量**（`default`）⇒ 所有版本共用一份。
`perVersion: true` 则是另一头：共享组那一段是**该插件自己的版本号** ⇒
**升版本号 = 换一份全新的数据**，旧的那一份**不会**被自动搬过去，它会变成孤儿
（用户能在面板上看见并删掉）。**版本号不只是分发用的，它还是数据身份的一半。**

第三段**只由 `ports` 决定**，与 `concurrent` 和 `data` 都无关。
`concurrent` 管的是**另一件事**：「能不能同时开两份」（第二份是**临时的**，
会话结束就丢）。

`data.perInstance` **已经删除**。它今天得到一句指路的报错（**机器**），
而不是"认不得的键" —— 报错里会写出新名字 `contributes.concurrent`。

### 2.4 `site` —— 站点侧读的声明

这一节的读者是**站点管理员与守护进程**，不是客户端。**客户端的清单校验只检查
整个 `site` 是不是一个对象**，一个键都不读。

**所以下一张表的「保证」栏说的是守护进程那一侧。** 一个作者在自己机器上
永远看不到这一节的报错 —— 它们只在站点扫描时才出现。

| 键 | 形状 | 缺省 | 等级 | 保证 | 说明 |
|---|---|---|---|---|---|
| `site.defaultCpus` | 整数，`1..MAX_CPUS_REQUEST` | **无缺省，必填** | 稳定 | **机器** | **整个 `site` 段缺席也会被拒** —— 因为这一格拿不到值 |
| `site.defaultMem` | 字符串（如 `"8G"`） | **无缺省，必填** | 稳定 | **机器** | 同上 |
| `site.defaultEnabled` | 布尔 | `false` | 稳定 | **机器**（形状） | 本站新用户缺省开不开 |
| `site.bin` | `{env, discovery, name, fallback}` | 无 | 稳定 | **机器** | 可执行文件怎么找、路径怎么传给作业 |
| `site.bin.env` | 字符串 | 无 | 稳定 | **机器** | **必须**以 `SLURMATE_` 开头 —— 这个名字会塞进作业的环境变量表 |
| `site.bin.discovery` | `'which'` \| `'convention'` | `'convention'` | 稳定 | **机器** | |
| `site.bin.name` | 字符串 | 无 | 稳定 | **机器** | `discovery: 'which'` 时**必须**给 |
| `site.bin.fallback` | 非空路径字符串 | 无 | 稳定 | **机器** | |
| `site.enumKeys` | `{键: {choices, default}}` | 无 | 稳定 | **机器** | `default` **必须**在 `choices` 里 |
| `site.defaultGpus` | —— | —— | **不存在** | —— | 见 §7 与账本 F15 |

**打错这一节里的键名，报错会说错方向：**

守护进程是**逐键取值**的，没有未知键检查。所以：

| 打错的是 | 会发生什么 |
|---|---|
| `defaultCpus`（比如写成 `defualtCpus`） | 会被拦下 —— 因为它**必填**，取不到值就报「`site.defaultCpus` 必须是整数」。报错**不说是键名打错了** |
| `defaultEnabled`（有缺省） | **没有任何人说**。插件照装，而那个开关**永远不生效** |
| `bin` 底下的子键 | `bin` 存在时子键会被逐条查；`bin` 整个不在时一个都不查 |

⇒ 见 §8.1 **T8**。

## 3. 客户端钩子

**三个钩子全部可选。** 一个声明式插件可以一个都不写。

导出它们的方式：`client/index.js` 的 `module.exports`。导出一个**不在名单里**的
键是**错误**（等级 **稳定**，保证 **机器**）—— 不是"被忽略"：静默忽略会让一个
旧插件看起来装上了、而它写的东西从头到尾没生效。

允许导出的键（**这是全部**）：`prepare`、`attach`、`closeWarning`。
`preferredPort` **已经删除**，导出它是错误。

### 3.1 `prepare(ctx)`

| 项 | 内容 |
|---|---|
| 何时调 | **提交之前**，且**在该槽通过并发闸之后** |
| 同步/异步 | **同步**。它的返回值当场被读 |
| 返回 | `{ok: true, sshPubkey?}` 或 `{ok: false, message}` |
| 等级 | 稳定 |
| 保证 | **机器** —— 返回 `ok: false` 时提交被中止，且刚建立的会话记录与临时那一份被撤回 |

**义务**：声明了 `contributes.submitPubkey` 的插件**必须**在这里返回 `sshPubkey`，
否则守护进程会拒绝这次提交。

**禁止**：在这里做耗时的事。它在一条**不许有 `await` 的同步窗口**里（见 §3.1.1）。

#### 3.1.1 为什么是同步的（这条约束是承重的）

从「认领那一份数据」到「把会话记录写进表」之间**禁止**让出控制权。两条 `app:start`
同时在飞时，让出控制权会让它们都看到"没有持有者"，后一条顶掉前一条的记录 ——
前一条的作业从此没有心跳，1800 秒后被 `scancel`，而界面上只有一条会话。

⇒ 所以 `prepare` 是同步的，`ctx.dataDir()` 在这个窗口里也是安全的。

#### 3.1.2 `ctx.dataDir()` 在 `prepare` 里可用

**次序是承重的**：`ctx.dataDir()` 从会话手里那一份数据算起，而那一份是
`controller` 记着的。若 `prepare` 跑在 `controller` 构造之前，一个「要工作区
**又** 带 `prepare`」的插件会**一提交就抛**。

所以次序是：**认领 → 建 controller → 记进表 → 快照数据 → `prepare`**。
所以 `ctx.dataDir()` 在 `prepare` 里是一个**有定义的值**。

### 3.2 `attach(ctx, snap)`

| 项 | 内容 |
|---|---|
| 何时调 | 会话**进入 RUNNING 且有 origin** 时；**每次状态变化都调** |
| 同步/异步 | **可以**返回 Promise（框架 `await` 它） |
| 返回 | 返回值被忽略 |
| 幂等 | **必须幂等**。同一次会话里它会被调用很多次 |
| 等级 | 稳定 |
| 保证 | **机器**（会被 await） |

**界面与它的关系**：

| 清单里的声明 | 框架先做什么 | 再调 `attach` |
|---|---|---|
| 有 `surface` | 建/复用那块视图并加载 URL | 是 |
| 无 `surface` | **只收掉这个插件那一块视图**（不碰别人的） | 是 |
| 会话类型未知 | 销毁视图，**绝不建界面、绝不 POST 口令** | **不调**（没有插件可调） |

**典型用途**：自动登录（`ctx.login`）、往它自己的页面里做点事。

**禁止**：在这里假设自己只被调用一次。**禁止**在这里假设「窗口里当前那块视图
就是我」—— 多开时窗口里可以同时有好几块。

### 3.3 `closeWarning`

| 项 | 内容 |
|---|---|
| 形状 | **静态对象** `{message, detail}`，不是函数 |
| 何时用 | 用户关窗时，那条会话的确认对话框 |
| 缺省 | 框架的中性文案 |
| 等级 | 稳定 |
| 保证 | **机器**（形状不对即装不上） |

**义务**：多条会话同时活着时，每一条**各念各的**。不写这一条的插件得到中性文案。

## 4. `ctx` —— 框架递给插件的全部能力

插件拿到的是这个对象，**不是**整个模块作用域。这份清单就是"一个插件能碰什么"
的完整答案。

**每一次调用都新建一个。** `connection()` 与 `session()` 是**取值器式**的
（每次现取），所以跨越 `await` 之后拿到的仍然是当下的值。

| 成员 | 形状 | 等级 | 保证（语义） | 说明 |
|---|---|---|---|---|
| `win.surfaceSession` | **取值器**，返回 Electron `session` 或 `null` | 稳定 | 一句话 | **绑在这一条会话上**。是取值器不是方法 |
| `win.reloadSurface()` | `() => Promise` | 稳定 | 一句话 | 重新加载**这一条会话**那块视图 |
| `connection()` | `() => {id, label, user, host, port} \| null` | 稳定 | **一句话** | **冻结的副本**。是"属于哪条连接"，不是"当前活跃的那条"。字段集没被守住：少一个字段拿到的就是 `undefined` |
| `session()` | `() => object \| null` | **试验** | 一句话 | 这是**服务端的原始会话对象**，字段集由守护进程定义。不要按字段依赖它 |
| `dataDir()` | `() => string` | 稳定 | 一句话 | **这个插件的**数据目录（绝对路径）。可能还不存在。算不出根时**抛**，不返回 `null` |
| `home()` | `() => string` | 稳定 | 一句话 | **用户自己的**家目录。开发者模式落在沙盒里 |
| `dev` | 布尔（**值**，不是函数） | 稳定 | 一句话 | 这次会话是不是跑在假后端上 |
| `whoami()` | `() => object` | **试验** | 一句话 | 当前账户信息。字段集未定义 |
| `keys` | 六个函数，见 §4.2 | 稳定 | 一句话 | 钥匙工具箱 |
| `login(ses, origin, password)` | `async (…) => {ok, reason?, status?}` | 稳定 | 一句话 | 自动登录。契约由框架从**这个插件自己的清单**取 |
| `notice(kind, text)` | `(string, string) => void` | 试验 | **一句话** | 往界面推一条提示。见 §4.3 |
| `once(key)` | `(string) => boolean` | 试验 | 一句话 | "这句话我说过没有"。按 `id@版本` 分桶 |

**这张表每一行的保证都是「一句话」。** 这不是疏忽，是现状 —— 见 §0.2 那段。
读法：**等级**说"我们承诺它不变"，**保证**说"没有东西挡着别人把它改坏"。
两者同时为真时，那条承诺的强度取决于**评审**，而不是取决于**机器**。

### 4.1 明确**不**给的东西

| 不给 | 理由 |
|---|---|
| `config` 模块 / `ctx.cfg` | 那是整个 `config.json` 的**写**权。插件要的只是"我这条会话属于哪条连接" |
| 客户端自己的私钥 | `keys.js` 里没有任何"读到客户端自己那把私钥"的入口 |
| 别的会话的视图 | `ctx.win` 绑在这一条会话上 |
| 本地端口的选择权 | 由那一份数据决定，且**只读** |
| 界面的 URL | 由 `surface.path` + 隧道 origin 决定 |

### 4.2 `keys` 工具箱

| 成员 | 形状 | 等级 | 保证 |
|---|---|---|---|
| `keys.generate()` | 生成一把 ed25519 | 稳定 | 一句话 |
| `keys.publicKeyLine(...)` | 拼出 OpenSSH 公钥行 | 稳定 | 一句话 |
| `keys.publicKeyLineFromPrivatePem(...)` | 同上，从私钥 PEM 来 | 稳定 | 一句话 |
| `keys.isUsablePrivatePem(...)` | 判断 | 稳定 | 一句话 |
| `keys.fingerprintOf(...)` | `SHA256:…` 指纹 | 稳定 | 一句话 |
| `keys.isValidPublicKeyLine(...)` | 判断 | 稳定 | 一句话 |

与 §4 那张表同一个口径（见 §0.2）。这是 `ctx` 里**唯一有专门单测**的一组 ——
所以它的"一句话"是这一节里最接近"机器"的那一句，但那仍然是**测试**在守，
不是**校验**在守。

#### 4.2.1 `login()` 的返回值

| 返回 | 含义 |
|---|---|
| `{ok: true, status}` | 拿到了会话 cookie |
| `{ok: false, reason: 'no_contract'}` | 没声明 `contributes.login` |
| `{ok: false, reason: 'no_password'}` | 控制节点还没返回口令（**稍后再试是有意义的**） |
| `{ok: false, reason: 'no_cookie', status}` | 端点是通的但没拿到 cookie。口令错**与**服务升级改了端点**都**长这样 |
| `{ok: false, reason: 'fetch_failed: …'}` | 根本没连上 |

**判据是"分区里有没有 cookie"，不是 HTTP 状态码** —— 这套网页表单登录
在口令错时返回的是 `200`。所以 `no_cookie` 这一档**必须**翻译成给用户的话，
而且**应当**把"口令不对"与"服务改了端点"分开说。

### 4.3 `notice` 的 `kind`：一个**没有定义域**的参数

`kind` 原样进渲染端的 `className`（`'notice ' + kind`），**没有任何校验**。
今天实际用到的值：`'ok'`、`'error'`、`'info'`、`'warn'`。

⇒ 等级 **试验**，保证 **一句话**。传别的值不会报错，也不会有效果 ——
这是一条**应当**被收紧的要求（见 §8 待办）。

## 5. 作业侧契约

这一节的读者是**写 `job/start.sh` 的人**。它与 §2–§4 是**两条独立的边界**：
§2–§4 管"客户端这一半"，本节管"作业这一半"。两半配套 —— **对不上就用不了**。

**权威定义**在 `plugins/README.md` 的〈作业侧契约〉一节。本节判等级，**不重复正文**。

### 5.1 分派：短名决定函数名

作业侧只有一个分派点（`run.sbatch` 的 `plugin_call`）：

```
函数名 = <动词>_<短名>       其中短名里的 `-` 写成 `_`
```

| 动词 | 何时调 | 缺省行为 |
|---|---|---|
| `precheck_<短名>` | 起服务**之前** | **可以**没有 —— 分派函数返回 `3` 表示"没有这个钩子"，宿主跳过并记一行日志 |
| `start_<短名>` | **每个候选端口各一次**，直到某一个返回 `0` | **必须**有（编织期断言） |
| `cleanup_<短名>` | 收尾时 | **可以**没有 |

**短名里的 `-` 转 `_` 是硬规则**：短名 `my-plugin` 的函数叫 `start_my_plugin`。
这一点在**编织期与运行期各判一次**（等级 **稳定**，保证 **机器**）。

### 5.2 宿主**给**插件的变量

插件片段与宿主在**同一个 shell** 里，直接读这些变量。

| 变量 | 形状 | 等级 | 保证 | 说明 |
|---|---|---|---|---|
| `$1` | 十进制端口串 | 稳定 | 机器 | 宿主挑好的端口，**已实测可绑定** |
| `$NODE_IP` | **字面 IPv4** | 稳定 | 机器 | 本节点地址。以 `scontrol show node` 的 `NodeAddr` 为权威，**不是** DNS |
| `$SVC_PORT` | 端口串 | 稳定 | 机器 | 仅 `start_*` 成功后非空 |
| `$SVC_PID` | pid | 稳定 | **一句话** | **由插件的 `start_*` 写入** —— 见 §5.4 |
| `$LOCAL_LOG_DIR` | 目录路径（`0700`） | 稳定 | 机器 | 唯一**官方**的临时文件落点。**节点本地**：登录节点看不见它 |
| `$AUTH_MODE` | `password` \| `publickey` \| `none` | 稳定 | 机器 | 在 `start_*` **之前**定好 |
| `$AUTH_PASSWORD` / `$PASSWORD` | 口令串 | 稳定 | 机器 | 仅 `password` 模式非空。`PASSWORD` **已导出**给服务进程 |
| `$MY_UID` / `$MY_USER` | 数字 uid / 用户名 | **待定** | **无** | 两个插件都在用，而它**不在接口表里** —— 见 §5.8 |
| `$JOB_ID` / `$NODE` | Slurm 作业号 / 节点短名 | 稳定 | 机器 | |
| `$STARTED_AT` | epoch 秒 | 试验 | 一句话 | |
| `PLUGIN_SESSION_FIELDS` | 关联数组 | 稳定 | 机器 | 插件往里写键值，宿主统一做 JSON 转义 |

**`SLURMATE_*` 环境变量**（由守护进程在提交时注入）：

| 类别 | 内容 |
|---|---|
| **硬断言**（缺一个作业当场死） | `SLURMATE_SESSION_ID`、`SLURMATE_CANDIDATES`、`SLURMATE_SERVICE_KIND`、`SLURMATE_AUTH_MODE` |
| **带缺省** | `SLURMATE_PARTITION`、`SLURMATE_CPUS`、`SLURMATE_MEM`、`SLURMATE_GRES`、`SLURMATE_PORT_MIN`、`SLURMATE_PORT_MAX`、`SLURMATE_CLUSTER_CIDR`、`SLURMATE_SESS_DIR`、`SLURMATE_LOG_DIR`、`SLURMATE_PASSWORD_BYTES`、`SLURMATE_SSH_PUBKEY` |
| **插件专属，由插件的清单声明** | `site.bin.env` 那一个名字。它的值**必须**以 `SLURMATE_` 开头（等级 **稳定**，保证 **机器**） |

`SLURMATE_CANDIDATES` 的分隔符是**分号**，不是逗号（`--export` 按逗号切）。
**禁止**假设它是逗号分隔。

插件专属变量名**宿主不认识** —— 加第三个插件不用动 `run.sbatch` 一个字。
惯例是给插件的 `bin` 配一个兜底值（两个插件都这么做）。

### 5.3 宿主**提供**的函数

**正式承诺的只有四个**（`plugins/README.md`）：`log` / `json_escape` /
`write_atomic` / `write_session`。等级 **稳定**。

保证分两半：**调用一个不存在的命令**会让作业当场失败（**机器**）；
而**用错参数**（少给一个、给错类型）**不会被拦**（**一句话**）。

| 函数 | 用途 |
|---|---|
| `log(msg)` | 往作业日志的**标准输出**上写一行（⇒ `slurm-<作业号>.out`）。`log_err(msg)` 同理，走标准错误 |
| `json_escape(s)` | `\` / `"` / 制表符 |
| `write_atomic(dst, content)` | 写临时文件 + `mv -f`（NFSv4 RENAME 服务端原子） |
| `write_session(state, ec)` | 写整个会话文件；插件的 `PLUGIN_SESSION_FIELDS` 在此展开 |

宿主**还定义了** `is_ipv4` / `write_jobhb` / `detect_node_ip` / `port_free` /
`plugin_call` / `host_start_service` / `plugin_names` / `pick_port_and_start` /
`cleanup` / `gen_password` —— 这些是**宿主的内部实现**。等级 **内部**：
**禁止**依赖它们，虽然它们在同一个 shell 里够得着。

### 5.4 插件**必须**实现什么

**`start_<短名>(端口)`**

| 返回 | 含义 |
|---|---|
| `0` | 起来了。**并且必须把服务进程的 pid 写进 `$SVC_PID`** |
| 非 `0` | 这个端口失败，宿主换下一个候选 |

**写 `$SVC_PID` 是本契约里最脆弱的一条。**

- 等级 **稳定**，保证 **一句话** —— `deploy.sh` 里**没有任何断言**检查它。
- 三处消费它：心跳的存活门、`cleanup` 里的杀进程、主流程最后的 `wait`。
- **违反了会怎样**：`wait ""` 立刻返回 ⇒ 作业在打出"会话就绪"那一行之后
  **立刻结束**。用户在界面上看到的是"起来了又马上没了"。
- 失败路径上**必须清空它**（`SVC_PID=""`），否则 `cleanup` 会去杀一个不存在的 pid。

**`precheck_<短名>()`**（**可以**没有）

| 返回 | 含义 |
|---|---|
| `0` | 通过 |
| `3` | **不是失败** —— "没有这个钩子"的约定值，宿主跳过 |
| 其他 | 失败：写 `failed` 会话状态并以 `exit 24` 结束作业 |

**`cleanup_<短名>()`**（**可以**没有）

- 返回值被**忽略**（宿主 `|| true`）。
- **调用位置不重要。** 服务进程的输出**实时**直接落在作业日志上（见 R15、§5.5），
  没有"结束时并回来"这一步，因此没有时序约束。

### 5.5 调用次序

```
precheck_<短名>                    ← ①  一次
  → 定 AUTH_MODE / 生成口令
  → 写 "starting"
  → pick_port_and_start            ← ②  每个候选端口各调一次 start_<短名>
  → 写 "running" + 起心跳循环
  → wait "$SVC_PID"                ← 依赖插件写了 SVC_PID
  → cleanup(rc):
       kill 心跳 → kill 日志管家 → kill SVC_PID → 写墓碑 → 清口令
       → log "清理完成"
       → cleanup_<短名>            ← ③
       → 保留期与总量上限再看一眼
       → 删 LOCAL_LOG_DIR
```

`start_<短名>` 返回 `0` 之后，宿主会核对**服务进程的 stdout/stderr 与自己的
是不是同一条流**（`/proc/<pid>/fd/N` 逐字比对）。不是 ⇒ 判本次启动失败，
写 `failed` 会话状态并以 `exit 25` 结束作业。见 R15。

### 5.6 会话文件与跨语言字段

**插件不直接写会话文件** —— 走 `PLUGIN_SESSION_FIELDS`。宿主写死的那一批字段
由守护进程按白名单过滤后经 RPC 给客户端；**客户端从不直接读这个文件**。

**`PLUGIN_SESSION_FIELDS` 的键必须登记**（等级 **稳定**，保证 **一句话** ——
守护进程的白名单**静默丢弃**未登记的键，**不报错**）。今天已登记的是 `ssh_host_key`
（作业侧写、客户端读：把作业里那个 ssh 服务的主机密钥带进 `known_hosts`）。

⇒ **加一个新键是一次两端的改动**，不是插件自己说了算。

### 5.7 编织期的断言（违反即部署中止）

| # | 断言 | 位置 |
|---|---|---|
| 1 | 模板里拼接标记**恰好一处** | `deploy.sh` |
| 2 | 插件 id 是合法 ULID | `deploy.sh` |
| 3 | 包里有 `job/start.sh` 且能取出来 | `deploy.sh` |
| 4 | **无 shebang、无 `#SBATCH`** | `deploy.sh` |
| 5 | **定义了 `start_<短名>`** | `deploy.sh` |
| 6 | **其余函数一律带 `_<短名>_` 前缀**（白名单：`start_` / `precheck_` / `cleanup_`） | `deploy.sh` |
| 7 | 织完不许残留标记行 | `deploy.sh` |
| 8 | 织后 `bash -n` 语法检查 | `deploy.sh` |

**包里有 `job/start.sh` 但没有 `start_<短名>`** 会在**部署期**中止，而不是
安装期 —— 作者在自己的机器上看不到这个错。

**包里没有 `job/start.sh` 是合法状态**：那样的插件装得上、看得见，**但提交不了**。
部署只记一条警告。

### 5.8 这一节暴露出的接口缺口

| # | 缺口 | 后果 |
|---|---|---|
| G1 | **`$AUTH_MODE` 与 `$MY_USER` 不在接口表里**，而两个插件都在用 | 它们**事实上是接口**。宿主改名 ⇒ 两个插件静默出错。等级栏今天只能填"无" |
| G2 | **`$SVC_PID` 只有文档、没有断言** | 见 §5.4 —— 违反的后果很重，而发现它的成本很高 |
| ~~G3~~ | ~~"不许把服务输出直接写 `$LOCAL_LOG`"没有部署期断言~~ | **已消除**：`$LOCAL_LOG` 本身没有了，取而代之的判据是"服务进程的 stdout/stderr 必须还是作业自己的那两条流"，由宿主在**运行期**逐字比对 `/proc/<pid>/fd/N`（见 R15）。编号保留、不重用 |
| G4 | **"函数外不许有顶层语句"没有断言** | 今天靠"一个插件一份"从结构上消除危害 |
| G5 | `tools/conformance/tree/job/start.sh` **带 shebang 且没有 `start_*`** | 它是打包器的符合性夹具，**故意如此**。但它长得像模板 —— 抄它的人会在下一个站点上撞见断言 4/5 |

## 6. 红线

这一节列的是**禁止**做的事。每条都注明挡住了没有。

| # | 禁止 | 保证 | 违反了会怎样 |
|---|---|---|---|
| R1 | 清单里出现未知的键 | **机器**（**两侧都拒**） | 装不上（客户端）／拒绝安装与分发（站点），两边都报错点名那个键 |
| R2 | 同一个 `(id, version)` 两份内容不同的构件 | **机器** | **两个都不加载**，并报错 |
| R3 | 负载里出现符号链接、目录项、非普通文件 | **机器** | 拒绝整个包 |
| R4 | 负载路径违反 §3.3 的路径规则 | **机器** | 拒绝整个包 |
| R5 | 导出一个不在 `['prepare','attach','closeWarning']` 里的键 | **机器** | 装不上 |
| R6 | 声明 `concurrent: true` 而 `ports` 不是 `≥1` | **机器** | 装不上 |
| R7 | 读客户端自己的私钥 | **机器** | 没有入口（`keys.js` 不导出） |
| R8 | 写 `config.json` | **机器** | 没有入口（不给 `config` 模块） |
| R9 | 拿 `ctx.win` 去操作**别人的**会话 | **机器** | 入口绑在这一条会话上 |
| R10 | 在**目录**形态下带 `node_modules` | **一句话**（目录）／**机器**（包） | 目录形态：摘要**不看**它，而 `require()` **会读**它 ⇒ **两棵摘要相同的树可以有不同行为**；包形态：被路径规则直接拒（见 R3/R4） —— 见 F24 |
| R11 | 在 `attach` 里假设自己只被调一次 | 一句话 | 重复执行，症状由插件自己承担 |
| R12 | 作业片段里写 shebang 或 `#SBATCH` | **机器** | **部署中止**（不是安装被拒 —— 插件作者在自己机器上看不到这个错） |
| R13 | 作业片段的其余函数不带 `_<短名>_` 前缀 | **机器** | 部署中止。理由不是"插件之间互相覆盖"（那已经不可能），而是**不许遮蔽宿主自己的函数** |
| R14 | 依赖 §7 里"不提供"的东西 | —— | 不存在 |
| R15 | 在 `start_<短名>` 里把服务进程的 stdout/stderr **重定向走**（`>> 自己的文件`、`>/dev/null`、`exec 3>`…都一样） | **机器** | **当场拒绝启动**：作业写 `failed` 并以 `exit 25` 结束，报错点名是哪一条流、指到了哪里。判据是运行期 `/proc/<pid>/fd/N` 与宿主自己的 fd **逐字比对** —— 扫源码扫不干净，而内核那张 fd 表骗不过去 |
| R16 | 假设 `SLURMATE_CANDIDATES` 是逗号分隔 | 一句话 | 它是**分号**分隔（`--export` 按逗号切） |
| R17 | 未经登记就往 `PLUGIN_SESSION_FIELDS` 里写键 | **一句话** | 守护进程的白名单**静默丢弃**它 —— 客户端永远看不到，**而没有任何报错** |
| R18 | 依赖宿主那些**没有**正式承诺的函数（§5.3 下半） | 一句话 | 它们是内部实现，随时可变 |
| ~~R19~~ | ~~假设"守护进程会报出清单里的未知键"~~ | **机器** | **不是红线。** 两侧都报，判据是 [`tools/manifest-keys.json`](../tools/manifest-keys.json)，见 R1。编号保留、**不重用** |
| R20 | 请求超过站点配额，或**同时开很多会话** | **机器**（`rate_limited`） | 见账本 S25。多开让这件事成了日常问题 |
