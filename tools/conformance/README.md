# 符合性向量

**三份实现对同一批字节必须得出同一个答案。** 这个目录就是"同一批字节"。

| 文件 | 是什么 |
|---|---|
| `tree/` | 固定的输入树。每一份文件都故意挑过，见 `tree/README.md` |
| `expected.json` | 期望的内容摘要 + 期望的**包字节**（十六进制）+ 逐份 sha256 + 一份带签名的包 |
| `bad.json` | 一批坏包（常量十六进制）+ 每条的 `change`（改了哪几个字节）+ 期望的**理由词** |
| `generate.mjs` | 造出上面两个文件的脚本。**变异怎么造只写在这一个文件里** |

```
node tools/conformance/generate.mjs      # 重新生成（确定性，跑两次逐字节相同）
```

## 谁读它

| 端 | 用例 | 读什么 |
|---|---|---|
| 打包器 | `packer/test-packer.mjs` | 打出来的字节 == `expected.json`；23 条坏包全拒且理由词相同；**顺带把客户端那一份读方拉进来对答案** |
| 守护进程 | `cluster/test-sessiond-logic.py` 的 19.14 | 同一个摘要、同一批理由词 |
| 客户端 | `client/test/plugin-package.test.mjs` | 同一个摘要、同一批理由词、验签、签名不影响摘要 |

## 为什么是常量而不是文件

坏包**不能**是磁盘上的文件：三端拿到的字节必须**逐字节相同**，而"各自用自己
语言里的库去造一个坏包"必然造出不同的字节 —— 那时"三端都拒了"这句话就退化成
三句各说各的。所以坏包是**十六进制常量**，三端只做 `bytes.fromhex(...)`。

代价是它们不可读。对价是两条：

1. 每一条都带 `change`（改了哪几个字节）与 `why`（为什么这该被拒）；
2. 变异**只在 `generate.mjs` 里造** —— 一份引擎，不是三份。

于是 `bad.json` 的每一行都是复核过的：`generate.mjs` 里那个 `CASES` 表连的是
"种进去的变换"与"期望的理由词"，跑一次就是一次对账。

## 判的次序也是契约

一个包同时犯两条时，先判哪条决定了报出来的是哪个词。次序写在
`docs/PLUGIN-CONTAINER.md` 的 **A.4**（那份规范的附录 A），三端照抄 —— 所以这里断言的是
**逐条相等的词**，不只是"拒了"。词表有九个词，`bad.json` 里每一个词都有
坏包钉住（有一条用例断言这件事：有一个词没人守，就是一条没人守的判据）。

## 两条刻意留下的"不一致"

- ★ **`needs: "verify"` 的坏包，守护进程**预期会收下**。**
  站点不验签（§6 没有给它这条义务），验签是客户端的事（§5.4）。所以这不是漏掉
  的检查，而是一条**有断言的**事实 —— 19.14 里那两条断言就是
  "守护进程收下了它"。把一条被省掉的检查写成一个有断言的事实，比让它悄悄躺在
  那里好。
- ★ **`expected.json` 里那把签名钥匙是公开的，种子写死在 `generate.mjs` 里。**
  这不构成问题：签名在这套东西里只表达"与上一次是同一把钥匙"（§5.4 的钉表），
  没有证书颁发机构。一把谁都知道的钥匙冒充不了任何**已经**被钉住的 `id`。
  写死种子是为了**重新生成时逐字节相同**——早先是每次现铸，于是每跑一次
  `expected.json` 里的公钥与签名都换一遍，而那份 diff 一个字节都不意味着什么。

## 改输入树之后

`expected.json` 会过期，三端的用例会**一起红**。那是设计：它是夹具，不是数据。
重新跑一次 `generate.mjs` 即可；**别去手改那两个 JSON** —— 手改等于把夹具挪到
实现那一边去。
