# 符合性向量的输入树

**这不是一个能用的插件。** 它是 `tools/conformance/expected.json` 里那份期望值的
来源 —— 一份固定的输入树，三份实现（打包器 / 守护进程 / 客户端）各自对它跑一遍，
必须得到同一个内容摘要、同一份包字节。

树里每一份文件都是**故意挑的**，逐条对应一条会被写错的规则：

| 路径 | 它钉住什么 |
|---|---|
| `plugin.json` | 负载里必须有它；它自己进摘要，而摘要**不**含目录名 |
| `lineage.json` | ★ 血统表（§2.5）—— 它在**源码树里**，所以它也在**负载里**（§3.6）。表里那条记的是下面那把夹具钥匙，于是"包里的表"与"签这个包的钥匙"是对得上的（`verify` 会核对这件事） |
| `README.md` | 最普通的一份 —— 对照组 |
| `client/index.js`、`client/extra.js` | 两条边长为同一段的两条路径（`/` 分段） |
| `job/start.sh` | ★ 它是 `100755` —— 包**丢得掉**这个位（§3.2 定死 `0644`），所以打包器必须**说一声** |
| `cases/empty.txt` | 零字节的一份（`size = 0` 与"没有这一份"必须分得开） |
| `cases/zeros.bin` | 内容里有 `0x00` —— 一切"按行读"的实现在这里露馅。（它**不叫** `nul.bin`：`NUL` 是 §3.3 禁止的 Windows 保留名，而这条规则真的会红 —— 我第一版就叫了 `nul.bin`，打包器当场拒了） |
| `cases/crlf.txt` | 内容是 CRLF —— 行尾归一化会让包在 Windows 上算出另一个摘要 |
| `cases/中文.txt` | 路径与内容都是非 ASCII |
| `cases/😀.txt`、`cases/￿.txt` | ★★ **排序的判据**。UTF-8 字节序里 `EF BF BD` < `F0 9F 98 80`（`￿` 在前），而 JS 的 `<` 比的是 UTF-16 码元（`U+FFFD` vs `U+D83D`），**次序正好相反**。用 `<` 排的实现在这里分家 |

★ 后两条路径的第二个字符是 `U+FFFD`（替换字符）：它落在 `U+E000..U+FFFF` 这一段，
而 UTF-16 里非 BMP 字符的第一码元是 `U+D800..U+DBFF` —— 两者相比，UTF-8 与
UTF-16 给**相反的答案**。换一个 BMP 低位的字符（比如 `中`）就测不出来了。

改这棵树 ⇒ `expected.json` 会过期 ⇒ 三端的用例一起红。**那是设计**：
它是夹具，不是数据。
