# slurmate-packer

插件作者的打包器。单文件、零依赖（只用 `crypto` / `fs` / `os` / `path` /
`child_process`），只要一个 `node`。

发布形态是单个文件：每个版本的 Release 上有一个 `slurmate-packer-<版本>.js`，
与客户端安装包、站点包同一页。在仓库里则直接跑 `packer/slurmate-packer.js`。

命令一律是 `node slurmate-packer.js <动词>`。没有单独安装的 `packer` 命令。

```sh
node slurmate-packer.js init    path/to/your-plugin
node slurmate-packer.js keygen  path/to/your-plugin     # 想签名才需要这一步
git commit -am "铸一个 id（和一把钥匙）"
node slurmate-packer.js build   path/to/your-plugin
node slurmate-packer.js sign    <id>.splug
node slurmate-packer.js inspect <id>.splug
```

产出的 `.splug` 发布到作者的网站 / GitHub；站点管理员下载下来交给安装器。
服务器上从头到尾没有源码树 —— 打包发生在作者的机器上。

规范：`packer/docs/PLUGIN-SPEC.md`（§2 身份、§3 包、§4 签名、§5–§7 运行）与
`packer/docs/PLUGIN-CONTAINER.md`（容器格式，即那份规范的附录 A）。

## 六个动词

| 动词 | 做什么 |
|---|---|
| `init <目录> [--fork] [--adopt]` | 树里没有 id 时铸一个 ULID，**插入**写回 `plugin.json`，并在血统表里记一条。树里**已经有** id 而血统表不认识它时它会停下来问（§2.5），两个答案是 `--fork`（这是**另一个**插件，换 id）与 `--adopt`（这是**同一个**插件、只是记录不在了，补一条） |
| `keygen <目录>` | 给这个 id 定一把 Ed25519 钥匙：公钥进血统表，私钥进钥匙库（`0600`）。钥匙库里**已经**有一把（§4.1 的〈换机器 = 复制 .pem〉）就**认它**，不铸新的 |
| `build <目录> [--commit <ref>] [--out <文件>] [--reuse-version]` | 从一个**提交**打出一个 `.splug`。它**不看钥匙库**，但会判负载的大小上限（§3.7，见下）；树带 `site` 时还判作业侧那四条断言（〈作业侧契约〉） |
| `sign <包> [--out <文件>]` | 给一个已经打好的包盖上签名 —— **不改内容摘要**，所以不必重新打包 |
| `verify <包> [--against <目录>[@<ref>]] [--expect-digest <hex>] [--expect-signer <指纹>]` | 逐份校字节、算摘要、验签，并核对血统表与签名者；`--against` 顺带判 §3.6 |
| `inspect <包> [--json]` | 打出包里到底有什么 —— 拿它对着规范逐行核对 |

`build` 会在产出之前判负载的大小上限（§3.7）：单份 ≤ 256 KiB、加起来
≤ 1,561,905 字节、份数 ≤ 256。超了它拒绝，并给出数字与是哪一条。

那是发布之前唯一会说话的地方：站点那边只有一条管理员看得见的告警，客户端那边要等包
发出去、收下来才拒。这几个数与守护进程、客户端那两份由用例钉着逐字相同；它们为什么
长这样写在 `packer/docs/PLUGIN-SPEC.md` 的 §3.7。

清单里带 `site` 的树，`job/start.sh` 还要过四条断言：无 shebang、有 `start_<短名>`、
函数带命名空间、定义之外没有语句。判据与站点编织时同一套，作者不必先有一台集群。
（没有 `site` 的树不判 —— 它不装到站点上，作业侧也就不会被执行。）

## 树里的、机器上的：三样东西分开放

| | 放哪 | 谁写 | 为什么在那儿 |
|---|---|---|---|
| **血统表** `lineage.json` | **源码树里**，提交进 git | `init` / `keygen` | clone 要带着它走 —— §2.5 要求"这个 id 是谁签的"**本地可判** |
| **私钥** `<id>.pem` | 作者机器上，`--home` 底下 | `keygen` | §4.1：它属于**这个插件**，换机器的方式是**整份复制**它 |
| **发布表** `releases.json` | 作者机器上，`--home` 底下 | 每次 `build` | 每打一次就变，进树就会把树弄脏，与 §3.5 打架 |

`--home` 默认 `~/.config/slurmate/packer`，也可以用 `$SLURMATE_PACKER_HOME`。
用例与 CI 必须换掉它：不换的话跑一次就往家目录里写字，而且第二次跑会撞上
下面〈三处"停下来问"〉的第 3 条那道闸（夹具树故意会变，而版本号不变）。

血统表在负载里（它是一份普通文件，不在跳过集里，§3.6），所以：

- `sign` 不必知道源码树在哪 —— 表跟着包走，别人打好的包也签得动；
- `verify` / `inspect` 能发现"表里说这个 id 归 K1、而签这个包的是 K2"这种陈旧；
- 代价：给表加一条记录就是改内容，按 §2.4 必须升版本号。所以正常次序是
  「init → keygen → 提交 → build」，而不是"发出去之后再补签"。

## 为什么 `init` 与 `build` 是两条命令

铸 id（以及 `keygen` 写血统表）会弄脏源码树，而 §3.5 要求打包的输入是一个
干净的提交。一条命令做完两件事必然自相矛盾。所以它们只改树、把树弄脏，
然后停下来，等作者自己提交。

## 三处"停下来问"，以及为什么不能代选

1. 树带着 id，而血统表不认识它（`init` / `build` / `keygen`）。两种可能的后果相反：
   真分身时铸新 id 是正解；"这条记录不在了"时铸新 id 是代价（所有已同意的用户重新
   同意一次）。

   所以停下来，两条路连同后果一起说，而这两条路各有可执行的形式：`--fork` 与
   `--adopt`。`--adopt` 记下的是作者的一次声明（"这个 id 归这棵树"），它不证明这棵
   树就是当初铸出这个 id 的那一棵。打包器判不了那件事，真正守它的是客户端那张按 id
   的钉表（§5.4）。
2. 要签的钥匙与血统表里的不是同一把（`sign`）。要么找回那份私钥（§4.1：私钥
   要有备份），要么走 `--fork`。在这里另铸一把没有用 —— 客户端钉的是旧那一把。
3. 同一个 `(id, 版本)` 算出第二个摘要（`build`，§2.4）。改内容的任何字节就必须
   升版本号；唯一的例外是"这一版从来没发出去过"，那要显式加 `--reuse-version`。

## 六条容易写错、这里刻意写对的地方

1. 不用 `git archive`。它会读 `.gitattributes` 的 `export-ignore` /
   `export-subst`，于是包的负载能被仓库里一份属性文件改掉。这里走
   `git ls-tree -r -z` + `git cat-file`。
2. 排序按 UTF-8 字节（`Buffer.compare`），不是 JS 的 `<` —— 后者比的是
   UTF-16 码元，与非 BMP 字符的字节序相反，于是同一棵树在两台机器上算出两个
   摘要。（`cases/😀.txt` 与 `cases/￿.txt` 就是为这条准备的。）
3. 路径取自 `ls-tree`，不取自 `readdir` —— macOS 的文件系统会把文件名做 NFD
   归一化，`readdir` 拿到的字节与 git 里存的不一样。
4. 大小写折叠是 ASCII-only —— 全 Unicode 的 `toLowerCase()` 会把 `İ` 与 `i`
   折到一起，而"只差大小写"是一条拒绝规则。
5. 摘要一定自己排序，不信记录表的次序 —— 一个手写的包可以把记录按任意次序
   排，而签名盖的是摘要。（不排的话用例会当场抓住 —— 它的症状会是
   "签名验不过"，而排查的人会去查钥匙。）
6. 输出不许落在自己的源码树里 —— 否则下一次打包时那个 `.splug` 会进负载，
   摘要每次都变。落在里面就直接拒绝，一个字节都不写。

## `sign` 为什么能是一个独立动词

因为签名不改内容摘要（§4.2：签名盖的是摘要那 32 个字节，不覆盖信封）。
所以"给一个已经打好的包补签名"是合法的 —— 按 §2.4 它还是同一份构件。
两个后果：

- `build` 不看钥匙库：它的输出只是 `(提交, 选项)` 的函数，与这台机器上有什么
  钥匙无关。§3.5 那句"同一输入逐字节相同"因此没有星号。
- Ed25519 是确定性签名，所以同一个包、同一把钥匙签两次，逐字节相同。`sign` 不需要
  任何随机源。

`sign` 默认原地写（未签名的那几个字节被换掉）—— 因为它与签名后的那份是同一个
`(id, 版本)` 的同一份构件，留两个文件正是 §2.4 要防的那种混乱。想要不带签名的那
一份：`build` 会逐字节重现它。

## 测试

```sh
node packer/test-packer.mjs
```

141 条，不需要网络、不需要这个仓库处于任何特定提交状态（它自己造临时仓库）。
它顺带把客户端那一份读方（`client/src/main/plugin-package.js`）拉进来跑同一批
坏包 —— 三份实现里这两份都在 JS 里，让它们在同一批字节上给出同一个理由词，是
"三端一致"这条契约里最容易分家的一半。

## 它还没有的东西

站点侧的验签有 —— 安装器（`slurmate plugin install`）接系统 openssl 验，
并且按 `id` 记住签名者（规范 §6.4）。这件事在作者的机器上没有对应动作，写在这里
是因为它决定了两条插件作者**必须**知道的规矩：换了签名者 = 出事（管理员会被
拦下来，新包装不上），以及别把签名摘掉发新版本（那看起来像一次 §2.5 事件）。

- 跨机器的一致性。发布表每台机器一份，所以它挡的是手滑，不是攻击 ——
  与"同一个 `(id, 版本)` 只能对应一份内容"（规范 §2.4，收包方两个都不加载，
  绝不挑一个）自带的是同一个保留。
