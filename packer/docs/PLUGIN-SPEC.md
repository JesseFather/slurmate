# Slurmate 插件规范

规范版本：1

---

## 0. 这份规范写给谁

写给一个打算写插件的人。

基座 —— 客户端、守护进程、部署脚本 —— 是一份，且只有这一份。这份规范
不承诺"照着它就能另写一个客户端"：没有那个需要，也没有那个打算。

这份规范给出两样东西：

| | 在哪 | 是什么 |
|---|---|---|
| **插件必须做什么** | §2 – §4 | 插件、打包器要满足这些，才能被装上、被分发 |
| **可以依赖什么** | §5 – §6 | 基座会保证什么。写在这里是因为**插件作者需要知道**（所以哪些事不用自己想办法），**不是**因为它们是插件作者的义务 |

两者都是可断言的：§2–§4 的每一条都有打包器或收包方上的符合性用例；
§5–§6 的每一条都有基座自己的用例。一份读起来像承诺、实际没人守的保证，
比一条明写的义务更糟。

正文里没有实现进度这一栏，这是有意的：写进去会让读者把承诺读成现状，而"文件里
写着、实际什么也没发生"正是这套东西最想消灭的一类问题。进度记在各实现自己的
README 与缺陷账本里。

一条要求 = 一条「改坏了它就会红」的符合性用例。挂不上用例的要求不进这份规范 ——
它会退化成一句谁都不看的愿望。

所以不能顺手改：要改一条，先证明它对应的用例是错的。用例红了，先假设是实现错了。

附录 A（容器格式）住在单独的一份文件里 ——
[PLUGIN-CONTAINER.md](PLUGIN-CONTAINER.md)。拆开只是因为读者不同：正文写给
插件作者，附录 A 写给读包的人（三份实现要有一处共同指向的字节定义）。
把它复制到别的仓库时，两个文件一起带 —— 正文说"什么算合规"，附录 A 说
"字节长什么样"，缺任何一半都读不通。

### 0.1 规范性措辞

| 措辞 | 含义 |
|---|---|
| **必须** / **禁止** | 规范要求。不满足即不合规 |
| **应当** / **不应当** | 有理由的推荐。偏离要有说得出的理由 |
| **可以** | 真正可选的 |

## 1. 术语

- 插件（plugin） —— 一种服务。一个会话提供哪种服务，就由哪个插件负责接起来。
- 包（package） —— 插件的分发单位，一个文件（`.splug`）。见 §3。
- 信封（envelope） —— 包里除负载之外的全部字节：头 + 记录表 + 签名块。
  字节布局见附录 A（在 [PLUGIN-CONTAINER.md](PLUGIN-CONTAINER.md) 里，编号 A.1–A.5）。
- 负载（payload） —— 包里装的那棵树。包里除信封之外只有负载。
- 清单（manifest） —— 负载里的 `plugin.json`，声明插件的身份与能力。
- 构件（artifact） —— 一份具体的内容，由内容摘要标识。见 §3.4。
- 内容摘要（content digest） —— 内容的规范哈希，判"是不是同一份构件"。见 §3.4。
- 分身（fork） —— 从一份已有插件派生出来、内容不同的一份新插件。见 §2.5。
- 血统表（lineage record） —— 跟着源码树走的一份小文件，记着"这个 id 是谁签的"。
  见 §2.5。

## 2. 插件必须做什么 · 身份

清单里认得的键是一个封闭集合：多一个键不是被忽略，是整份清单被拒。

这条适用在每一个层级上 —— 顶层、`contributes`、以及 `contributes.surface` /
`.login` / `.data` 各自的内容。判据只有一份书面形式（
[`tools/manifest-keys.json`](../../tools/manifest-keys.json)），而客户端与站点两侧
都拒：客户端在装之前，站点在安装与分发的时候。所以一个拼错的键不会变成一个
"装了、但在站点上没人装得上"的包。

> 为什么：一个拼错的键（`contribution`、`contrib`、`login.pathh`）如果只是被
> 忽略，结果就是"配了但不生效"—— 写了、它没读，而没有任何地方会说出来。
>
> 判的只是键名。值的形状另有一套规则，而两套不是同一条：下面那张表说的是「写什么
> 值才算合规」，而每一格属于承诺还是细节，由 `docs/CONTRACT.md` §2 判。

清单里全部认得的键如下。这一张表是查表用的 —— 每个键的取值域与违反的后果都在这，
而为什么这么定见「详见」那一栏。

| 键 | 类型 | 必填 | 取值域 | 违反的后果 | 详见 |
|---|---|---|---|---|---|
| `id` | 字符串 | 是 | ULID，26 字符 | 拒 | §2.1 |
| `name` | 字符串 | 是 | `^[a-z][a-z0-9-]{0,31}$` | 拒 | §2.2 |
| `displayName` | 字符串 | 否 | 非空 | 拒 | §2.2 |
| `version` | 字符串 | 是 | `x.y.z`，无前导零，`y` / `z` ≤ 255 | 拒 | §2.3 |
| `description` | 字符串 | 否 | 任意，缺省空串 | 拒 | [README](README.md) |
| `author` | 字符串 | 否 | 任意，缺省空串 | 拒 | [README](README.md) |
| `engines` | 对象 | 是 | 只认 `slurmate` 一个子键 | 拒 | §2.3.1 |
| `engines.slurmate` | 字符串 | 是 | 范围片段，如 `>=0.5` | 拒 | §2.3.1 |

| `contributes.login` | 对象 | 否 | 不写 = 不自动登录 | 拒 | [README](README.md) |

| `contributes.submitPubkey` | 布尔 | 否 | 缺省 `false` | 拒 | [README](README.md) |

由 `tools/check-plugin-docs.py` 判。键名之外还有一条组合判定：
`contributes.concurrent: true` 而 `contributes.ports` 不是 `≥ 1`，整份清单被拒。

### 2.1 id

一个插件**必须**有一个 `id`：一个 26 字符的 ULID（Crockford base32，
字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`；前 10 字符是 48 位毫秒时间戳，
后 16 字符是 80 位密码学随机）。

- 铸 id 是打包器的活：源码树里没有合法 id 时铸一次，此后永不改变。
  基座不铸 id，只读它。
- 铸出之后**必须**把它写回源码树（`plugin.json`），使这棵树此后带着同一个 id。
- 写回**禁止**用字符串替换实现：**必须**是一次插入（在对象里按原有缩进插入
  `"id": …` 这一行），**禁止**把整份 JSON 解析再序列化回去 —— 那会重排键序、
  丢掉 `\u` 转义与数字写法，于是"只改了一个键"对任何一份真实的清单都是假的。
- 写回会弄脏源码树，所以**应当**在写回之后停下来提示提交，**禁止**代为提交。
- **应当**拒绝在源码树不干净时铸 id。

> 为什么：`id` 是「会在用户工作站上跑的那段代码」的身份，而同意台账按
> `id@版本` 记（§5.2）。允许第二个地方铸 id，就等于允许同一个插件有两个身份，
> 而"一份内容、多份引用"整条规则建立在"同一个 id 就是同一个构件"上。
>
> 写回要保 diff 最小，是因为打包顺手重排源码树会让这个工具没人敢用。

### 2.2 名字不是身份

- 短名 `name`（**必须**匹配 `^[a-z][a-z0-9-]{0,31}$`）与 `displayName`
  （**必须**是非空字符串）**可以**随时修改。
- 短名不需要全球唯一，也不需要在单个站点内唯一 —— 两个 `id` 不同、
  短名一样的插件允许在同一个站点上并存（它们不是同一个东西）。
- 名字、以及插件目录的目录名，**禁止**参与任何判定。

> 为什么：同一个插件被两个站点分发时能被认出来是同一个，靠的是 id 相同；两个站点
> 各写一个同名插件时能被分开，靠的是 id 不同。名字做不到这两件事。

> 这也意味着插件可以随便改名、随便把仓库目录叫成什么，都不会让已装的用户出问题。

同一个站点上真的出现两个同名插件时，"名字 → 哪一个"就只能在寻址那一层
解决：**必须**写 `<id>.conf`／`service_kind` 填 id，写短名指不到具体哪一个。挑一个
的后果是"哪个生效"取决于遍历次序 —— 那是没人会想到去查的地方。判据绝不代挑
（报错把那几个 id 都列出来），而两条路的档位不同：

| 在哪 | 歧义的后果 |
|---|---|
| **配置文件名**（`slurmate.conf.d/<短名>.conf`） | 一条警告：这一份**不生效**（那两个插件各自按清单缺省跑），**不拦启动** |
| **提交的 `service_kind`** | **硬拒绝**（`2 bad_service_kind`）—— 那里必须当场给出一个确定的答案 |

### 2.3 版本号

插件版本（这一节的前半段说的都是清单里的 `version`）**必须**匹配
`major.minor.patch`：三段十进制数字，点分隔。

1. **禁止**前导零。每一段**必须**是 `0`，或不以 `0` 开头的十进制串。
2. `minor` 与 `patch` **必须** ∈ `0..255`。`major` **可以**任意大。
   超出上界时**必须**进位到上一位（`1.255.255` 之后是 `2.0.0`）。
3. 比较规则：逐段比较，先比十进制字符串的长度，长度相同再比字典序。
   **禁止**把段转成有界的机器整数再比较。

> 为什么：前导零会造出同一个版本的两个字符串（`1.007.0` 与 `1.7.0` 数值相等、字符串
> 不等），而按 `(id, 版本)` 查表是精确字符串比对。于是同一个插件会出现两个槽位、两次
> 同意、两份目录，而"升级"会被判成"没升"。

> 不转机器整数是因为：IEEE 754 双精度在 2^53 以上失精，会让
> `9007199254740993.0.0` 与 `…992.0.0` 判等，而任意精度整数不会，两侧于是不一致。

> 按字符串比与数值序完全一致，不依赖任何整数精度，这才让第 2 条里那个"`major` 可以
> 任意大"真的成立。

> `0..255` 的价值是挡住把日期或提交号塞进版本号。版本号是 §2.4 的唯一执行手段：它要
> 是能随手造新值，"改了内容就升版本号"就退化成"改了内容就换个号"。

校验，不归一化。打包器与收包方只判合不合上面三条，
**禁止**把不合规的版本号改写成合规的（`1.256.0` 不许变成 `2.0.0`，
`1.007.0` 不许变成 `1.7.0`）—— 那是静默改版本号，与 §2.4 直接冲突：
两侧算出来的 `(id, 版本)` 会不是同一个键，而"升级"会被判成"没升"。
不合规就是不合规：拒绝，并说出来。

#### 2.3.1 第二个版本号：框架版本

清单里还有一个 `engines.slurmate`。它说的不是插件，而是跑它的那个
基座 —— 客户端、守护进程、协议是同一个号（下面叫它框架版本）。

- `engines` 是可选的。不写它 = 对基座没有任何要求。
- 写了它就必须是一个普通对象，而且只允许 `slurmate` 这一个键 ——
  多一个认不得的键（`node`、`python`……）会被拒，不是被忽略。
  `null`、数组、以及整个 `engines` 写成一个字符串，同样被拒。
- `engines.slurmate` **必须**是一个非空字符串，内容是空格分隔的比较式合取：
  `>=` `>` `<=` `<` `=` 之一紧接一个框架版本，如 `>=0.5`、`>=0.5 <0.7`。
- 框架版本**必须**是 `major.minor`：两段十进制数字。
- 三条纪律与上面完全一样：**禁止**前导零、`minor` ∈ `0..255`、
  逐段按十进制字符串比较。只是没有 `patch` 那一段。
- **禁止**写三段（`>=0.5.0` 是一个看不懂的片段，不是"`>=0.5`"）；
  **禁止** `^`、`~`、`||`、逗号；两段之间**禁止**空格（`>= 0.5` 同样看不懂）。
- 整条范围全部满足才算通过；不满足、看不懂、或者是空的，这个插件就不被接受。

两侧都必须满足，而且它们判的是两件事。插件有两半 —— 客户端那一半跑在
用户机器上（那台机器上是客户端的版本），作业侧那一半跑在集群上（那台机器上是
服务端的版本）。两半各判各的，都得过：

- 客户端判不过，用户那一侧装不上（例如客户端 0.9 而插件要 `>=1.0`）；
- 服务端判不过，站点根本不分发它（例如服务端 0.5 而插件要 `>=0.6`）。

而"满足"不等于"能用"：这条范围是必要条件，不是兼容性承诺。基座的大版本
之间不保证兼容（见 [PROTOCOL.md](../../docs/PROTOCOL.md)〈三方：谁不低于谁〉）——
而这也正是只声明真正需要的那一版的理由 —— 随手写一个很高的下限，会白白挡住
本来装得上的基座。

> 为什么 `minor` 只到 255：`major` 那一档是"可以不兼容"、`minor` 那一档是
> "加东西但不破坏兼容"，所以 256 个 `minor` 对一条"低频更新"的线来说相当宽裕 ——
> 上界设在那里是为了让"同一个版本号只有一个字符串"这件事成立（三段位数不固定的话，
> `1.007` 与 `1.7` 会同时存在）。到顶了就进位（`0.255` 之后是 `1.0`），
> 而进位意味着一次大版本：那一次才可以不兼容。

> 为什么：两套版本号长得像，但段数不同，而写错段数的后果是确定的 —— 拒绝加载，不是
> "宽松地理解成对的那个"。理由与上面第 1 条是同一个：`0.5` 与 `0.5.0` 是同一个意思的
> 两种写法，而任何一处"我以为它懂"的地方，最终都表现为"升级之后我的插件忽然不加载，
> 而报错只说清单不合法"。

> 顺带一个后果：框架版本没有第三段，所以"补丁级兼容性"在这个字段里表达不出来 ——
> 需要那个粒度就声明一个更大的范围（`>=0.5 <0.7`）。

### 2.4 一个 `(id, 版本)` 只有一份内容

- 内容不可变。改了内容的任何字节，就必须升版本号。
- 同一个 `(id, 版本)` 下出现两份内容不同的构件时，收包方会两个都不加载并报错。

> 为什么：取错的那一方会静默地跑另一个插件的代码，而用户完全看不出来。宁可让这个
> 插件暂时不可用，因为那种失败是看得见的。

> 实际含义：发出去的版本号不能"回收再改"。改了东西就发新版本号。

"一份内容"要按侧读。同一个 `(id, 版本)` 在路上有两个包：
给站点的整包，与站点转手给客户端的只含客户端侧那一份（§3.1）。它们的
字节不同（少了一半负载、信封也不同），而它们是同一份内容 —— 两侧的负载
都逐字节取自同一棵树，而四元组签名（附录 A.3）把两侧各一份摘要都盖住了。

所以这一条的判据是逐侧的：每一侧各自只有一份内容。站点不会把"客户端侧那一半变了"
当成"你发了个新包"，客户端手里也根本没有站点侧那一半。它只有自己那份，用它自己算
出来的摘要去对签名里属于它的那一个。

### 2.5 分身必须铸新 id

从一份已有插件派生、且内容不同的插件，**必须**铸一个新的 `id`。

- 判据是机械的：包的签名者与本机血统表里这个 id 的签名者不同，客户端就拒绝。
- **禁止**在一棵树带有 `id`、而本机血统表又不认识它时静默换 id 或静默沿用 id。
  打包器**必须**停下来，把两种可能（真分身 / 换了钥匙）连同各自的后果说清，由作者决定。
- 站点装这个包时也会停下来问同一件事（§6.4）—— 它按自己记住的那把钥匙判，
  与客户端各记各的（两边都不会替对方做判断，也不该做）。

> 为什么：分身沿用 id 会让两个不同的东西抢同一个 `(id, 版本)`（§2.4），后果是一个
> 站点的分身能把另一个站点正在用的插件弄坏 —— 这是"会给插件起个名就能发动"的跨站
> 拒绝服务。

> 停下来问而不是自动铸新 id，是因为"真分身"与"我丢了自己的钥匙"后果相反：后者铸新
> id 意味着所有已同意的用户重新同意、正在跑的会话变成"未知服务"。那是把"我丢了钥匙"
> 变成"我换了个插件"，不能代选。

> 血统表跟着源码树走（**应当**提交进版本控制）：这样别人 clone 下来的树带着它，
> "这个 id 是谁签的"本地就有答案，手滑的情形全部机械可判。唯一无法机械判的是血统表
> 被人从树里删掉 —— 那是故意的，不是手滑。

> 血统表是插件目录根上的 `lineage.json`（`id → 签名者公钥`），由打包器写：它 `init`
> 时记一条、`keygen` 时把公钥填进去，由作者提交它。不要手改 —— 它进负载（它是一份
> 普通文件），所以改它就是改内容，而按 §2.4 那要升版本号。

### 2.6 同一站点里不许两个插件同 id

- 同一个站点里，两个插件**禁止**自报同一个 `id`。犯了就是安装会被拒绝。

> 为什么：作业侧产物按 `id` 命名（一个插件一份），两个插件同 id 就是后写的覆盖先写
> 的，而那是静默的。

> 它拦不住跨站点的那一种（分身在一个站点、原件在另一个站点），那一种归 §2.5 的签名
> 管。
>
> 它是对插件作者的要求，不是基座的保证。

### 2.7 运行时的数据存在哪儿，由清单声明

插件在运行中会产生用户攒下来的数据（界面布局、登录 cookie 这类）。基座为它准备
了一份身份：

```
<插件 id> / <共享组> / [<数据空间 id>]
```

第三段有没有由 `contributes.ports` 决定（`≥1` = 要一个本地端口 = 要不要一份
origin）；`contributes.concurrent` 管的是另一件事（能不能同时开第二份），
见 §2.8。

- `contributes.data` **可以**不出现。不出现是合规的（见下）—— 这不是"少配了一样
  东西"。但能不能同时开两份是另一格，而且那一格必填（见 §2.8）。
- `contributes.data` 出现时**必须**是一个对象，只允许 `inherit` 与 `perVersion`
  这两个键，多一个键就是安装会被拒绝。
- `inherit` 出现时**必须**匹配 `^[a-z][a-z0-9-]{0,31}$`（这个串会进磁盘路径）。
- `perVersion` 出现时**必须**是 `true` 或 `false`。
- 两个键答的是同一件事（共享组那一段写什么），所以同时写是错误 —— 安装会
  被拒，报错点名这两个键。（`perVersion: false` 与 `inherit` 不冲突：它说的正是
  "不要每个版本各一份"。）

| 清单里写的 | 共享组那一段 | 意思 |
|---|---|---|
| **两个都不写**（缺省） | 一个固定常量 | **所有版本共用一份** |
| `"inherit": "editor"` | `editor` | 写了这个名字的几个版本共用一份 |
| `"perVersion": true` | **该插件的版本号** | 每个版本各一份 |

> 为什么缺省是"继承"：一个新版本读不懂旧数据时，用户看到的是界面一片错乱，看得见
> 也修得好（删掉重配）。反过来，「每个版本悄悄攒一份没人再看过的数据」是静默的，而且
> 会一直攒下去。没人管比读错更糟，所以缺省是继承。

> 代价是缺省之下一个改过数据格式的新版本会读到旧格式的东西。出路两条：声明
> `perVersion: true`；或者新版本自己判断读不读（基座交给它的是路径，读不读由新版
> 自己定）。

> "能不能同时开两份"没有缺省，它是必填的 —— 而这里的理由与上面正好相反：那一格答的
> 是"插件代码能不能同时处理两份"，基座答不了。

> 缺省无论取哪一边都是基座替插件作者表态：取"不能"，一个真能多开的插件永远不知道
> 为什么只能开一份；取"能"，一个没想过的插件会得到一个静默的第二份。所以它必须由
> 清单说，见 §2.8。

共享组名由插件作者自己起，两个插件正好都叫 `editor` 完全正常：身份的头一段是插件 id。

运行期的那一半：客户端按"槽"决定"两个会话能不能同时活"（
`client/src/main/plugin-data.js` 的 `slotOf`）—— 要工作区的会话按那一份数据分槽，
不要工作区的一整类共用一个槽。§2.8 里声明的那一格与它必须一致。

槽按数据分，不按工作区分 —— 于是同一个工作区里两个不同的插件可以同时活着
（它们天然是两份数据）。而同一个插件的同一份数据上，第二个会话被拒。

同一份身份有两个落点，而框架保证两边用的是同一个身份：

| 落点 | 谁写 | 怎么拿 |
|---|---|---|
| **浏览器存储**（localStorage、cookie…） | 插件自己的页面写 | 框架建的，插件什么都不用做 |
| **插件的数据目录** | **插件自己**在客户端的主进程里写文件 | `ctx.dataDir()` 给出一个绝对路径 |

那个目录由身份算出来，所以它和"用户在界面上看到的那一份"是同一个东西，这正是"看得
见、删得掉"能成立的原因。目录可能还不存在 —— 它在第一次真的写东西时才出现（框架不
代建，自己 `mkdirSync(dir, { recursive: true, mode: 0o700 })`）。

不要自己发明位置，比如写进 `~/.slurmate/<自己挑的一个名字>/` 这类路径。自己发明的
位置，基座既不知道它在哪儿，也没法列给用户看。

`ctx.dataDir()` 不收参数。第三段由框架从这条会话填（就是那个工作区里
属于这个插件的那一份数据），它和 `ctx.session()` 一样不用管 —— 与 `ctx.login()`
同一条理由：一个不传的参数，没机会传错。

这份数据在用户的机器上是"看得见、删得掉"的。客户端有一块界面列出没有任何连接在用
的那些数据，并给用户一个删除按钮。删的时候两个落点一起删（浏览器存储与磁盘上的文件
是同一条清单项的两半）。

所以别把用户重建不出来的东西只放在这里 —— 放了就要接受"用户点一下它就没了"，而且
那时候没有任何东西会提醒。

"没有任何连接在用"还有一种发生方式，它不由用户按下删除按钮：这一份数据在没有任何
工作区引用它、也没有任何活会话拿着它的时候自动删掉。

"引用"就是工作区那张表：一个工作区把它名下的每个插件指到一份数据上。所以删掉一个
工作区不一定删掉它指过的数据 —— 那份数据还被别的工作区指着时，它一个字都不动。

反过来，不要工作区的插件没有第三段、不属于任何工作区，它不会被任何一次回收带走
（`~/.ssh/config` 那行 `Include` 指着的东西就是这一类）。

哪一边是想要的，取决于"用户重建它有多贵"。

第二档：临时那一份，跟着会话走（见 §2.8 —— `concurrent: true` 的第二份
及以后）。它的起点是持有者那份在开局那一刻的快照，而它在会话结束时消失：
数据目录、浏览器存储、本地端口全部回收。所以：

| 清单声明的是 | 那份数据的生死 |
|---|---|
| `ports: 0`（没有第三段） | 一直留着，直到**用户**在面板上删掉它，或者它变成下面第四行那种 |
| `ports` ≥ 1 | 它跟着**引用它的那些工作区**走：最后一个引用它的工作区没了、也没有活会话拿着它，就一起删。它**不**跟着单条连接走，也不跟着某一个工作区走 |
| `concurrent: true` 开出来的**第二份及以后** | 跟着**那一次会话**走，会话结束就没了 |
| **上面任何一份，一旦"按当前装着的插件再也算不出来"** | **下一次打开客户端时自动收掉**（最多等到那时候）。判据是"盘上有 ∖ 按现在的清单算得出 ∖ 没有任何活会话认领"，三者同时成立才收 |
| **更早的身份算法留下的分区**（名字是 `slot-…` / `layout-…` / `plugin-…` 那种形状） | **同样在下一次打开客户端时自动收掉**（面板上会单列出来）。那些名字是按**更早的身份算法**造的，**按现在的清单永远算不出来**，而里面躺着的是那时候的登录 cookie —— 不会再被任何东西读到 |

判据只有一条：其中"持久"的那一份是开局那一刻先来的那个。所以要攒的东西，
必须写得下"只有一份在攒"这件事 —— 两份各自攒各自的，这一格今天给不了（那就声明
`false`）。

那一行（"再也算不出来"）是怎么发生的：换了共享组（改了 `inherit`），或者用户把那个
版本从本机删掉了。从那一刻起，旧名字再也算不出来。

判据不是"引用它的工作区没有连接在用它"。那个工作区还在配置里，下一次有连接指过去
（或者那个插件重新装回来）就会读它，所以它在清单上只列不删，一份都不会被自动收。

注记（写给基座实现者）：身份的两端**必须**在各自的入口处校验形状：共享组名在清单
校验里，数据空间 id 在配置读取里（那是用户能改的文件）。

身份会变成磁盘上的目录名，所以"校验"与"拼接"**禁止**分家。基座**禁止**在拿不到第三
段的情况下把它当成"一份共享的"
来实现：那是一句谎话，且症状是两份数据互相覆盖。

### 2.8 能不能同时开两份，由清单声明（必填）

```json
"contributes": { "ports": 1, "concurrent": true }
```

- `contributes.concurrent` **必须**出现，**必须**是 `true` 或 `false`。不写就安装被拒
  —— 这一格没有缺省，理由见下。
- `true` 时**必须**同时有 `contributes.ports` ≥ 1。犯了也是安装会被拒绝。

| 值 | 意思 |
|---|---|
| `true` | **插件的代码能同时处理两份**：客户端允许同一时刻有两个这个插件的会话，第二个拿一份**临时的**副本 |
| `false` | 同一时刻只能有一个 |

> 为什么没有缺省。这一格答的是"你的代码能不能同时处理两份" —— 基座推不出来。
> 特别注意：「一个端口都不要」（`ports: 0`）与「不能同时开两份」是两件事，别把它们
> 混起来：`ports` 说的是"这份数据要不要一个本地端口与一份浏览器存储"，
> `concurrent` 说的是"你的插件能不能有两个同时活着"。

> 为什么 `true` 要求一个端口。第二份就是第二份数据（一份临时的副本），"哪几条连接算
> 同一个"由用户在那个工作区里说了算。没有第一份就没有"第二份"可指。

> 所以一个端口都不要的插件一律只能写 `false`。这不是对插件的额外要求，是那一格在物理
> 上没有第二份可发：它的对外身份（写进用户 ssh 配置的那个别名）是插件自己造的，基座
> 既不知道它是什么，也发不出第二份。

> 于是两层判据都要过：基座算资源（这一份要的东西，它发不发得出第二份），插件答代码
> （它的实现能不能处理两份）。

> 架构不允许的那一类照样要写 `false`，因为那是两条独立的事实，一条变了另一条不跟着
> 变。而基座代答的那一天，插件会在自己没表态的情况下多开出一份。

> 这里的「资源」与 CPU/内存/GRES 那个「资源」是两回事，别互相套。这一段的「资源」指的
> 是基座手里的东西够不够分（并发的第二份、工作区、数据）；而 `submit` 里那个
> `resources`（`cpus` / `mem` / `gres`）指的是向集群要的算力 —— 那个由管理员在 Slurm
> 上定，插件管不着（见 [PROTOCOL.md](../../docs/PROTOCOL.md) 的〈`gres`：一个结构化
> 描述符〉）。

> 同一个词两个意思，两边都会碰到这个词，所以各自限定。

> 不设数量。`true` 就是"能"，开多少份都是同一个逻辑；上限由站点那一侧管
> （`max_sessions_per_user`，以及每个插件那一份配置里的 `max_sessions`）。

> 范围要说清，否则这一格会被读大。它是本机的声明：基座在这台客户端上不会给出第二
> 份。它不是"一个用户只有一份"这条规则 —— 那一层在站点，两格都在那里
> （全局的 `max_sessions_per_user` 与这个插件自己的 `max_sessions`，见
> [CONFIGURATION.md](../../cluster/docs/CONFIGURATION.md)），而它们的缺省压在安全侧。

> 两条合起来：一个没改配置的站点上，写了 `true` 也只能开一份。别把"我声明了能多开"
> 读成"用户一定能多开"。反过来，想全局只允许一份也不靠这一格，站点配额自己就够。

写了 `true` 之后，第二份是什么（这一段决定插件该怎么做）：

- 第一份是"持久的"那一份：它的数据就是那个工作区里属于这个插件的那一份
  （`<插件 id>/<共享组>/<数据 id>`），与单开时逐字相同 —— 不会搬家，也不会因为
  多开而重置。
- 第二份及以后是临时的：它拿到一个新的数据 id、一个新的本地端口
  （于是是一份空的浏览器存储 —— localStorage 按 origin 隔离，新端口就是新
  origin）、以及一份持有者那份数据的快照（客户端在开局时拷一份）。
  它的一切在这个会话结束时消失：数据目录、浏览器存储、端口，全部回收。
- 持有者结束后，已经开着的那几份不会"升格"：它们是什么就是什么。下一个
  新开的会话才认领持有者那一份。
- 所以：多开时只有一份能攒数据，而"哪一份"是"开局那一刻谁先来"决定的。
  如果插件需要"两份各自攒各自的东西"，这一格今天给不了 —— 别写 `true`。

注记（写给基座实现者）：`ports` 与 `concurrent` 是两条独立的声明，而它们
在运行期的落点都是"槽"（`slotOf`）。认领的规则是：开局那一刻看这一份数据上有没有
活会话 —— 没有它就是持有者，有（且作者允许开第二份）就给它一份临时的。

五条只有实现者用得上的事实（前四条不这么做会删掉活数据，第五条会让
"临时"变成"永久"，所以都写在这里）：

1. 磁盘上的目录名是折叠过的。那一步是 `EscapePath(ToLowerASCII(分区名去掉
   persist:))`（`electron_browser_context.cc`），所以插件 id 那一段落盘时是小写。

   `EscapePath` 不逃 `@`（它逃的是 `#%:<>?[\]^{|}` 与反引号、控制字符、非 ASCII），
   所以 `@` 当分隔符能活着到磁盘上。分区目录的根是 `sessionData`
   （`app.getPath('sessionData')`）加 `Partitions`，不是 `userData`（两者今天相同，
   所以这是一处"恰好对"）。
2. 判断"某一份是不是孤儿"必须正向算，不能逆向解析那个目录名。正向是把配置里那张
   数据表里被工作区引用着的身份都算出来，两边折叠后做差。

   它不是"每个插件 × 每个工作区"：数据 id 是铸出来的，推不出来，而推出来的那些会把
   每一份活着的数据都算成孤儿。

   逆向是解析目录名、认不出来就当垃圾。而第二段可以是版本号（声明了
   `data.perVersion: true` 的插件就是），加上折叠，一个活着的版本会被判成"认不出来"。
   逆向解析只配用来写一句人能读的解释，不配当判据。
3. 第二个落点的"该有的"入口不能照抄第一个。数据目录那一侧不由框架建（它是插件
   自己调 `ctx.dataDir()` 建的，数不出来），所以那张"该有的身份"表必须按注册表里的
   所有插件算。

   照抄"有界面的插件"，会让没有界面却会写数据的那一份正被用着的数据一诞生就是孤儿，
   而界面上会给它一个删除按钮。放宽是安全方向（孤儿变少），且在分区那一侧不改变任何
   行为：多算出来的身份在磁盘上没有目录，不产生行。
4. 数据目录这一侧的两个身份必须同名。段之间用 `@` 拼成一个目录名，不是
   `<插件 id>/<共享组>/<数据 id>` 那样分层。

   分层的话，`<插件 id>/<共享组>` 会既是两段身份的数据目录、又是三段身份的父目录 ——
   而这两份身份真的会同时存在（同一个插件的一个版本声明 `ports: 0`、另一个版本声明
   `ports: 1`），于是"删掉没人用的那一份"会把正在用的那份连根删掉。单段名字让两份
   身份永远是兄弟。
5. 临时那一份必须被对账"护住"，而且两个根都要护。那一份不在配置里，它算出来的
   身份就永远不在"该有的"那一张表里，于是天生长得像一个孤儿，而界面上会给它一个删除
   按钮 —— 落在用户正在写的那份数据上。

   护住它的是"此刻正被活会话拿着的名字"（`audit` 的 `held`），而它**必须**由两个根
   合并而成：浏览器存储分区由窗口持有，插件数据目录由会话持有。只收前者的那一份，
   护不住没有界面的插件（以及临时那一份在数据根下那一半）。

   同理，回收一个临时的调用点**必须**排在销毁那块视图之后。反过来写的话，"正被用
   着"那道守卫还看得见它，于是每一次回收都在盘上留下一份垃圾，而症状看起来像"没清
   干净"，不像"次序错了"。

## 3. 插件必须做什么 · 包

### 3.1 一个插件是一个包

一个插件**必须**以单个文件（一个包，`.splug`）分发。包里**必须**同时容纳作业侧
与客户端侧，基座按需激活 —— 客户端不读作业侧，站点不读客户端侧。

"一个包"说的是交给站点的那个形状（整包，一次带走两侧）。而站点发给
客户端的是另一个包 —— 只含客户端侧的那一份：`client/**` + `plugin.json` +
`lineage.json`。站点从整包里现打，用的是同一次签名（附录 A.3：签名块
不覆盖信封字节，所以少了一半负载也不必重签，而站点手里也没有私钥）。

所以用户机器上没有 `job/**`。这件事有一个可执行的判据：客户端解包时拒绝
任何含站点侧路径的包（拒整份，不是把那几份跳过 —— 跳过会把"有人塞了东西"
变成"安静地少装了几份"）。

包**必须**能表达"某一侧为空"：只有声明式一侧、或只有作业侧的插件是合法的。
后者（没有客户端侧）落到客户端手里就是"一个只有清单与血统表的包" —— 合法，
只是它在界面上不带任何代码。

> 为什么：作业侧与客户端侧是配套的。分开发就等于让"两半版本不一致"
> 成为可能，而"两边配套"正是分发要解决的问题。

### 3.2 负载里只允许普通文件

包的信封头**必须**记录一个格式版本号（`format`，本规范版本 1 即 `1`）。
信封的字节布局在[附录 A](PLUGIN-CONTAINER.md)（规范性）里写死了 ——
那不是"实现细节"，因为
打包器要把那个字节序列造出来，而收包方会一个字节一个字节地判它。

负载里**禁止**出现除普通文件之外的任何条目：

- **禁止**目录条目。目录结构**必须**由文件路径里的 `/` 表达。
- **禁止**符号链接、硬链接、命名管道、设备节点、套接字。
- **禁止**空目录 —— 它没有表达形式，因此不可能出现。
- 所有文件的权限位**必须**由格式规定，不随包携带。版本 1 规定为 `0644`。

> 为什么：这是 §3.4 那条摘要公式成立的前提。磁盘上的一棵树可以含符号链接、空目录、
> 各种权限位，每一种都是一次"摘要相同而内容不同"的机会。

> 比如 `client/x.js` 是指向 `../y.js` 的链接，与它是"内容恰好为 `../y.js` 的普通
> 文件"，两者行为天差地别（一个加载 `y.js`，一个导出一个字符串），而摘要可以完全
> 相同。格式不允许这些东西，问题就不存在。

> 权限位定死 `0644` 不疼：作业侧脚本是被内容拼进作业脚本的，权限位不参与任何事；
> 客户端侧代码是被加载器读的，也不需要可执行位。

> 要放宽的正确方式是"在清单里声明"（例如声明"这个路径要 `0755`"），不是把权限位还给
> 文件系统 —— 因为清单是一份文件、在负载里，所以"需要可执行"仍然是内容的一部分，
> 仍然进摘要。

### 3.3 路径规则

负载里每一条路径**必须**是以 `/` 分隔的相对路径，并且：

- **禁止**为空、**禁止**含 NUL、**禁止**含反斜杠（**禁止**把 `\` 翻译成 `/` ——
  一侧翻译而另一侧不翻译就是歧义的来源）；
- **禁止**以 `/` 开头、以 `/` 结尾、含连续的两个 `/`；
- 每一段**禁止**为空、为 `.`、为 `..`；每段**必须** ≤ 255 字节；
- 段数**必须**不超过深度上限（版本 1 为 8）；
- **禁止**出现下列跳过集合里的任何一段（逐字，区分大小写）：
  `.git`、`.github`、`.gitignore`、`.gitattributes`、`node_modules`；
- **禁止** Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`–`COM9`/`LPT1`–`LPT9`，
  不区分大小写，含带扩展名的形式）、**禁止** Windows 上不合法的字符
  （`: * ? " < > |`）、**禁止**任何一段以空格或点结尾；
- 每一条路径**必须**是合法的 UTF-8 字节序列；
- 同一次打包里，两条路径**禁止**只差大小写，也禁止完全相同。

任何一条不满足就拒绝整个包，不是拒绝那一条。

"只差大小写"的判据是只折叠 `A`–`Z`。禁止用"全 Unicode 的大小写折叠"
（JS 的 `toLowerCase()`、Python 的 `str.lower()`）—— 它们会把 `İ`（U+0130）
与 `i`、`K`（U+212A KELVIN）与 `k` 折到一起。这是一条拒绝规则，口径不一致
就意味着同一个包在一台机器上装得上、在另一台上装不上，而报错里一个字都不会
提到大小写。

"完全相同"那半条是补上的。只禁"只差大小写"时，两条逐字相同的路径是
合法的 —— 而它们带着两份不同的内容时，内容摘要有定义（它按路径排序后拼接），
可解出来的树是歧义的（哪一个字节该落到那个路径上？）。

"路径必须合法 UTF-8"那半条也是补上的。不合法的字节会被解码器悄悄换成
`U+FFFD`，于是摘要算的是一个被替换过的字符串 —— 两端算的不是同一份东西。

> 为什么：收包方会对同一条路径再判一遍 —— 发包方可能被换过，"对面已经判过"不构成
> 省略的理由。而"一个说不清的清单"本身就是"这份东西不能信"。

> 大小写那一条的坑在落盘之后：macOS 与 Windows 的文件系统不区分大小写，两条只差大小
> 写的路径会互相覆盖，而摘要是写入之后的磁盘上算的 —— 于是用户同意的是另一棵树。

### 3.4 内容摘要

内容摘要是判"是不是同一份构件"的唯一判据，**必须**按下面的公式计算：

```
内容摘要 = sha256(
    对全部文件按路径排序（逐字节比较，与语言/区域设置无关）之后，
    依次拼接： 路径的 UTF-8 字节 ‖ 0x00 ‖ sha256(该文件内容的字节) 的十六进制小写 ‖ 0x0A
)  的十六进制小写
```

**禁止**把任何别的东西拌进这个哈希：**禁止**包含容器字节、信封头、压缩参数、
打包器版本、时间戳、作者身份、目录名。清单里写的字段会进摘要 ——
但仅仅因为清单是一份文件。

> 为什么：如果这个值跟打包器有关（信封格式、时间戳、压缩参数），"同一份内容"就会算
> 出两个身份，而 `(id, 版本)` 只有一个槽位，按 §2.4 两个都不加载。

> 于是 §2.2 要保的那件事（同一个插件被两个站点分发就识别为同一个）会变成坏事。对插件
> 作者的实际含义是：同一棵树，谁在哪台机器上打包，都必须得到同一个摘要。这是 §3.5 那条
> 要求的来源。

### 3.5 打包的输入是一个提交，不是工作树

- 打包器**必须**以版本控制里的一个提交为输入，**禁止**以工作树为输入；
  工作树不干净时**必须**拒绝打包。
- 对同一个输入，打包器**必须**产出逐字节相同的包。

> 为什么："同一份源码"需要一个精确的定义，否则工作树里多一个编辑器临时文件就是"两个
> 结果"，而那是打包器再确定也救不了的。

> 从提交打包时，可复现性由版本控制系统保证（例如 `git archive` 对同一个 tree 的输出是
> 确定的：uid/gid 写 `0`、mtime 取提交时间），不需要自己写规格去守。

### 3.6 负载等于源码树

包的信封头**禁止**对负载做任何变换、混淆、加密或隐藏。解包得到的树**必须**
与源码树里那棵树逐字节相同。

"源码树里那棵树"指的是过掉跳过集（§3.3）之后的那棵树。不这样读的话，这一条与 §3.3
是字面矛盾的：真实的源码树几乎总有一份 `.gitignore`，而它是 §3.3 禁止出现的路径 ——
于是"逐字节相同"永远不成立，"少了一份文件"也说不清。

唯一说得通的读法是：负载 = 源码树减去跳过集，而减去的东西必须被说出来（打包器要把
跳过了什么打出来，不许静默少东西）。

字节取自版本控制里的 blob，不是检出之后的字节（附录 A.5）。`text=auto`
一类的属性会在检出时改行尾，而 §3.4 要的是"谁在哪台机器上打包都是同一个摘要"。
也正因为如此，打包禁止用 `git archive` —— 它会读 `.gitattributes` 的
`export-ignore` / `export-subst`，于是负载能被仓库里一份属性文件改掉，
而打包的人看不出来。

> 为什么：这一条就是「不混淆、不加密、没有隐藏字节」那句话的判据形式 ——
> 那句话本身钉不住，这一条钉得住：任何混淆、加密、藏字节都会让这条红。
>
> 而这对插件作者也有用：装包的人（站点管理员、以及最终的用户）能读到
> 将要在这台机器上执行的东西 —— 一份能被读的插件才有人敢装。

### 3.7 包有多大

这一节要说的只有一件事：上限是有的，而且它们之间是一条算得出来的关系。
具体数值不住在这份规范里（见附录 B）—— 它们住在 `tools/plugin-limits.json`，
三份实现各持一份常量，各有用例与 CI 的 lint 钉着它们逐字相同。

| | 管什么 | 今天的值 | 谁执行 |
|---|---|---|---|
| 单份上限 | 负载里**任何一份**文件的字节数 | 256 KiB | 客户端（读方）+ 打包器（产出时） |
| 整体上限 | 负载里**所有**文件加起来的字节数 | 1,561,905 字节（≈ 1.49 MiB） | 同上 |
| 份数上限 | 负载里有几份文件 | 256 | 同上 |
| 深度上限 | 一条路径最多几段、一段最多几字节（§3.3） | 8 段 / 每段 255 字节 | 三份实现 |

整体上限不是一个拍出来的数，它是算出来的：整包上限（2 MiB）减去信封在
最坏情况下的长度。而信封的长度是精确的（附录 A.1）：

```
包 = 头(20) ‖ 记录表 Σ(2 + pathlen + 8 + 32) ‖ 签名(0 或 188 + verlen) ‖ 负载 Σsize
```

按 §3.3 允许的最长路径（8 段 × 每段 255 字节 + 7 个 `/` = 2047 字节）与份数上限
（256）算下来，信封最坏要占 535,247 字节（约 522 KiB）—— 所以负载的整体上限
只能是 `2 MiB − 535,247`。于是「按上限做出来的包，一定装得下」是一句算出来的
结论，而不是碰巧成立的。

签名那一项为什么是 `188 + verlen`：签名块盖的是四元组（附录 A.3），而版本串那一段
的长度是一个 u8，最坏 188 + 255 = 443 字节。

所以"版本串超过 255 字节的插件签不了名"是同一个 u8 的另一面 —— 而那不是一个理论上
的边界：版本号的正则没有限制 `major` 段的上界。

站点只能收紧，不能放宽。上表是协议允许的最大值。一个站点可以在
`plugins` 那一项里自报更小的数，而客户端取两者中更严的那个 —— 那几个数字是
本站自述的，拿自述去放宽读方的护栏等于让被告自己定刑期。

这些不需要插件作者自己算。`packer build` 会在产出之前判，超限时给出数字、告诉作者
是哪一条。那是发布之前唯一会说话的地方：站点那边只有一条管理员看得见的告警
（`--check-plugins`），客户端那边要等包发出去、收下来才拒。

> 为什么这一节不写"你必须小于 1.49 MiB"：那样写的话，改一个数字就要改一次
> 规范，而附录 B 明写这些数值可以演进。这里给的是关系（谁由谁推出来、
> 往哪个方向不能松）—— 它比数字稳，而数字由那三份常量与它们的用例守着。

## 4. 插件必须做什么 · 签名

### 4.1 密钥属于插件

签名是**可以**选的：包**可以**不带签名。但一旦带，本节全部适用。

- 一个插件**应当**对应一把签名密钥。私钥属于这个插件，不属于某台机器 ——
  换机器的方式是复制私钥。
- 私钥**禁止**出现在源码树里（也就是**禁止**进版本控制）。它**必须**放在源码树
  之外 —— 树里的东西会被提交、会被分发，而一个提交出去的私钥等于血统当场作废，
  且没有办法收回来。
- 包的签名**必须**带公钥（自签名即可，本规范不要求任何证书颁发机构或注册表）。
- 公钥**必须**以可复制的形式暴露给用户（指纹），以便人工核对。

> 可操作的建议只有一条：私钥要备份。

> 为什么：私钥是"血统"的载体，丢了就是血统断了。而 §5 里那条"客户端会钉住插件公钥"
> 意味着丢了私钥就不能换一把接着发 —— 老用户会拒绝，只能给这个插件铸一个新 id
> （§2.5），让所有人重新同意一遍。

> 这是诚实的结果，不是需要兜掉的失败。而正因为这个后果明确、不致命，密钥管理从"绝
> 不能出错"降级成"最好别出错"，这才让它是一件可做的事。

### 4.2 签名覆盖四元组

签名**必须**覆盖这四项：插件的 id、它的版本号、站点侧的内容摘要、客户端侧的
内容摘要。**禁止**覆盖信封字节，也**禁止**覆盖包文件的整体哈希。签名块的
字节布局与被签消息怎么拼（两个摘要是原值 32 字节，不是十六进制写法）在
附录 A.3 里写死。

> 为什么：信封的格式会演进（今天加签名槽，明天加别的）。签名盖在信封字节上，每动
> 一次信封所有签名全废，而且"同一份内容、两个包"要两个签名。

> 那后半句是真的用上了：站点发给客户端的就是"同一份内容的另一个包"（§3.1）。两项进
> 被签消息各有各的用处。

> - `id` 与版本进了消息，两份构件就配不错对。少了它们，一份构件可以被改名成另一个
>   插件、或者把版本换掉，而签名照旧成立。

> - 两侧各一份摘要进了消息，站点就改不动客户端侧任何一个字节。改了就与签名里那一半
>   对不上，而客户端自己会算（它手里有那一半的每一份文件）。

> 第二条是"拆包不减安全"的机械证明：不是"我们相信站点"，是"它做不到，而做没做到是
> 可判的"。

> 而"签名不覆盖信封"这一条，正是"站点重打包不必重签"的全部依据。站点手里也没有
> 私钥，本来也重签不了 —— 那是设计，不是缺陷。

## 5. 插件可以依赖什么 · 客户端

这一节是对基座的要求，写在这里是因为插件需要知道。它不是插件的义务。

### 5.1 装插件只有一条路

- 插件进"池子"**必须**只经由"安装一个包"这一个动作。
- 往池目录里手工放置内容**必须**不产生任何效果：那些内容**禁止**出现在插件
  列表里、**禁止**被加载，**禁止**被当作"某个站点要给你装的东西"呈现给用户。
- 客户端**必须**能区分并分别陈述这三种"你没有这个插件"：① 站点不支持分发；
  ② 站点支持但这一份没下来（给出原因）；③ 本机有一份，但没有任何站点报过它。

> 对插件作者的实际含义：别在文档里教用户"把目录拷到某处"。那件事在设计上
> 不产生任何效果 —— 用户照做之后会看到"什么也没发生"，而那是这套东西里
> 最难查的一类症状。要发插件就发包。

### 5.2 装之前会问用户一次

- 装一个带客户端代码的插件之前，**必须**要用户点一次同意。
- 台账**必须**以 `(id, 版本)` 为键、以全长内容摘要为值。
- **禁止**给任何一类插件开免同意的口子。

> 对插件作者的实际含义：插件第一次被装、以及内容变了之后，用户会看到一个
> 对话框，里面是它的名字、它从哪来、以及摘要变成了什么。
> 所以 `displayName` 与 `description` 是写给用户看的，不是写给自己看的。

注记（写给基座实现者）：同意界面**必须**说清用户在同意什么 —— 至少包括"这段
代码会在这台机器上以完整权限执行"、它来自哪里、以及内容与上一次相比变了什么。台账
条目**必须**绑定摘要值（回写前再核一次）。**应当**先写台账、后激活插件。

理由是：一个恶意的清单也在往这台机器上放东西。一个登录契约可以让客户端往某个地址
提交一个口令，那是数据不是代码，但仍然是站点的指令。而规则一有分支，绕过它的路就会
长出来。

### 5.3 删掉本机那一份 = 撤回同意

- 删掉本机一个构件，台账里对应的那条**必须**一并消失，下一次对账**必须**重新走一遍
  同意闸。
- 这一条**禁止**被实现成"静默装回来"。也**禁止**在文案里断言是用户删的 ——
  客户端不知道原因，它只知道"不在了"。

> 为什么：删除是一个没说出口的决定，而对账不认识它。若只删内容、台账那条
> 还在，下次同步会按"摘要与台账相符"静默装回来、一个字都不问 ——
> 那不是"当作从来没有过"，那是"用户想让它消失，它自己回来了"。

### 5.4 客户端会钉住插件的公钥

- 客户端第一次接受某个 `id` 的构件时，**必须**记下它的签名公钥（首次即信任）。
- 此后任何自报同一个 `id` 的包，**必须**核对其签名者是否为同一把公钥；
  不同就必须拒绝，并**必须**把两把公钥的指纹都说出来。
- 内容没变而签名者变了，必须拒绝。

> 这是插件作者最需要知道的一条保证 —— 它就是 §4.1 那句"丢了私钥只能铸新 id"的来
> 源，也是 §2.5 里"分身"唯一能被机械判出来的地方。

> 为什么：一致性判据判不了"作者换了人"。分身升个版本号，在一致性台账上就是一条全新
> 的正常条目，用户看到的是一次普通的"要不要装新版本"。

> 一致性判据与认证判据不是一回事，禁止合并：摘要回答"还是不是我同意的那一份"，
> 签名回答"是不是我以为的那个人"。合并会得到一个看起来更强的检查，而它挡不住"第一
> 次给的就是坏的"。摘要跟内容同行、由同一个工具写下，它挡得住事后偷换，挡不住首次
> 欺骗。

> 首次即信任的固有弱点：全新的、从没见过这个 `id` 的客户端会被先到的包钉住。这条
> 没有本地解法；本规范不假装有。

## 6. 插件可以依赖什么 · 站点

同样是对基座的要求，写在这里是因为插件需要知道。

### 6.1 绝不谎报成功

站点**禁止**在任何一个字节没送达或与声明不符时报告成功。报告成功时，客户端
磁盘上的内容**必须**按字节就是站点那一份。**禁止**截断：发出去的那一份超出本站
通报的上限（`package_bytes`）时**必须**明确失败，绝不截断了发出去。

> 对插件作者的实际含义：要么完整送到、要么明确失败。插件作者不会遇到"用户那里那一份
> 只到了一半"这种状态，而那种状态是没法查的。

> 线上只有一条投递方式：一份包一次发下去 —— 散装字节那条路不可能存在，因为它证不了
> 签名者。而发下去的那一份只含客户端侧：`job/**` 与其它只属于站点侧的路径一个字节都
> 不出站点，所以"发出去的那一份"比整包小。

> 上面这两条对它成立，尤其是禁止截断：一个被截断的容器在客户端那里根本解不开，而
> 它只会被报成"这个包坏了" —— 指向的是插件作者，不是那条链路。

### 6.2 判据是能力缺席，不是这次失败

- "这个站点支不支持分发"**必须**由一个协议事实判定，**禁止**由"这次下载
  成不成功"判定。
- 下载失败时，**禁止**回退到本机自装的任何一份。

> 为什么：把两者合并，等于给一个能让下载失败的人（断流、丢包、中间人）一个
> 把用户降级到旧本地副本的开关 —— 攻击成本从"改内容"降到"让下载失败"，
> 而后者便宜得多。

### 6.3 不知道谁在引用时，什么都不删

- 引用表读不出来或写不下去时，站点**必须**只报告、**禁止**回收任何内容。
- 写引用表**必须**在回收之前。

> 对插件作者的实际含义：站点不会因为这一版暂时没被报出来就把它删掉。
> 内容不可变（§2.4）加上这一条，意味着一次网络抖动不会让用户丢掉已经装好的版本。

### 6.4 站点也会验签，而且它自己也记得"上一次"

站点装上插件的包时**必须**：

- 验那个签名（§4.2 那四项）—— 用系统上现成的密码学实现，不自己写；
- 把签名者记下来，此后同一个 `id` 的包**必须**是同一把钥匙签的，否则
  停下来问管理员（§2.5），并把两把指纹都报出来；
- 包没有签名是允许的（§4.1），但记录里"上一次有签名"而这一次没有，同样
  停下来问 —— 摘掉签名正是"降级到不用验"的那一步。

"验"发生在两个时刻，不是一处：

| 时刻 | 验什么 |
|---|---|
| **装的那一刻**（安装器） | 这个包与它带来的那把钥匙**自洽吗** |
| **此后每一次**（启动对账、以及每一次分发之前） | 站点盘上那棵树**此刻**仍与签名里属于它那一侧的摘要相符吗 |

第二处不是锦上添花：拆包之后站点盘上是一棵树，而树本身不带任何校验信息
（包是自校验的，树不是）。记录表是它的解药，而"每次都重算一遍再与签名比"就是
解药起效的那个动作。少了它，有人改 `job/start.sh` 一个字节之后，它会一路被
织进作业脚本 —— 而那是以提交者本人的身份在集群上跑的。

站点验签回答的问题与客户端不一样（§5.4）。把这三个问题分清，这套东西才
立得住：

| | 回答什么 | 依据 |
|---|---|---|
| 站点验签 | 这个包与它带来的那把钥匙**自洽吗** | 包本身 |
| 站点记签名者 | 这一次的**钥匙**与上一次是同一把吗 | 站点**自己**的记录 |
| 客户端钉公钥 | 这一次的钥匙与**用户当初同意**的那把是同一把吗 | 用户**自己**的决定 |

第一个挡的是传输损坏与就地改字节，第二个挡的是"管理员被喂了一个换了钥匙的包"，
第三个挡的是"站点被整个换掉"。三个都只能靠各自那一侧的记忆 —— 谁也不能替
谁判。

> 对插件作者的实际含义有两条。

> - 换了签名者 = 出事。§2.5 说过丢了私钥只能铸一个新 `id`，这里就是那条规矩在
>   站点侧的落点：管理员会被拦下来，而那个新包在那之前装不上。

> - 别把签名摘掉发一个新版本。那看起来像"退回到不签名"，站点会当成一次 §2.5
>   事件处理。

> 站点不、也无法替插件作者回答"这个包是不是那位作者发的"：钥匙是随包一起来的，能改包的
> 人也能把钥匙一起换掉。授权在客户端那一侧（§5.4），靠的是用户点过的那一次同意。
